    《深入理解 AI Agent》精读：第一章 AI Agent 入门

    2026-08-04 AI 深入理解AI Agent | in AI
    AI Agent Agent ReAct 读书笔记

    书名：深入理解 AI Agent：设计原理与工程实践（作者 bojieli / 李博杰，Pine AI 首席科学家）

    本章：第一章 AI Agent 入门（全书的概念地图）

    配套代码仓库：https://github.com/bojieli/ai-agent-book（chapter1/ ~ chapter10/，实验编号"实验 X-Y"）

    0. 全书背景（引言）

    • 本书源自 2025 年 8-10 月图灵《AI Agent 实战营》技术讲座，目标是把 Agent 设计从"感觉驱动"变成"原则驱动"。

    • 成书方式：whisper coding（口述式协作）——作者向自己的语音 Agent 口述提纲，由它调研、整理初稿，再反复讨论打磨。语音带宽约为打字四倍。

    • 核心立场：实践在前，命名在后。Skill、harness、loop engineering 等名词不是 Anthropic 先发明、业界才使用，而是大量 Agent 早就这么做，Anthropic 才提炼成原则。

    • 作者实战背景：Pine AI——第一个能自主与真人交互、可靠处理涉及金钱的敏感复杂长程任务的通用 Agent（打电话协商账单、交涉退款、取消订阅，全程无人工接管），可靠性要求倒逼出本书的架构原则。

    • 领先业界的实践举例：Skill 流行前就用动态加载提示词解决提示词膨胀、命令行工具解决工具列表膨胀、系统状态栏解决环境感知问题；harness 流行前就用类似 Claude Code 的方法解决工具调用不稳定/幻觉/越权；loop engineering 流行前就用"提议者-审核者"（proposer-reviewer）解决模型过早认为任务完成。

    • 赶在名词流行前就知道怎么做，靠两点：①拥有对 Agent 能力上限要求极高的真实业务与真实反馈；②建立评估（Evaluation）机制——没有评估就没有进步。

    • Sutton 视角：智能体是宇宙演化中全新存在——能通过生成代码实现自举（bootstrap）和自我进化，理解自身机制并创造/改进新智能体。

    • 术语约定：reasoning 统一译"思考"（模型内部推导），inference 统一译"推理"（模型部署运行）；例外保留"逻辑推理、多跳推理、空间推理、时序推理"等固化复合词。

    1. 核心公式：Agent = LLM + 上下文 + 工具

    三者缺一不可。直观说法：大脑 + 眼睛 + 手脚。

    直觉理解 实现组件 学术概念（RL，可选） 含义
    大脑 LLM 策略（Policy） 决定"下一步做什么"的决策逻辑
    眼睛 上下文 观察空间（Observation Space） Agent 能看到的所有信息
    手脚 工具 动作空间（Action Space） Agent 能做的所有事情的集合

    • LLM（大脑）：不只是一组参数，是整个决策内核——理解意图、思考规划、做出判断。能力来自预训练（世界知识与语言能力）+ 后训练（决策策略，第七章展开）。

    • 上下文（眼睛）：每个决策点能看到的全部信息——环境信息、用户记忆、领域知识、自身状态、任务进展。

    • 工具（手脚）：能做的一切事情——预定义工具调用、按需加载的 Skills、动态生成代码创造新能力、委托子 Agent、主动与用户沟通、响应外部事件。

    1.1 观察空间与动作空间：模型与世界的接口

    • 类比计算机体系结构中的 ISA（指令集体系结构）：观察空间 + 动作空间 = LLM 与外部环境之间的接口。没进入观察空间的信息对模型来说就像不存在；没进入动作空间的操作，模型只能停留在文字建议上。

    • 底层模型固定时，提升任务表现最主要的系统工程手段 = 扩展上下文和工具（重新定义观察/动作空间）。许多看似"需要更聪明模型"的问题其实是接口问题。

    • Manus：率先把 Deep Research（搜索）、Coding（代码生成）、Computer Use（电脑操控）三条独立路线合并进同一生产级 Agent——取三类 Agent 观察/动作空间的并集，而非只换更强模型。

    • OpenClaw：本地优先的 Gateway，通过 WhatsApp/Telegram/Slack/Discord/iMessage 等消息渠道触达，经授权连接 Google Drive、Notion、云应用与本地文件系统，跨越更大数据边界。

    • 扩展空间 ≠ 把所有信息一次性塞给模型：无关上下文制造噪声、过多工具增加选择成本与安全风险。有效扩展应按需、相关、可控（检索放信息、工具发现只暴露当前需要的动作、权限控制 + 结果验证）。

    • 五类 Agent 产品的"眼睛/手脚/策略"对比：

    Agent 产品 眼睛（感知） 手脚（行动） 策略
    Cursor 等 Coding Agent 需求文档、代码库、终端环境 开放式（思考、代码搜索、文件读写、执行命令） 增量开发：理解需求→搜索→编辑→测试→调试修复
    Deep Research 等搜索 Agent 网络资源、学术数据库、本地文件 开放式（思考、搜索、网页阅读、摘要生成） 迭代深化：按已有信息调整搜索方向，综合出报告
    Browser Use 等电脑操控 Agent 屏幕、浏览器页面、文件系统 开放式（思考、点击、输入、滚动、截图、执行代码） 视觉感知+操作：观察→识别→执行→验证
    豆包等手机助手 Agent 手机屏幕、已装 App 开放式（思考、点击、滑动、输入、打开 App） 意图理解+App 操控：理解需求→定位 App→执行→确认
    Pine AI 等个人办事 Agent 用户账户信息、历史账单、服务商知识库 开放式（思考、打电话、发邮件、填表单、与用户确认） 多步骤执行：收集信息→制定策略→联系→谈判→汇报
    • 共同特征：开放式动作空间（可生成任意自然语言和代码）、能内部思考（先规划再行动）、能持续交互（根据环境反馈调整策略）。

    1.2 工具：Agent 的手脚

    按 Agent 与外界交互方向分五类：

    1. 感知工具：访问信息——搜索引擎（实时网络）、文件系统（本地文档）、API 和数据库（外部服务与企业数据）。

    2. 执行工具：改变世界——代码执行、文件操作、系统命令、外部 API 调用。

    3. 协作工具：与其他 Agent 分工——委托子 Agent、关键决策点请求人工确认、多 Agent 系统协调。

    4. 事件触发工具：与前三类本质不同——不是 Agent 主动调用，而是外部输入驱动 Agent 开始执行（新邮件、定时时间点、Webhook 回调）。

    5. 用户沟通工具：主动与用户建立连接、传递信息（文字、语音通话、邮件）。

    • 工具调用（Tool Calling / Function Calling）：让模型通过结构化方式调用外部工具，把 LLM 从文本生成器变成能执行操作的智能系统。四步流程：①在上下文声明可用工具（名称/用途/参数）→ ②模型自主判断要不要调、调哪个、传什么参数 → ③工具执行结果追加到上下文 → ④模型据此决定下一步。这是 ReAct 的基础。

    • 工具设计核心原则：通用基础能力用于组合与探索；专用工具用于约束高风险和强业务规则操作（支付、删除数据、发送邮件、生产部署等封装为参数明确、权限受限、可审计的专用工具，必要时加预览与人工确认）。

    • 通用工具（如受限 Python 代码解释器）安全要求：隔离沙盒运行、默认不能访问网络、不能读授权目录外文件、对执行时间/CPU/内存/输出大小设上限。

    • 长程任务：受控虚拟工作目录同时保存计划、中间结果、日志、最终产物，供多次执行间接续工作；限定读写路径、容量、文件类型，防路径越界，不暴露宿主文件系统。

    • 工具设计质量决定 Agent 能走多远：接口不清晰 → 模型乱用工具；错误处理不到位 → 工具失败变死锁；权限过宽 → 出错后果难挽回。MCP（模型上下文协议）正让工具接入像安装插件，但设计原则不过时。

    1.3 LLM：Agent 的大脑

    • “理解-规划-执行”：先解析真实意图（用户说的往往不是他真正想要的），再拆解任务，执行中持续判断下一步。

    • 内部思考：采取实际行动前先规划推演，不改变外部环境但显著提升行动质量；推演建立在预训练习得的结构化知识（数学定律、因果关系、问题分解策略）上，不是盲目随机探索。

    • 零样本泛化（Zero-shot）：没见过任务也能组合已有知识处理；少样本适应（Few-shot）：给两三个示范例子就能掌握新任务模式。

    • 模型即 Agent（Model as Agent）——新范式：

      • 先进模型通过后训练（尤其强化学习）把工具调用能力内化为原生能力：何时调用、调哪个、传什么参数由模型自己决定，无需人工编排。

      • 关键区分（本书特别澄清）：RL 内化的是决策策略（用不用、怎么用），工具本身及执行仍由 Agent 框架/API 内置工具在服务端提供（如 Kimi 的 Formula 服务端脚本引擎）。编排循环没有消失，而是从客户端移到服务端，决策权交给模型。

      • Kimi K3（实验 1-2）：Moonshot AI 2026 年发布，约 2.8 万亿参数 MoE（专家团队按问题类型自动选专家），100 万 token 上下文，原生视觉理解，思考模式常开；突出优势是长链工具调用稳定——连续 200~300 次工具调用保持思考一致性；提供 K3 Max（对话与 Agent 任务）与 K3 Swarm Max（大规模并行）；开源。

      • GPT-5.6（实验 1-3）：提供 Sol/Terra/Luna 三种规格；自由格式工具调用（type: "custom" 直接发原始文本如 Python 代码/SQL，免 JSON 转义——是 API 参数格式演进而非模型架构革新）；Verbosity 参数（控制详略）、Reasoning Effort 参数（控制思考深度，Sol 有 max 档）；Responses API 内置 web_search + code_interpreter，服务端闭环 Deep Research 的"搜索→阅读→分析→再搜索"；意图澄清机制——接到任务先提问确认真实需求（如"用哪个数据源？要哪些指标？"），弥合"用户说了什么"与"用户真正想要什么"的差距。

      • 无厂商绑定可复现：阿里云百炼 qwen3.7-plus Responses API 同样内置 web_search 与 code_interpreter（配套代码 chapter1/search-codegen 已跑通）。

    • Harness 隐喻：马具不是限制马的奔跑，而是把力量引导到正确方向；或赛车保障系统（安全带、护栏、进站团队）——车手（模型）越快，这套系统越重要。

    • 苦涩的教训（The Bitter Lesson）：Harness 里的约束/验证/纠正有多少是"人的先验"终将被模型内化？本书立场八个字：方向认同，节奏务实——模型会持续吃掉 Harness（工具调用、长程规划曾是外部编排，如今已是原生能力），但"吃"远比直觉慢（训练以月计，无法一次内化真实业务的约束与偏好）。Harness 工程不是对苦涩教训的抵抗，而是该教训在工程时间尺度上的实践：模型还做不稳的 Harness 先补上；模型每内化一层，Harness 就卸下一层、转而兜底新的能力前沿。

    • Agent 学习机制三条路径（按更新位置与持续时间）：

      1. 上下文适应（任务内）：示例/状态/检索结果进上下文，立即调整行为但不改持久状态——快速、低成本，受窗口与信息组织方式约束（第二章）。

      2. 外部产物更新（跨任务）：事实经验→知识文档，可语言化策略→Prompt/Skill，确定性流程→程序与 Harness——可审计可修订（第三至五章、第八章）。

      3. 参数更新（训练周期）：适用于医疗影像理解、风格、隐式决策策略等高维能力——部署成本高但泛化自然广泛（第七章）。

      • 三者不是互斥分类，而是不同时间尺度上的协同：上下文负责临场适应，外部产物负责可控积累，参数负责内化难以显式表达的能力。

    1.4 上下文：Agent 的眼睛

    上下文 = 每次调用 LLM 时它实际"看到"的全部信息，五个组成部分：

    1. 系统提示词（System Prompt）：开发者编写、对话全程不变，是"岗位说明书"——定义身份、权限、行为准则；还包含跨会话用户记忆与动态注入的环境状态。

    2. 工具定义（Tool Definitions）：声明可用工具的名称、功能描述、参数格式；没有它 Agent 无法识别和调用任何工具。

    3. 用户消息（User Messages）：用户输入；可包含 RAG 动态检索引入的外部知识（覆盖训练截止后信息或私有领域知识）。

    4. 模型回复（Assistant Messages）：最多三部分——思考过程（reasoning）、文本内容（content）、工具调用请求（tool_calls）；三者不一定同时出现（要调工具时通常 reasoning + tool_calls，给最终回答时通常 reasoning + content）。

    5. 工具执行结果（Tool Results）：框架执行工具后返回的结果，是下一步思考的直接依据，让 Agent 从执行结果中学习、避免重复犯错。

    • 结构：静态前缀（系统提示词 + 工具定义）+ 动态轨迹（用户消息 + 模型回复 + 工具执行结果）。前两项不变，后三项随交互增长。

    • 消融实验（实验 1-1 ★★）——逐一去掉组件验证其作用（系统提示词作基本身份定义不参与消融）：

    去掉的组件 后果
    工具定义 Agent 完全丧失行动能力
    工具执行结果 看不到上一步反馈，反复调用同一工具，陷入无限循环
    思考过程（reasoning） 前后决策互相矛盾
    历史消息 Agent 失忆，从头重复执行已完成步骤
    • 核心洞察：上下文决定 Agent 能看到什么，而 Agent 只能基于看到的信息做决策。

    1.5 ReAct 循环

    • ReAct = Reasoning + Acting，但实际循环有三环节：想→做→看→想→做→看，直到任务完成。

    • 轨迹（trajectory）：执行过程中不断积累的消息历史（用户消息、模型回复含思考与工具调用、工具执行结果）。每次调用 LLM，完整上下文 = 静态前缀 + 轨迹。

    • 多币种收入汇总示例：第一轮分析后并行调用三个货币转换工具 → 第二轮基于结果调用代码解释器计算 → 第三轮生成最终答案。3 次迭代、4 次工具调用完成复杂多步骤任务。

    • 设计精妙处：上下文的累积性——每次调用看到完整轨迹，保持全局认知（当前阶段、试过什么、得到什么）；轨迹结构化带来高度可解释性与可调试性。

    • 轨迹不仅是记录更是能力：可分析行为模式、优化决策路径、改进工具设计，甚至总结进知识库或用强化学习训练更好模型，形成从经验中学习的闭环。

    • **实验 1-2（Kimi K3）与实验 1-3（GPT-5.6）**即展示不同模型如何驱动这个循环（见 1.3 节）。

    2. Harness 工程：模型之外的竞争力

    • 问题起点：一个能跑的 Demo 和一个可靠的产品之间还有巨大鸿沟——模型可能幻觉（编造不存在的工具或参数）、选错工具、出错无法自我恢复。

    • 生产形态完整公式：

      Agent = LLM + [上下文 + 工具 + 约束 + 验证 + 纠正] = Model + Harness

      • 最小公式是 Demo 视角，扩展公式是生产视角；后者完全包含前者并加一圈安全网。

      • Harness = 模型之外的全部基础设施。核心是"上下文 + 工具"，外加三层保障：约束（限定能做什么不能做什么）、验证（检查做得对不对）、纠正（做错了怎么补救）。

    • 退款例子对比：无 Harness 时模型看不到政策、不知调哪个 API、编造退款结果回复用户、用户发现退款没发生；有 Harness 时政策写入系统提示词（上下文）、调用 query_order/process_refund（工具）、校验退款金额不超订单金额（约束）、校验数据库确认成功（验证）、API 超时自动重试（纠正）。同一模型，有无 Harness 结果天壤之别。

    Harness 功能 一句话职责 与上下文/工具的关系
    Context（上下文） 提供感知信息 核心能力
    Tools（工具） 提供行动手段 核心能力
    Constrain（约束） 设定行为边界 安全边界
    Verify（验证） 自动判断操作结果对错 检查机制
    Correct（纠正） 发现问题自动修正或回退 恢复机制

    • 上下文与工具让 Agent"能做事"，约束、验证、纠正让 Agent"不做错事"。早期框架重前者，生产级 Agent 的重心已转向后者。

    • Claude Code 的 Harness 案例（绝大部分代码是保障机制而非工具本身）：流程状态管理、多层上下文压缩、权限分类、熔断器（错误连续发生时自动"断电"停止重试）、错误恢复机制（捕获异常→回滚→重试或交还人类）。

    2.1 工程范式演进：从提示工程到 Loop 工程

    • 演进弧线：软件工程（基础）→ 提示工程（第一波）→ 上下文工程（第二波）→ Harness 工程（第三波）→ Loop 工程 → Graph 工程（2026 年 7 月新词，未稳定）。

      • 提示工程：优化输入给模型的自然语言指令。

      • 上下文工程：系统管理模型能看到的所有信息（系统指令、工具定义、对话历史、外部知识）。

      • Harness 工程：从"模型能看到什么"扩展到"模型在什么样的系统中运行"（约束、验证、反馈循环、错误恢复）。

      • Loop 工程：从单次运行扩展到跨轮次持续自主运转（谁来发现下一件该做的事、何时验证、何时算完成）。

      • Graph 工程：把 Agent 循环、确定性程序和人工审批组织成显式执行图（节点=能力，边=路由与依赖，结构化状态沿边传递并在关键边界持久化）；不是 Loop 的替代品（循环就是带回边的图）；此处的"图"指控制流/执行图，非 GraphRAG 的知识图谱。

    • 层层包含：提示工程 ⊂ 上下文工程 ⊂ Harness 工程 ⊂ Loop 工程。模型能力越接近，竞争优势越转移到模型之外的工程实践。

    • 实证：LangChain 在 Terminal Bench 2.0（终端复杂任务基准）上 Coding Agent 从 52.8% 提升到 66.5%（排行榜 30 名开外 → 前 5），改变的只是 Harness（自动检查执行结果、检测重复循环、优化思考策略）；OpenAI 工程团队 3 人 5 个月完成约百万行代码、近 1500 个 PR，约 10 倍传统速度——背后是 Harness 做对了。

    功能 核心原则 实际例子 详见
    上下文 信息充分性：每个决策点基于足够信息判断 系统提示词、知识库、Agent 状态栏、Sidecar 旁路查询 第二、三章
    工具 接口清晰：命名直观、参数有例子、边界有说明 MCP 工具、代码解释器、搜索工具 第四章

    验证 输入隔离：安全检查只看结构化数据（如工具返回的 JSON 字段），不信任模型自由生成的文本（防提示注入操纵输出） Linter、类型系统、工具调用结果校验 第五、六章

    2.3 构建有效 Agent 的核心原则（Anthropic 经验）

    1. 保持简单：从最简单的方案开始，只在必要时加复杂度；直接 API 调用优于复杂框架，清晰代码优于聪明抽象——每多一层抽象都是以后调试时新的盲区。

    2. 保持透明：明确显示规划步骤、执行日志、决策轨迹——既为调试，也为建立用户信任；黑箱错误外部观察者无法定位也无法纠正。

    3. 设计好工具接口（ACI，Agent-Computer Interface）：从 Agent 视角设计接口（让 Agent 容易理解），而非传统 API 从程序员视角。命名与参数要直观，易误用之处从设计上让错误无法发生——如 SIM 卡缺角防插反、微波炉门未关绝不加热。制造业术语防呆（Poka-yoke）。模型与工具唯一的沟通通道就是接口，模糊的接口会被模型放大成系统性错误。

    2.4 如何选择模型

    • “御三家”：OpenAI（GPT/o 系列，能力均衡、用户最多）、Anthropic（Claude，复杂推理/编程/工具调用突出，当前 Agent 开发热门）、Google（Gemini，超长上下文 + 强多模态）。不要只看排行榜，要在自己的任务上做评估（第六章）。

    • 国内模型：豆包（国内延迟极低，适合实时交互）、Kimi（国内 Agent 能力较强）、Qwen/DeepSeek（开源，成本与可定制性优势）。不同模型工具调用能力差异很大，选型前务必在具体场景测试。访问渠道：火山引擎（豆包）、硅基流动（开源）、OpenRouter（海外统一访问）。

    • 开源 vs 闭源：闭源能力领先但贵、受厂商 API 策略限制；开源成本低、可私有化部署、支持微调，适合成本敏感或数据合规场景。

    • 策略边界：模型在基准测试中有某种能力 ≠ 产品允许用户调用（网络安全、蒸馏、提取、隐私数据、高风险操作各有策略边界）。同一任务在聊天产品、Coding Agent、API 中可能结果不同。业务关键任务要准备人工接管或其他合规模型作替代。

    • 绝大多数 Agent 需要支持思考（Reasoning）的模型：多步思考、工具选择需要复杂决策；仅单步简单任务或固定位置 GUI 点击可例外。

    • 输出速度：Agent 多轮推理，输出 token 速度直接决定端到端延迟（20 轮 × 每轮慢 2 秒 = 多等 40 秒）。

    • 多模态：需理解图片/音频/视频时是硬性要求，模型间差异大。

    2.5 编排模式：工作流与自主

    • 从简单到复杂的原则：单个 LLM 调用 → 工作流 → 自主 Agent。单次调用能解决（优化提示词和上下文示例）就不要引入 Agent；可清晰分解为固定子任务用工作流；只有需要动态决策和灵活路径才用自主 Agent。记住：Agent 系统通常用延迟和成本换任务性能。

    • 工作流（Workflow）：预定义代码路径编排 LLM 和工具，执行路径确定性，LLM 只在节点内部负责理解和生成（订机票例：核实身份→搜索航班→完成付款→确认预订，节点流转代码写死）。

      • 优势：①严格流程控制——“付款前不能预订"等业务规则代码强制执行，不依赖 LLM 判断；②安全性——执行路径确定，提示注入或模型犯错最多影响当前节点，攻击面被限制在单节点内。

      • 局限：缺乏变通性——预设流程未覆盖的情况（临时改签、航班取消需推荐替代）只能走异常分支或交还人类。

    • 自主 Agent（Autonomous Agent）：执行路径不是预定义的，而是根据环境反馈实时决定（订机票例：自行决定搜索→发现需登录→先核实身份→再搜索→发现最便宜需转机→询问用户→用户拒绝→调整条件……）。

      • 需要自主规划能力、识别失败并调整策略；必须有明确停止条件（任务完成、达到最大迭代次数、遭遇不可恢复错误），否则易死循环或过度执行。

      • 实现本质 = 循环中使用工具的 LLM（ReAct）；常见退出条件：调用最终输出工具、模型返回无工具调用的响应、遇到错误、达到最大轮次。

      • 适用：开放式问题——SWE-bench（自动修复真实 GitHub Issue）、Computer Use、需迭代搜索分析的研究任务。

      • 代价：更高成本 + 复合错误风险；需沙盒充分测试、设置护栏监控、关键决策点加人机协作检查点。

    • 混合模式：关键合规流程用工作流保可靠，灵活部分切自主（n8n 可同系统混用工作流节点与自主 Agent 节点）。

    • 主流 Agent 框架对比：

    框架/平台 核心定位 编排模式 开发方式 适用场景
    OpenAI Agents SDK 轻量级开发库 自主（工具循环） 代码优先 快速原型、单 Agent 应用
    Claude Agent SDK 生产级开发框架 自主（工具循环 + 子 Agent） 代码优先 复杂自主任务、Coding Agent

    2.6 护栏与安全性

    • 护栏（Guardrails）= Harness 中"约束、验证、纠正"层面的核心实现手段，构成分层防线：管理数据隐私风险（如防系统提示泄露）与声誉风险（模型行为与品牌一致）。可先针对已识别风险设置，再随新漏洞逐步添加。

    • 护栏也有失败方式：误拒绝——为降低危险请求放行概率，可能误拒合法但敏感的任务（授权安全测试、模型评估、蒸馏研究）。评估要双向：既测"应当拒绝的请求是否被拦截”，也测"明确允许的请求能否正常完成"；合法敏感任务应提供解释、人工升级或授权执行路径，而非笼统拒绝。

    • 按防护位置分三类：

      1. 输入侧（请求到达前拦截）——四种机制：

        • 相关性分类器：标记偏离主题查询；

        • 安全分类器：检测越狱（Jailbreak）与提示注入（Prompt Injection）。关键区别：越狱是用户自己试图绕过模型安全限制；提示注入是攻击者通过外部数据（网页内容、文档）间接操纵模型行为；

        • 内容审核：标记有害/不当输入；

        • 基于规则的保护：黑名单、输入长度限制、正则过滤器（防 SQL 注入等已知威胁）。

      2. 执行侧（工具调用时验证）——核心是工具风险评级：按操作可逆性、权限等级、财务影响标注低/中/高，高风险操作需额外审查或人工确认。

      3. 输出侧（响应返回前检查）——PII 过滤器（身份证号、手机号等个人身份信息）、输出验证（内容与品牌价值一致）。

    • Constitutional Classifiers（Anthropic 代表工业实践）三大机制：①规则驱动——用自然语言"宪法"（明确允许/禁止内容）生成合成训练数据，训练输入输出分类器；②上下文联合判断——把用户提问和模型回答放在一起检查（“食品调味料"单独看没问题，对照提问才知是化学试剂暗语）；③两级筛查——先极轻量探针直接读模型内部激活（近零成本）检查所有对话，可疑处再交更强分类器复审而非直接拒绝，第一级误报多也不影响体验、成本低。

    • 人工干预（Human in the loop）：关键保护措施，部署早期尤为重要（识别失败模式、发现边缘情况、建立评估周期）。让 Agent 无法完成任务时优雅移交控制权（客服升级人工、Coding Agent 交还开发者）。两种主要触发情况：

      1. 超过失败阈值：为重试/操作次数设上限，超过则升级人工。

      2. 高风险操作：敏感、不可逆或高风险（取消订单、授权大额退款或付款），至少在团队建立足够信心前触发人工监督。

    3. 本章小结（书中原文要点）

    1. Agent = 大脑 + 眼睛 + 手脚：LLM 是大脑（决策核心），上下文是眼睛（决定能看到什么），工具是手脚（决定能做什么）。三者缺一不可。

    2. 扩展眼睛和手脚是最主要的能力杠杆：模型固定时，扩展观察空间与动作空间（即上下文和工具）往往能直接把原本不可解的任务变为可解；Manus 与 OpenClaw 的演进都说明通用性来自接口边界扩大，且必须按需、配合权限控制与验证。

    3. 眼睛（上下文）是决定性因素：上下文 = 静态前缀（系统提示词 + 工具定义）+ 动态轨迹（消息历史）；消融实验表明去掉任何组件系统都显著退化；ReAct 循环的本质是通过不断追加轨迹让模型持续推进任务。

    4. Harness 是竞争力所在：模型能力正在商品化，真正差异在于 Harness——围绕上下文和工具构建的约束、验证与纠正机制，确保 Agent"可靠地做事"；生产级系统中 Harness 绝大部分代码在做保障机制。

    5. 从工作流到自主 Agent：先优化提示词，再考虑工作流，最后才引入自主 Agent——降低意外风险最实用的顺序；每种编排模式各有适用场景，不存在通用最优解。

    6. 安全是架构问题：护栏、人工干预、对齐（alignment）——安全问题从第一行代码就要考虑，而不是上线前打补丁；贯穿模型、上下文、工具、协作和社会五个层面。

    4. 思考题（共 10 道，星级标注）

    • ★★ 如果只能给一个 Agent 系统增加一项能力——更强的模型、更丰富的上下文、还是更多的工具——你会选哪个？什么条件下选择会改变？

    • ★★★ ReAct 循环中每次 LLM 调用都看到完整历史轨迹，随轨迹增长成本是二次方增长。能否在不丢失关键信息的前提下打破这个二次方？

    • ★★ “模型即 Agent"范式下模型工具调用决策越来越自主，但本章论证 Harness 工程重要性反而增加。两个趋势如何共存？Agent 框架未来核心价值体现在哪？

    • ★★ 消融实验中"工具结果反馈"缺失导致无限循环。生产环境中除工具结果缺失外还有哪些情况会导致无限循环？如何设计检测与终止机制？

    • ★ 用感知、行动、策略三个维度分析一个你日常使用的 AI 产品，评估其架构设计是否合理、有何改进空间。

    • ★★ 设计航班订票客服系统，选工作流还是自主 Agent？能否在同一系统混合两种模式？

    • ★★★ 工具风险评级中，若某工具大多数情况下低风险、特定参数组合下高风险（如 delete_file 删普通文件 vs 删系统文件），如何设计动态风险评估？

    • ★★ 本章产品表格中所有 Agent 动作空间都是"开放式"的。受限动作空间（只能从预定义选项选择）在什么场景下反而优于开放式？

    • ★★ 人工干预要求 Agent"优雅移交控制”，但用户可能不在线、响应慢、指令模糊，此时 Agent 该怎么办？

    • ★★★ 引言称"好的设计原则应该穿越模型的迭代周期"。试举一个你认为可能随模型进步而过时的当前 Agent 设计原则并说明理由。
