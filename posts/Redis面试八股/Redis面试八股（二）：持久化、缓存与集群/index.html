    Redis 面试八股（二）：持久化、缓存与集群

    来源：面试八股资料整理（redis八股-上.pdf、redis八股-下.pdf），结合 Redis 官方文档口径校正。 定位：Redis 面试八股第二篇，生产实战向。事务与 Lua、持久化、缓存三兄弟、一致性、热点治理、集群，这些问题是面试中区分是否真正在生产环境用过 Redis 的分水岭。 收藏：本系列收录于 后端八股复习指南。

    一、Redis 事务与 Lua 脚本

    1. 事务的基本用法

    Redis 事务把多个命令打包，按顺序执行且中途不被其他命令插入。用 MULTI 开启，命令入队，EXEC 执行，DISCARD 取消队列。WATCH 提供乐观锁，事务执行前监听指定 key，如果事务外部的其他客户端修改了被监视的 key，EXEC 时整个事务不执行。

    如果 WATCH 的 key 是在事务内部被本事务修改的，事务可以正常执行，只有外部修改才会触发中止。

    2. 事务满足 ACID 吗

    Redis 事务和我们理解的关系型数据库事务不是一回事，实际开发中很少用，比较鸡肋。

    • 原子性不满足。Redis 事务不支持回滚，执行过程中某条命令出错，其他命令照常执行。官方解释是没必要支持回滚，错误应该在开发期暴露，支持回滚会让实现复杂且拖慢性能
    • 隔离性天然满足。单线程串行执行，事务不会被其他命令打断
    • 持久性无法保证。持久化与 AOF 的 fsync 策略有关，always 才基本满足，默认配置下事务提交后可能丢数据
    • 一致性在命令都正确的前提下可以得到保证

    3. Lua 脚本

    Redis 2.6 起支持 Lua，一段脚本当作单条命令原子执行，执行过程中不会有其他脚本或命令插入，还能在脚本内做简单逻辑，批量操作且不需要多次网络往返，是替代事务的主流方案。

    但 Lua 脚本也不是万能的：脚本中途出错后，出错前已执行的写操作无法撤销，所以它同样不能提供数据库式回滚的原子性；Redis Cluster 下脚本的 key 必须都在同一哈希槽才能保证原子。Redis 7.0 新增的 functions 可以看作比 Lua 更强的脚本机制。

    4. pipeline

    pipeline 把一批命令一次性发给服务端，只需一次网络往返，减少 RTT 与 socket 开销。它和原生的 MGET、MSET 批量命令的区别：

    • 原生批量命令是原子的，pipeline 非原子
    • pipeline 可以组合任意命令，原生批量命令类型固定
    • 原生批量命令由服务端实现，pipeline 需要客户端与服务端配合
    • 控制单次批量数量，避免网络数据量过大

    注意 pipeline 不适合有依赖顺序的命令，前一条的结果要喂给后一条时用 Lua。在 Redis Cluster 下无论原生批量命令还是 pipeline，都受限于 key 必须落在同一哈希槽，跨槽需要客户端自行处理。

    二、持久化

    Redis 是内存数据库，但支持持久化，重启后能恢复数据。有 RDB、AOF 与二者的混合三种方式。

    1. RDB 快照

    RDB 把某个时刻的内存数据生成紧凑的二进制快照文件。默认配置按时间与变更次数触发，官方默认是三组条件，3600 秒内有 1 次写、300 秒内有 100 次写、60 秒内有 1 万次写，满足任一即触发。通过 fork 子进程生成快照，正常情况下不阻塞主线程。

    优点：文件紧凑、恢复快，适合冷备与全量恢复。缺点：两次快照之间的数据会丢，实时性差，不适合做增量持久化。

    2. AOF 追加文件

    AOF 以追加方式记录每一条写命令，实时性远好于 RDB。它把写命令追加到内存缓冲区，再由 fsync 刷到磁盘，刷盘策略由 appendfsync 配置：

    • always，每次写操作都 fsync，数据最安全，但性能最差
    • everysec，每秒钟 fsync 一次，默认值，兼顾性能与安全，最多丢 1 秒数据
    • no，由操作系统决定何时刷盘，通常约 30 秒一次，性能最好但丢数据风险最大

    AOF 文件会持续增长，需要 AOF 重写压缩，重写时生成当前数据集的最小命令集。随着命令越来越多，恢复时重放全部命令比 RDB 慢，文件也更占空间。

    3. 混合持久化

    Redis 4.0 引入混合持久化：AOF 重写时以 RDB 格式生成文件头部，之后新增的写命令以 AOF 格式追加。重启加载时先加载 RDB 部分快速恢复再补增量，兼顾 RDB 的加载速度与 AOF 的数据实时性，是生产环境的推荐配置。

    重启加载顺序：开启 AOF 时优先加载 AOF 文件，否则加载 RDB。混合持久化启用后，AOF 文件头部带 RDB 内容，加载逻辑自动识别。因为持久化始终有丢失窗口，这也是之前说不能把 Redis 当主数据库的原因之一。

    Redis 事务的持久性问题也由此而来，AOF 的 everysec 与 no 策略都可能在提交后丢数据，导致事务持久性无法保证。

    三、缓存三兄弟

    1. 缓存穿透

    定义：请求的 key 既不存在于缓存，也不存在于数据库，请求直接打穿缓存落到数据库，数据库也查不到数据。常见于黑客伪造大量不存在的 key 发起攻击，把数据库压垮。

    解决方法：

    • 参数校验，不合理的请求直接拒绝
    • 缓存空对象，查不到也把空值写入缓存并设短过期时间，比如 1 分钟，防止反复穿透。缺点是攻击者不停换 key 会导致缓存塞满无效键，所以空值过期时间要短
    • 布隆过滤器，把所有可能存在的 key 提前放入位图，请求先过布隆过滤器，不存在直接返回。布隆过滤器用位数组加多个哈希函数，内存占用取决于元素量与目标误判率，百万级数据、1% 误判率下约需 1.2 MB，但存在误判与删除困难两个特性
    • 接口限流，配合黑名单机制限制异常 IP

    2. 缓存击穿

    定义：某个热点 key 的缓存过期瞬间，大量请求同时打向数据库。数据本身存在，只是缓存刚好失效。典型场景是秒杀商品的缓存过期。

    解决：

    • 热点数据提前预热，秒杀结束前不过期
    • 设置互斥锁，缓存失效后只让一个请求去查库回填，其他请求等待或返回旧值
    • 长过期时间或永不过期，不推荐，会牺牲数据新鲜度

    3. 缓存雪崩

    定义：缓存中大量或全部数据在同一时间失效，或缓存服务整体宕机，导致大量请求全落到数据库。相比击穿只针对单个热点 key，雪崩是大面积失效。

    解决：

    • 针对大量同时失效，给过期时间加随机值打散
    • 热点数据提前预热
    • 针对缓存服务宕机，用 Redis 集群避免单点，配多级缓存（本地缓存加 Redis）兜底

    三者易混，一句话区分：穿透是查一个不存在的 key，击穿是一个热点 key 缓存刚过期，雪崩是大量 key 同时失效或缓存挂了。它们共同的解题思路都是把流量从数据库挡回去。

    4. 缓存预热

    两种常见做法：定时任务轮询，如用调度框架定时把数据库热点数据刷进缓存；消息队列异步预热，消费方根据主键查询数据库再更新缓存。

    四、缓存与数据库数据一致性

    常用的读写策略是旁路缓存模式 Cache Aside：

    • 读：先查缓存，命中返回，未命中则查数据库并把结果回填缓存
    • 写：先更新数据库，再删除缓存中对应的数据

    为什么写操作是删缓存而不是更新缓存？更新缓存会引入并发写脏数据与一致性维护的复杂问题，删除缓存让下次读到再从数据库拉最新值，实现简单且正确性更好。

    删除缓存失败怎么办？两种常见处理的思路：

    • 缩短缓存 TTL 治标不治本，下次过期仍会从库重新加载
    • 引入重试机制，删除失败后把删除消息投递到消息队列，由消费者异步重试直到成功，这是常用且更可靠的方案

    更进一步的方案把删除动作交给数据库侧：延迟双删在更新库后先删一次缓存、稍等片刻再删一次，覆盖并发下的旧值回写窗口；或者订阅数据库 binlog（比如 canal）异步更新缓存，让缓存与数据库的变更同源，是目前比较成熟的思路。

    绝对的强一致通常意味着巨大的复杂度与性能代价，实践中一般在性能与一致性之间找平衡，选择能接受的最终一致即可。

    这里顺带补一个缓存系高频题，分布式锁的正确实现。加锁用 SET key value NX EX 原子操作，解锁用 Lua 比对 value 防止误删别人的锁，配合看门狗续期，Redisson 封装了这些逻辑；Redis 主从下锁也有失效窗口，所以才有 Redlock 这类多节点方案的争议。

    五、bigkey 与 hotkey

    1. 什么是 bigkey

    value 占用的内存较大的 key 就是 bigkey，参考标准是 String 类型的 value 超过 1MB，或复合类型包含的元素超过 5000 个。

    bigkey 的产生原因：把大文件直接存 String，集合类型未预估数据增长，以及垃圾数据未清理。

    bigkey 的危害：

    • 阻塞，单线程执行下操作大 key 耗时，客户端表现为长时间无响应
    • 网络带宽，每次取大 key 产生巨量流量，1MB 的 key 每秒访问 1000 次就是 1GB 流量，普通千兆网卡扛不住
    • 删除阻塞，DEL 一个包含海量元素的大 key 会堵塞工作线程

    发现手段：redis-cli –bigkeys 扫描（只能找到每个类型 top 1 的 key，线上加 -i 限速）；SCAN 遍历后配合 STRLEN、HLEN、LLEN 等命令，或 MEMORY USAGE 查看内存占用；分析 RDB 快照文件；公有云 Redis 的 key 分析服务。

    处理手段：把大 key 拆分成多个小 key；用 UNLINK 异步删除或 SCAN 加 DEL 分批删；选更合适的数据结构，比如不把文件二进制存 String、用 Bitmap 存状态、HyperLogLog 统计 UV；开启 lazy-free 让删除异步化。

    2. 什么是 hotkey

    访问量远高于其他 key 的 key 就是 hotkey，比如每秒 5000 次请求中某个 key 独占 2000 次。产生原因是热点事件、秒杀商品等数据访问量暴增。

    hotkey 的危害：占用大量 CPU 与带宽，影响其他请求；访问量超出处理能力会让 Redis 宕机，进而把流量压向数据库，可能拖垮数据库。

    发现手段：redis-cli –hotkeys，前提是淘汰策略设为 LFU；MONITOR 抓请求流量分析，但影响性能不能长期开；开源工具；依据业务预估；公有云分析服务。

    处理手段：读写分离，从节点分流读；Redis Cluster 把热点分散到多个节点；二级缓存，把 hotkey 放一份到应用本地内存，用如 Caffeine 的本地缓存扛住。

    六、慢查询与使用规范

    1. 慢查询命令

    Redis 大部分命令 O(1)，少数 O(n) 命令会成为慢查询元凶：KEYS、HGETALL、LRANGE、SMEMBERS、SINTER、SUNION、SDIFF 等。这些命令并非不能用，但要知道 n 的大小；有遍历需求用 HSCAN、SSCAN、ZSCAN 代替。

    Redis 提供慢查询日志，slowlog-log-slower-than 设置耗时阈值，slowlog-max-len 限制记录条数，SLOWLOG GET 查看、SLOWLOG LEN 统计、SLOWLOG RESET 清空。思路与 MySQL 的慢查询日志一致。

    2. 内存碎片

    Redis 内存分配与释放粒度不一致会产生内存碎片，通过 INFO memory 观察 mem_fragmentation_ratio，通常大于 1.5 视为碎片偏高，值偏大说明碎片严重，可开启 activedefrag 自动整理。

    3. 使用规范

    • 用连接池，避免频繁建连
    • 少用 O(n) 命令，用了要明确 n
    • 用批量操作减少网络往返，原生批量、pipeline、Lua 按场景选
    • 尽量不用 Redis 事务，用 Lua 代替
    • 禁止长时间开 MONITOR
    • 控制 key 的生命周期与数量，避免塞满不常访问的数据

    七、Redis 集群

    主从复制是集群的基础。全量同步在首次连接或复制偏移落后过大时触发，主库生成 RDB 快照发给从库，再补放期间的增量；正常运行时的增量同步按复制偏移持续拉取，代价很小。从库只读，异步接收主库写入，因此存在主从延迟窗口。

    1. Redis Sentinel

    Sentinel 哨兵负责监控与自动故障转移，解决主从架构的高可用问题。核心机制：

    • 监控所有节点，周期性探查状态
    • 主观下线，单个哨兵判定某节点不可达；客观下线，多个哨兵都认定后真正判定下线的机制
    • 故障转移，客观下线后从从节点中选举新的主节点并切换
    • 哨兵本身建议部署多个构成集群，避免单点；多哨兵通过类似 Raft 的机制选举领导哨兵来主导转移
    • 脑裂问题。Sentinel 本身不能完全防脑裂，需要配合 min-slaves-to-write、min-slaves-max-lag 等参数限制主节点在失去多数从节点时拒绝写入，降低脑裂丢数据风险

    2. Redis Cluster

    Cluster 解决数据分片与横向扩展，不用一致性哈希，而用哈希槽分区。槽数量固定 16384，写入时对 key 做 CRC16 计算后对 16384 取模，定位到槽，再由槽映射到节点。

    为什么是 16384 个槽？这个数目与节点心跳消息的大小、以及槽分配的元数据开销权衡有关，是官方经过评估的选择。Cluster 支持槽的重新分配，可以在扩容缩容时迁移数据，期间服务基本可用。节点之间通过 Gossip 协议交换状态，撒播元数据。

    MGET 等多 key 操作与 Lua 脚本在 Cluster 下都要求 key 落在同一槽，跨槽操作需要客户端如 RedisCluster 客户端分片处理。

    八、性能优化要点

    一个 Redis 命令的执行分四步，发送、排队、执行、返回，第一步和第四步是网络传输的往返时间。优化的大方向就是减少 RTT：

    • 原生批量命令，原子且服务端实现，如 MGET、MSET
    • pipeline，非原子但能打包任意命令，减少往返
    • Lua 脚本，原子且支持逻辑，还能解决命令间依赖

    三者对比如前所述，按需要原子性、命令类型是否固定、是否存在依赖关系来选。单次批量注意数量控制。Redis Cluster 下所有多 key 操作都要考虑哈希槽约束。

    小结

    本篇把 Redis 的生产面收齐。事务要讲清它和数据库事务的本质差异，以及 Lua 如何替代它。持久化记住 RDB 快照、AOF 追加与混合三者的取舍，fsync 三种策略和丢失窗口是高频追问点。缓存三兄弟务必能互相区分定义与解法，穿透靠布隆过滤器与空对象，击穿靠预热与互斥锁，雪崩靠随机过期与集群。一致性记住 Cache Aside 的删缓存策略与重试兜底。bigkey、hotkey 与慢查询是检验实战深度的题，能讲全发现手段与处理手段很加分。集群部分 Sentinel 保高可用，Cluster 做分片，16384 哈希槽与 CRC16 是必背答案。至此 Redis 两篇与前面的 Go、MySQL 系列，共同构成了计算机基础面试的知识主干。
