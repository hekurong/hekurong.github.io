    Redis 面试八股（一）：数据类型与底层结构

    来源：面试八股资料整理（redis八股-上.pdf、redis八股-下.pdf），结合 Redis 官方文档口径校正。 定位：Redis 面试八股共两篇。本篇覆盖 Redis 基础、数据类型与底层结构、线程模型、内存管理。下一篇进入持久化、缓存三兄弟、一致性、集群与治理。 收藏：本系列收录于 后端八股复习指南。

    一、Redis 基础

    1. 什么是 Redis

    Redis 是基于 C 语言开发的开源内存数据库，以键值对形式存储数据。数据常驻内存，读写速度极快，被广泛用于分布式缓存。与传统关系型数据库不同，内存读写本身在几十纳秒到亚微秒量级，而磁盘数据库在毫秒级，相差数个数量级；加上网络往返后，端到端通常以微秒计。

    Redis 有两层意思不可混淆：它被当成缓存用，但本身是完整的数据库；它很快，靠的是内存加精心设计的 I/O 模型，而不是什么魔法。官方推荐生产环境用 Linux 部署。

    2. Redis 为什么这么快

    • 纯内存操作，这是最主要的原因
    • 单线程事件循环配合 I/O 多路复用，一个线程同时处理大量连接上的读写事件，避免了多线程的上下文切换与锁竞争
    • 优化的内部数据结构，底层对不同的数据类型动态选择最合适的编码，如 listpack、quicklist、intset、skiplist、hashtable（Redis 7.0 起小对象编码由 ziplist 逐步迁移到 listpack）
    • 简洁的 RESP 通信协议，实现简单、解析快、二进制安全，序列化开销小

    既然这么快，为什么不直接当主数据库？主要是内存成本太高，而且 Redis 的持久化仍有数据丢失风险。

    3. 与其他分布式缓存对比

    Memcached 是 Redis 出现前主流的分布式缓存，两者的共同点是都基于内存、都有过期策略、性能都高。区别明显：

    • 数据类型，Redis 支持 String、List、Set、Hash、Zset 等丰富类型，Memcached 只有 K/V
    • 持久化，Redis 支持落盘重启恢复，Memcached 数据全在内存
    • 集群，Redis 3.0 起原生支持集群，Memcached 没有原生集群
    • 线程模型，Memcached 多线程非阻塞 IO，Redis 单线程 IO 多路复用，6.0 起网络读写引入多线程
    • 扩展能力，Redis 支持发布订阅、Lua 脚本、事务，Memcached 不支持
    • 过期删除，Memcached 只有惰性删除，Redis 同时用惰性与定期删除

    结论没有悬念，新项目基本直接选 Redis。如今业界比较认可的 Redis 替代品还有 Dragonfly 与 KeyDB，都是兼容 Redis 协议的内存数据库，但选型仍建议首选经过多年检验的 Redis。

    4. Redis 的应用场景

    除了缓存，Redis 还广泛用于：

    • 分布式锁，基于 Redisson，底层用 Lua 保证原子
    • 限流，Redis 加 Lua 脚本实现，Redisson 的 RRateLimiter 基于令牌桶
    • 消息队列，List 可做简易队列，Redis 5.0 的 Stream 更适合做消息队列，有消费组与 ACK 机制。但与专业消息队列相比，消息丢失和堆积问题不好解决，实际项目不建议用 Redis 做 MQ
    • 延时队列，Redisson 内置基于 Sorted Set 的实现
    • 分布式 Session，所有服务器共用一份会话数据
    • 复杂业务场景，Bitmap 统计活跃用户、Sorted Set 维护排行榜、HyperLogLog 统计 UV

    5. 为什么用 Redis 不用本地缓存

    本地缓存部署在一台服务器上，多服务器部署存在数据不一致问题，且受单机内存限制，宕机即丢。Redis 独立部署，内存空间更大，可持久化不易丢，集中管理且有丰富工具。同时缓存可以扛下远超数据库的并发量，MySQL 单机 QPS 大概 4k，Redis 单机可到 5 万甚至 10 万以上。

    二、数据类型总览

    Redis 的常用数据类型分两类：

    • 5 种基础类型，String 字符串、List 列表、Set 集合、Hash 散列、Zset 有序集合
    • 3 种特殊类型，Bitmap 位图、HyperLogLog 基数统计、Geospatial 地理位置

    另有布隆过滤器、位域等扩展。选型时按数据形态与操作模型决定，String 适合简单值与计数，Hash 适合对象字段，List 适合队列，Set 适合去重与集合运算，Zset 适合带权重的排序。

    三、String 与它的底层 SDS

    1. String 的应用

    String 是 Redis 中最常用也最简单的基础类型，二进制安全，可存字符串、整数、浮点数、序列化对象、图片路径等。典型场景：

    • 常规数据缓存，Session、Token、序列化对象
    • 计数，单位时间请求数、页面访问量，INCR 系列命令原子自增
    • 最简分布式锁，利用 SETNX 加锁

    2. String 底层为什么用 SDS

    Redis 基于 C 语言实现，但 String 的底层不是 C 语言以空字符结尾的字符数组，而是自研的简单动态字符串 SDS。

    SDS 的头部包含长度的字段，分多种类型按长度选择以节省内存。SDS 头部的 len 记录已用字节数，alloc 记录总容量，buf 存数据。对比 C 字符串，SDS 有四个优势：

    • 避免缓冲区溢出，修改字符串前按 len 检查空间，不够先扩容
    • O(1) 获取长度，C 字符串要遍历计数
    • 减少内存分配次数，采用空间预分配与惰性空间释放，连续多次增长不必每次重新分配
    • 二进制安全，C 字符串以空字符结尾，遇到包含空字符的二进制数据会截断，SDS 按 len 判断结束位置，可以安全保存图片、音视频等二进制内容

    3. String 还是 Hash 存对象

    • String 存序列化后的整个对象，操作简单，整体读写性能好，但修改部分字段要整体序列化
    • Hash 对对象字段单独存储，可以单独改一个字段、查部分字段，节省网络流量，小型 Hash 有压缩编码优化更省内存

    结论，对象简单且整体读写为主用 String，经常单独操作部分字段或想省内存用 Hash。购物车这类频繁增删改字段的场景适合用 Hash，以用户 ID 为 key，商品 ID 为 field，数量为 value；用户数据高频变动时也适合 Hash。

    四、List、Set、Hash 的应用

    1. List

    List 是有序可重复的列表，可用作简易消息队列，RPUSH 入队、LPOP 出队。主动轮询 LPOP 在队列为空时会产生大量无效请求，应改用阻塞式 BLPOP、BRPOP，队列空时挂起等待，带超时参数，超时为 0 则无限等待。

    玩家常用 List 做任务队列、消息分发。注意用 List 做 MQ 没有广播与确认机制，复杂需求交给 Stream 或专业消息队列。

    2. Set

    Set 是无序去重集合，元素唯一。应用场景：

    • 去重场景，文章点赞、动态点赞、UV 统计（数据量巨大时用 HyperLogLog 更省）
    • 集合运算，共同好友取交集、好友推荐取差集、订阅号推荐组合运算
    • 随机抽取，抽奖系统，SADD 入池、SPOP 随机移除取出（不重复中奖）、SRANDMEMBER 随机取出不删除（可重复中奖）

    3. Hash

    Hash 存储字段到值的映射，适合对象数据，前面讲购物车时已经覆盖。底层字段少用 listpack 紧凑编码（老版本为 ziplist），字段多再转 hashtable。

    五、Zset 与跳表选型

    1. Zset 的应用

    Zset 有序集合，每个元素绑一个分值，按分值排序。典型场景是排行榜，直播间送礼排行榜、微信步数榜、话题热度榜。常用命令 ZRANGE 从小到大、ZREVRANGE 从大到小、ZREVRANK 查看排名。

    2. Zset 的底层：跳表加哈希表双结构

    Zset 的底层不是单一结构，而是跳表加哈希表组合，这是最常见的追问点。跳表负责按分值排序和范围查询，哈希表负责按 member 快速定位分值，两者互补。

    哈希表（dict）做两件事：

    • ZSCORE 按 member 在 O(1) 时间内取分值
    • ZADD 时判断 member 是否已存在，避免在跳表里翻找
    • 键是 member，值是 score

    跳表（skiplist）做两件事：

    • 全部元素按分值升序串成有序结构，支撑 ZRANGE、ZREVRANGE、ZRANK 等范围与排名命令
    • 插入时先定位再插入，始终维持有序

    为什么非要双结构：跳表擅长按分值排序与范围查询，但要按 member 找元素是 O(log n)；dict 恰恰相反，O(1) 按 member 取值却无法有序遍历。一个管有序、一个管定位，缺一不可，ZADD 时两处同步更新。

    3. 跳表是怎么工作的

    跳表本质是多层有序链表。最底层链表包含全部元素且有序，上面的每一层都是对下一层的加速索引，节点以固定概率出现在更高层，Redis 里晋升概率为 1/4、最高 32 层。查询从最高层起步，向右跳过不需要的节点段，再向下落到更细的层，逐层逼近目标，期望复杂度 O(log n)。

    每个跳表节点的核心字段：

    • member 与 score，数据本身
    • backward，后退指针，指向前一个节点，支撑 ZREVRANGE 从队尾倒序输出
    • level 数组，每个 level 内有 forward 前进指针和 span 跨度

    span 跨度记录该层向后跨越的底层节点个数。排名命令 ZRANK 不用线性数元素，而是沿查询路径把各层 span 累加，所以 O(log n) 就能拿到排名，这是跳表能为排行榜秒出名次的关键。

    两个常被追问的细节：

    • 分数相同怎么办，按 member 的字节字典序排序，保证同分时顺序稳定
    • 跳表是概率平衡，插入删除不用像平衡树那样旋转、像红黑树那样变色，实现与维护都简单

    4. 元素少时的内存优化：listpack

    元素少、分值小的 Zset 不会一上来就用跳表，而是先用紧凑编码 listpack，Redis 7.0 起由 ziplist 迁移而来。listpack 把元素按分值顺序紧排在连续内存里，成员和分值成对存放，省去指针与层数开销，读取时线性扫描即可。升级为跳表的阈值由配置控制：zset-max-listpack-entries 默认 128 个元素，zset-max-listpack-value 默认 64 字节，任一超过就换跳表加哈希表。这个升级不可逆，元素再删回 128 以内也不会降级回 listpack。

    为什么弃用 ziplist：ziplist 每个节点开头记录前一个节点的长度，修改或插入某个节点可能让后续节点的长度头连锁变化，最坏退化成 O(n²)；listpack 让每个元素自带完整长度、正反都能遍历，把这个连锁更新问题整个消掉了。

    面试里可以用 OBJECT ENCODING key 直接查看一个 Zset 当前是 listpack 还是 skiplist，立见真章。

    5. 为什么 Zset 用跳表而不用平衡树、红黑树或 B+ 树

    • 与平衡树相比，插入删除都需要保证绝对平衡，失衡就要旋转，耗时；跳表用概率平衡，插入删除算法简单得多、更快
    • 与红黑树相比，实现更简单，不需要旋转变色，且区间查找效率高于红黑树
    • 与 B+ 树相比，B+ 树的核心是用少的磁盘 IO 定位大量索引，适合数据量大、存在磁盘的场景；Redis 是内存数据库，数据量受内存限制，不需要这种维护成本高的索引，跳表插入时随机维护高度即可，无需节点分裂合并

    一句话：内存场景追求简单高效，跳表以概率换取实现简洁，适合区间查询。

    六、特殊数据类型

    1. Bitmap

    Bitmap 是存储二进制 0 和 1 的数组，每个位只占一个 bit，极省内存。用日期做 key，用户 ID 做偏移量，活跃置 1，即可统计日活；跨天统计用 BITOP 做与或运算再 BITCOUNT。

    2. HyperLogLog

    HyperLogLog 用于基数统计，即统计不重复元素个数。PFADD 添加元素，PFCOUNT 求基数。用它统计页面 UV，内存占用极小且有可容忍的误差率，适合海量数据下的近似去重计数。注意它是概率性结构，不精确存储每个元素。

    3. Geospatial

    Geospatial 地理位置类型，Redis 3.2 加入，支持经纬度存入、计算距离、查询附近的人，底层是 Zset 的编码。

    七、线程模型

    1. 单线程模型

    这里要澄清一个容易混淆的说法：常说的单线程，指的是命令执行是单线程顺序执行。Redis 基于 Reactor 模式实现了文件事件处理器，包含四个部分，多个 socket、IO 多路复用程序、文件事件分派器、事件处理器。IO 多路复用程序监听大量连接上的读写事件，分派器把事件交给对应处理器，整套在单线程内运转，既高性能又保持内部模型简单。

    单线程为什么能处理大量连接？靠 IO 多路复用，把感兴趣的事件注册到内核，无需为每个连接建线程，和 NIO 里的 Selector 类似。

    2. 为什么 Redis 6.0 之前不用多线程

    • 单线程编写容易、维护简单
    • 性能瓶颈不在 CPU，而在内存与网络
    • 多线程带来死锁、上下文切换等问题

    3. 多线程的演进

    • Redis 4.0 引入多线程处理异步删除，新增 UNLINK、FLUSHALL ASYNC、FLUSHDB ASYNC，释放大对象不阻塞主线程
    • Redis 6.0 引入多线程处理网络数据的读写，这是网络方向的瓶颈；命令执行仍是单线程顺序执行，所以无线程安全问题。默认关闭，需在配置里设置 io-threads 大于 1 才生效
    • Redis 8.0（2025 年发布）起默认启用 4 个 IO 线程，多数场景无需再手动配置，命令执行依旧单线程
    • 后台线程常驻执行耗时操作，比如关闭文件、AOF 的 fsync 刷盘、lazy free 释放大对象内存

    八、内存管理

    1. 过期时间与过期字典

    给缓存设置过期时间，避免内存无上限增长导致 OOM。String 之外的类型靠 EXPIRE 设过期，String 有 SETEX 快捷命令，PERSIST 可移除过期时间。

    Redis 用一个独立的过期字典保存键的过期时间，键指向数据库中的 key，值是毫秒精度的时间戳。查询时先查该 key 是否在过期字典里，在的话判断是否过期，过期即删并返回空。

    2. 过期删除策略

    • 惰性删除，只在取 key 时检查过期。对 CPU 友好，但过期的 key 可能长时间残留
    • 定期删除，周期随机抽查一批带过期时间的 key 逐个检查删除。对内存友好，CPU 有开销
    • 定时删除，每个 key 到点立即删，CPU 压力最大
    • 延迟队列，到期再删，队列本身开销与维护成本高

    Redis 采用定期加惰性的组合。定期删除随机的抽查数量默认 20 个，执行频率由 hz 控制默认每秒 10 次，单次执行时间超过阈值中断，过期比例过高则加大清理力度。这样既保证内存不会被垃圾撑爆，又不至于频繁扫描占用 CPU。

    为什么不把所有过期 key 立即删掉？一是成本太高，挨个遍历庞大 key 空间很耗时；二是延迟队列或定时器维护复杂，内存收益不划算。

    3. 大量 key 集中过期怎么办

    大量 key 同一时刻过期会让 CPU 升高，且过期后未清理时仍占内存。处理手段是设置随机的过期时间打散，以及开启 lazy-free 让过期删除异步化，不阻塞主线程。

    4. 内存淘汰策略

    内存达到 maxmemory 上限后触发淘汰。64 位系统默认不限制，32 位默认 3GB。Redis 提供 8 种策略：

    • volatile-lru，从已设置过期时间的数据中淘汰最近最少使用
    • volatile-lfu，从有过期时间的数据中淘汰最不经常使用
    • volatile-random，从有过期时间的数据中随机淘汰
    • volatile-ttl，从有过期时间的数据中淘汰将要过期的
    • allkeys-lru，从全部 key 中淘汰最近最少使用
    • allkeys-lfu，从全部 key 中淘汰最不经常使用
    • allkeys-random，从全部 key 中随机淘汰
    • no-eviction，默认策略，禁止驱逐，内存不足时新写入报错

    volatile 开头的只碰设置了过期时间的 key，allkeys 开头的对全部 key 下手。面试常问的变体是 MySQL 有 2000 万数据、Redis 只能存 20 万，怎么保证缓存里全是热点，答案是把淘汰策略设为 allkeys-lfu，靠访问频率把热点留在内存。

    小结

    本篇把 Redis 的基础打完。先记住为什么快，四个要点里单线程事件循环加 IO 多路复用是理解一切后续问题的钥匙。数据类型部分，String 的 SDS 底层和 Zset 的跳表加哈希双结构、listpack 编码是高频深挖点，要能讲清各自相对 C 字符串和平衡树的取舍。线程模型要分辨命令执行单线程与网络 IO 多线程（6.0）的区别。内存管理记住定期加惰性的删除组合，以及 volatile 与 allkeys 两族淘汰策略。下一篇进入生产侧，持久化、缓存三兄弟、数据一致性和集群是真正决定面试成败的部分。
