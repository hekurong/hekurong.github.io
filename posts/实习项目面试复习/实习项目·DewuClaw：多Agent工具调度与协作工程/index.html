    实习项目·DewuClaw：多 Agent 工具调度与协作工程

    2026-08-21 AI 面试复习·实习与项目 | in 计算机基础

    实习项目·DewuClaw：多 Agent 工具调度与协作工程

    定位：面试复习·实习与项目系列第二篇。这个项目是 AI 应用方向面试的问答富矿，把「多 Agent 并行怎么防数据竞争、工具太多怎么让 Agent 找得准、隔离怎么做才轻量」三大追问点讲透。 收藏：本系列收录于 后端八股复习指南。

    一、项目背景

    项目是一款多 Agent 协作框架，多个 Agent 并行处理一条长链路任务，各自调用工具读写文件、执行操作。规模上来后暴露出两个真实的工程痛点：

    • 数据竞争与状态污染。多个 Agent 并行读写同一个文件路径，后写覆盖先写，协作链路的数据一致性被破坏
    • 工具定位困难。长链路任务里注册的工具数量庞大，Agent 选工具时要把全部工具描述过一遍才能找到可用的那个，又慢又容易选错

    两个问题分别对应隔离与调度，是面试官顺着项目必问的两条主线。

    二、多 Agent 的并发问题：为什么共享文件路径会出事

    多 Agent 共享同一套文件系统时，输出文件、临时目录、缓存路径极易撞车。两个 Agent 并行写同一个文件，A 写完 B 又写，A 的结果被覆盖，后读数据的 Agent 拿到的是 B 的内容，产生状态污染。即便同一 Agent 内部，多路并发操作同一个路径也有同样问题。

    根治思路无非两条：

    • 硬隔离。上容器级沙箱，每个 Agent 一套独立文件系统。干净彻底，但重：镜像、资源隔离、通信开销都上来，多 Agent 轻量协作场景不划算
    • 软隔离。不引入容器，在框架层给每个 Agent 分配独立的逻辑工作目录，把文件读写操作统一重定向

    项目选择软隔离，追求「轻量够用」。

    三、软隔离工作区：映射表与读写重定向

    软隔离的核心设计：为每个 Agent 分配一个独立工作目录作为边界，由上下文管理器维护一张「Agent 到工作目录」的映射表，在框架层统一拦截并重定向该 Agent 的全部文件读写操作。

    type WorkspaceManager struct {
    mu     sync.RWMutex
    table  map[string]string // agentID -> workdir
}

func (m *WorkspaceManager) Assign(agentID string) string {
    m.mu.Lock()
    defer m.mu.Unlock()
    dir := fmt.Sprintf(「workdir/%s」, agentID)
    m.table[agentID] = dir
    return dir
}

// 拦截文件操作：把参数里的路径重定向到 agent 自己的工作目录
func (m *WorkspaceManager) Resolve(agentID, path string) string {
    m.mu.RLock()
    defer m.mu.RUnlock()
    base, ok := m.table[agentID]
    if !ok {
        return path // 未登记，原样返回
    }
    return filepath.Join(base, path)
}

    设计要点三条：

    • 拦截点要统一。文件读写经过的公共入口全部走 Resolve 重定向，保证没有漏网之鱼直接摸到真实路径
    • 映射表本身要并发安全。映射表被所有 Agent 共享读写，用读写锁保护，读多写少时 RWMutex 是合适选择
    • 未登记的原样放行。内部系统文件不必重定向，避免过度隔离影响正常执行

    软隔离的收益：不引入容器级沙箱，只在框架层做路径重定向，消除数据竞争，协作链路数据一致，代价是框架层一次统一的路径拦截。面试时这一段的记忆点是「映射表加重定向」，把三要素（独立目录、映射表维护、统一拦截）讲清楚即可。

    四、工具调度：为什么工具多了 Agent 就变笨

    多工具场景的经典问题：工具描述是长文本，Agent 每一步都要从全部工具描述里找到能用的那个。工具少时遍历一遍可行，工具量上百时，遍历描述的 Token 成本高，且无关工具的描述混入上下文会干扰模型判断，选错工具。

    问题的本质是信息过载：Agent 的注意力被无关工具稀释了。解法的方向是先收窄候选，再精确匹配。

    五、Skill Hub：元数据注册与语义匹配

    项目把工具调度拆成注册中心加匹配器两层。

    1. Skill Hub 独立服务

    工具不是写死在 Agent 里的，而是向 Skill Hub 注册元数据。Hub 托管全部工具的注册信息：名称、功能描述、参数 Schema、依赖环境。Agent 执行时不再遍历全部工具描述，而是先向 Hub 拉取元数据做语义匹配，收窄候选范围。

    2. 两段式下发

    • 第一段，粗筛。把当前任务意图与工具元数据做语义匹配，只召回候选范围，候选往往只有全量的一个零头
    • 第二段，精排。对召回候选按语义相似度排序，把排序靠前的完整 Schema 描述下发给 Agent，执行时动态加载对应实现

    这样 Agent 每步只需处理少量相关工具的完整描述，无关工具根本不进上下文。工具命中率与上下文干净度同时改善。

    3. 在线反馈修正排序权重

    静态语义匹配有个盲点：语义相似不等于实际可用。两个工具描述都很像，但只有一个是当前环境能跑的。项目引入历史调用反馈：每次工具调用结果的成败写回 Hub，按工具的准确率与历史命中情况对排序权重做在线修正。高频好用的工具权重上浮，常失败的降权，排序逐渐贴近真实可用性。

    这部分面试可以讲到很细：语义匹配定冷启动，反馈修正做热收敛，两者结合让排序权重持续进化。

    六、命中率提升的验证

    上线前后按抽样对比，长链路任务的工具命中率提升约 20%。面试答这个数字时要说清口径：同一条评估集、同样的任务分布，对比优化前后的命中占比，而不是凭感觉说「好用多了」。能讲清评估口径，比数字本身更能体现工程素养。

    七、面试追问与答题要点

    • Q：软隔离和硬沙箱怎么选？ 答：看隔离强度需求。多 Agent 轻量协作、只防路径冲突时软隔离够用且代价小；涉及不可信代码执行、需要强环境隔离时硬沙箱。项目选软隔离是因为场景只需防数据竞争，不想背容器开销。
    • Q：路径拦截会不会漏？ 答：会，这是软隔离的天花板。所以拦截点要收敛到文件读写的统一入口，并给未登记路径留原样放行的兜底。真正要求强隔离时回到硬沙箱方案。
    • Q：语义匹配用什么做 Embedding 还是关键词？ 答：职责匹配用向量语义更稳，冷启动阶段可以语义与关键词双路召回再合并，避免单一信号偏差。
    • Q：反馈修正会不会收敛到错误方向？ 答：可能，所以要给权重设上下限与衰减，避免单次异常调用把某个工具权重拉爆或打沉，长期统计才有说服力。
    • Q：如果工具间有隐藏依赖怎么调度？ 答：和第一个项目异曲同工，工具也能建模成 DAG，按依赖排序执行，先完成前置工具再启用后续工具。

    小结

    这个项目讲的其实是多 Agent 工程的两块基石。隔离解决「能不能并行」，用软隔离工作区加映射表重定向，轻量消除数据竞争。调度解决「并行时能不能做对」，用 Skill Hub 注册元数据，语义匹配粗筛加精排两段式下发，再以在线反馈修正排序权重，命中率提升约 20%。两条线都从真实痛点出发，讲到方案设计与验证口径，是 AI 应用岗面试里的高区分度素材。
