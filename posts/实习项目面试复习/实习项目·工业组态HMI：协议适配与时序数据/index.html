    实习项目·工业组态 HMI：协议适配与时序数据

    定位：面试复习·实习与项目系列第三篇。这个项目的价值在于它同时覆盖两块独立的面试面：设计模式里的适配器思想，以及时序数据处理的完整链路。后端岗问到「接入异构协议怎么做、时序数据怎么存、查询慢怎么治」都能从这里取材。 收藏：本系列收录于 后端八股复习指南。

    一、项目背景

    工业组态 HMI 平台对接工业现场的各类设备，设备通过 Modbus TCP 与 OPC UA 等工业协议上报运行数据，平台负责把这些数据解析、存储并呈现给上层 Web 服务。做工业对接最要命的现实是协议碎片化：Modbus 与 OPC UA 的接口规范、报文格式互不兼容，一个设备一个脾气，硬编码对接到第三个设备类型时就要推翻重写。

    项目目标一条：让上层业务与具体协议解耦，新增设备类型只做增量适配，不碰既有代码。

    二、为什么协议适配能解耦

    Modbus TCP 与 OPC UA 是两种完全不同的工业通信协议。Modbus 报文紧凑、按寄存器地址读写，主要面向 PLC 与单片机这类资源受限设备；OPC UA 面向对象、自带信息模型与安全机制，多用于现代工厂的 MES、SCADA 系统。两者数据模型不同、报文结构不同、地址语义不同，上层 HMI 如果直接依赖某一种协议，换协议就得改上层。

    适配器模式正是为此而生：定义一个统一的数据接口，让不同协议各自实现适配器，把各自的报文解析成统一格式，上层只认这个统一接口。协议差异被挡在适配层内。

    三、数据结构设计与存储选型

    项目里有两类数据，性质完全不同，存储选型也不一样：

    • 配置与权限数据。工程配置、用户权限这类低频小数据，结构化程度高，用 SQLite3 存储，单机嵌入式数据库开箱即用
    • 实时变量数据。设备连续上报的运行值，高频写入、带时间戳、只增不改，是典型的时序数据，用 InfluxDB 存储

    为什么实时变量不丢进 SQLite：时序数据量巨大且高频追加，关系型数据库的行存储和索引维护扛不住这种写入模式，数据膨胀后查询也越来越慢。时序数据库按时间组织数据，专为高频写入与时间范围查询优化，是这一场景的正解。

    四、时序数据的高频写入与预降采样

    1. 直接查原始时序数据的代价

    设备高频上报，原始时序表的数据量增长速度极快。前端趋势图要按时间范围展示曲线，直接查原始数据表时，时间跨度一大就要扫描海量原始点，查询延迟高，用户体感就是「图卡住了」。

    2. 预降采样：用空间换时间

    项目的方案是预降采样：把原始高频数据按分钟聚合后落盘到聚合表，前端趋势图查聚合表而不是原始表。原始数据仍在，需要精细查看时再查明细；日常看趋势都走聚合，查询量级从千万级降到万级。

SELECT timestamp, value FROM raw_points
WHERE device_id = 'dev-01'
  AND timestamp >= '2026-08-21 00:00:00'
  AND timestamp <  '2026-08-21 23:59:59';

    十倍百倍的点数，直接聚合查询很慢。改成分钟粒度的聚合表：

    1
2
3
4
    # InfluxDB 聚合语句：按设备+分钟聚合
SELECT mean(value) FROM raw_points
WHERE time >= now() - 1h
GROUP BY time(1m), device_id

    聚合结果写入聚合表，趋势图只读聚合表，响应时间从秒级降到毫秒级，达到可交互级别。

    面试的加分点是能把这个策略的取舍讲清：降采样牺牲了时间分辨率换查询性能，所以原始表必须保留给需要精细分析的场景，聚合表只服务「看趋势」这类高频低精度需求，两个表并存、按需路由。

    五、时序数据库的追加知识点

    面试常顺着追问时序数据库本身，几个高频点要能答：

    • 为什么时序数据库写入快。按时间序列组织写入，写入基本是顺序追加，不需要像关系型那样维护随机索引，写入吞吐高
    • 数据模型。核心是 measurement（表）、tag（标签）、field（字段）、time（时间戳）。tag 参与索引、用于分组过滤，field 是值本身
    • 数据保留策略。时序数据可按保留策略自动过期清理，旧数据定期清除，避免无限膨胀
    • 降采样是时序库的标配编排。不仅本项目的分钟聚合，跨天、跨周维度的聚合也是同类思路，按不同粒度逐层聚合，查询按需选择层

    六、面试追问与答题要点

    • Q：适配器模式和策略模式的区别？ 答：适配器解决「接口不兼容」的转换适配，策略模式解决「同接口不同算法」的选择替换。本项目的 Modbus 与 OPC UA 是两种协议接口不兼容，用适配器把它们统一到同一个接口，符合适配器的语义。
    • Q：为什么配置数据不也放时序库？ 答：配置数据低频、结构化、有主键、需要事务，是关系型的工作；时序数据高频、追加、时间导向，是时序库的强项。存储选型跟随数据性质，混放反而两头受制。
    • Q：降采样会不会丢数据？ 答：聚合表本身会损失低于聚合粒度的细节，但原始表保留，查询路由按需选择。丢失的是「聚合粒度以下的展示精度」，不是数据的物理删除，明细仍可回溯。
    • Q：设备数据乱序或迟到怎么办？ 答：时序场景要点是时间戳由设备携带而非接收时间，按设备时间组织；结合缓冲与乱序修正处理迟到数据，避免按接收时间写入把时序秩序打乱。

    小结

    这个项目的两条主线正好是两类常考面。设计模式面：用适配器把互不兼容的工业协议统一到同一接口，新增设备只加适配器、不动上层，说明白了耦合与扩展的关系。数据面：配置与实时变量分离存储，实时变量进时序数据库，高频写入用预降采样以空间换时间，聚合表服务趋势查询，原始表保留明细。整条链路从协议接入到存储选型再到查询优化，是结构化完整的工程叙事，后端与物联网方向都能用。
