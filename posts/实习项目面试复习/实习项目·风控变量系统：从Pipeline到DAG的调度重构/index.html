    实习项目·风控变量系统：从 Pipeline 到 DAG 的调度重构

    2026-08-21 AI 面试复习·实习与项目 | in 计算机基础
    面试 复习 实习项目 Golang DAG 调度 并发

    实习项目·风控变量系统：从 Pipeline 到 DAG 的调度重构

    定位：面试复习·实习与项目系列第一篇。这个项目是 Go 后端岗面试最常被追问的来源，把「为什么重构、DAG 怎么调度、并行怎么实现、性能怎么验证」讲透，面试官顺着它深挖并发与系统设计时能接得住。 收藏：本系列收录于 后端八股复习指南。

    一、项目背景

    风控引擎负责在借贷决策前计算大量风控变量，这些变量的值直接决定预审、戳额等关键接口的放款与额度判断。旧引擎以 Pipeline 链式方式执行变量计算，几千个变量的依赖关系散落在业务代码里，存在两个致命问题：

    • 算得慢。链式串行执行，即使两个变量毫无依赖，也必须排队算完前一个才算后一个，整个链路延迟高
    • 改不动。变量之间存在隐式耦合，旧引擎根本表达不出「这个变量依赖那个变量」，修一个变量要逐条排查上下游，一次迭代耗时半天以上

    重构的目标是把计算链路从「串行管道」变成「有依赖关系的图」，让无依赖的变量并行计算，同时把依赖显式化，让修改变量变成改配置。

    二、为什么用 DAG 而不是 Pipeline

    Pipeline 是线性数据流，前一个处理的输出是后一个的输入，天然表达不了分支与并行。风控变量之间是典型的引用关系，一个基础变量被上层多个决策变量依赖，关系形态是有向无环图（DAG）。

    选 DAG 的核心理由三条：

    • 表达依赖。变量间的「谁依赖谁」用图的边显式表达，节点是变量计算，边是依赖关系
    • 暴露并行度。同一轮次内互不依赖的节点天然可以并行，这是 Pipeline 给不了的
    • 天然有序。DAG 保证节点可以拓扑排序，只要按拓扑序执行，任何节点的依赖一定先于它完成

    一句话：Pipeline 把并发能力阉割掉了，DAG 把本应存在的并行度还了回来。

    三、拓扑排序：执行顺序的基石

    DAG 调度器的核心是拓扑排序，两种经典算法都要掌握。

    1. Kahn 算法（BFS 式）

    基于入度：不断取入度为 0 的节点加入队列，输出后把它的出边邻居入度减一，重复直到所有节点处理完。环检测的副产品：如果最后输出的节点数小于总节点数，说明图里有环。

    func topoSort(n int, edges [][]int) []int {
    indeg := make([]int, n)
    graph := make([][]int, n)
    for _, e := range edges {
        graph[e[0]] = append(graph[e[0]], e[1])
        indeg[e[1]]++
    }
    q := make([]int, 0)
    for i := 0; i < n; i++ {
        if indeg[i] == 0 {
            q = append(q, i)
        }
    }
    res := make([]int, 0, n)
    for len(q) > 0 {
        u := q[0]
        q = q[1:]
        res = append(res, u)
        for _, v := range graph[u] {
            indeg[v]--
            if indeg[v] == 0 {
                q = append(q, v)
            }
        }
    }
    return res
}

    2. DFS 式

    对图做深度优先遍历，记录节点的状态（未访问、访问中、已访问），访问中的节点再次遇到说明有环。DFS 完成顺序的逆序就是一组拓扑序。

    3. 工程上怎么用

    工程版本通常按「轮次」组织：把入度为 0 的节点编号为第 0 轮，它们处理完释放依赖后产生第 1 轮，以此类推。每一轮内部的节点互不依赖，天然可并行，这就是调度的最小并行单位。项目里先把变量依赖写成配置文件，加载后构建图，再做轮次分组，无依赖组送进 goroutine 池并发执行。

    四、并行调度与 goroutine 池

    1. 为什么一轮一个 goroutine 不够

    如果每一轮直接用 goroutine 开跑，层数深时 goroutine 数量会爆炸，且频繁创建销毁有开销。工程实践用 goroutine 池：预建固定数量的 worker，任务从 channel 分发，worker 消费任务。池化控制了并发度上限，避免资源耗尽。

    type WorkerPool struct {
    jobs    chan Job
    results chan Result
    wg      sync.WaitGroup
}

func (p *WorkerPool) Run(workers int) {
    for i := 0; i < workers; i++ {
        p.wg.Add(1)
        go func() {
            defer p.wg.Done()
            for job := range p.jobs {
                p.results <- job.Execute()
            }
        }()
    }
    close(p.jobs)
    p.wg.Wait()
    close(p.results)
}

    2. 并发安全的三个坑

    并行计算绕不开共享数据，三个高频坑面试官必问：

    • 竞态条件。多个 worker 同时读写下级变量结果，必须用锁或改为「先算好后一次性写入」。工程上让每个变量算完独立落位，其他变量读的是已完成的版本，尽量避免共享可写状态
    • channel 误用。关闭 channel 后再发送会 panic，发送方与接收方职责要分清，通常由主协程 close，worker 只做消费
    • WaitGroup 计数。Add 必须在 go 启动前调用，Done 在协程结束时调用，顺序错了会死锁或提前返回

    3. 结果收集与错误处理

    并行场景的错误处理要特别设计：某个变量计算失败，不能静默吞掉，也不能 panic 拖垮整批。惯用做法是任务返回 error，主协程收集所有结果后统一判断，失败变量进入重试或失败名单。别在 worker 里直接处理业务错误，把错误带出来交给调度层决策。

    五、依赖显式化：从代码到配置

    旧引擎的依赖散落在代码里是最大的维护痛点。重构把依赖关系抽出来写成配置文件，每个变量声明自己的依赖列表，运行时由调度器解析构建 DAG。

    这样带来的直接收益是可维护性质变：新增变量只需在配置里登记节点与依赖，不再改动调度代码；修改变量只需改配置，上下游影响被 DAG 自动梳理清楚。项目迁移时按「从底层基础变量到上层决策变量」的顺序逐层上线，每层用回归测试核对计算结果与旧引擎一致后再切入生产流量，保证迁移不破坏线上行为。

    六、性能验证与收益

    重构的收益要拿数据说话。优化前特征计算是秒级，优化后降到毫秒级，关键预审、戳额接口的 P99 延迟降低约 70%。验证方式是在线监控对照旧引擎数据，确保对比口径一致。面试时这个数字要敢说、能讲清口径来源，比笼统说「变快了」有说服力得多。

    七、面试追问与答题要点

    面试官通常顺着这个项目往深挖，常见追问：

    • Q：拓扑排序有环怎么办？ 答：构建图时做环检测，发现环给出环路径并拒绝加载。风控变量设计上不允许循环依赖，报错即暴露配置错误。
    • Q：并发度设多少？ 答：取决于机器核数与单变量计算开销，一般取核心数的 1 到 2 倍，太小吃不满 CPU，太大线程切换与锁竞争反而拖慢。
    • Q：某个变量算挂了怎么处理？ 答：错误带出 worker，调度层收集后对失败变量做有限次重试，仍失败进入失败名单上报，不影响已成功的变量结果返回。
    • Q：Pipeline 到 DAG 的本质变化是什么？ 答：从「默认串行、靠人脑并行」变成「默认表达依赖、机器自动并行」，把数据流模型从线性升级为图，释放了本应存在的并行度，也让依赖关系可管理、可审计。

    小结

    这个项目的完整故事线：旧引擎 Pipeline 串行且依赖隐藏在代码里，重构为 DAG 调度，拓扑排序定执行顺序，轮次划分暴露并行度，goroutine 池并行执行，依赖外置成配置，逐层灰度迁移，最终 P99 降约 70%。面试答这条线时按「为什么重构、DAG 怎么表达依赖、并行怎么实现、并发安全怎么保证、收益怎么验证」五段讲，既完整又显工程功底。
