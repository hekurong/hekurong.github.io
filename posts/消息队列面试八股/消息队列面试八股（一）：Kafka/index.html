    消息队列面试八股（一）：Kafka

    2026-08-19 AI 消息队列面试八股 | in 计算机基础
    消息队列 面试 八股 Kafka 消息可靠性

    消息队列面试八股（一）：Kafka

    来源：面试八股资料整理（kafka八股.pdf），结合 Kafka 官方文档口径校正。 定位：消息队列面试八股第一篇，Kafka 专项。覆盖消息模型、核心概念、副本机制、顺序保证、消息不丢失与重复消费、重试机制。下一篇是 RabbitMQ 专项。 收藏：本系列收录于 后端八股复习指南。

    一、Kafka 基础

    1. Kafka 是什么

    Kafka 是分布式流式处理平台，兼具三个能力：发布订阅消息流，也就是消息队列功能；容错的持久化存储，消息落盘避免丢失；流式处理，提供完整的流处理类库。

    两大应用场景：一是建实时流数据管道，在系统与应用程序之间可靠搬运数据；二是构建实时流处理程序，对数据流做转换与处理。

    2. 相比其他消息队列的优势

    • 极致的性能。设计与实现大量运用批量处理与异步思想，配合顺序写磁盘、页缓存与 sendfile 零拷贝，单机可以支撑百万量级的消息吞吐
    • 生态兼容性最好。在大数据与流计算领域，与周边系统的集成都以 Kafka 为事实标准

    早期 Kafka 从 LinkedIn 的日志处理系统演变而来，消息可靠性并不出色，但这些短板已被逐步补齐，如今把 Kafka 当作不可靠的 MQ 已是过时说法。

    二、消息模型

    1. 队列模型

    队列模型用队列作为载体，满足生产者消费者模式，一条消息只能被一个消费者消费，未被消费的消息在队列里保留直到被消费或超时。生产者发 100 条消息，两个消费者大致一人一半。

    队列模型的局限：无法把一条消息完整地分发给多个消费者。有人提议为每个消费者建独立队列、生产者发多份，这浪费资源且违背使用 MQ 的初衷。

    2. 发布订阅模型

    发布订阅模型用主题作为载体，类似广播。发布者发一条消息，通过主题传给所有订阅者，订阅动作发生在广播之前的用户收不到该消息。只有一个订阅者时，发布订阅与队列模型基本等价，所以发布订阅在功能上可以兼容队列模型。

    Kafka 采用发布订阅模型。RocketMQ 的消息模型与 Kafka 基本一致，唯一区别是 RocketMQ 里有队列概念，Kafka 没有，与之对应的是分区 Partition。

    三、核心概念

    • Producer 生产者，产生消息的一方
    • Consumer 消费者，消费消息的一方
    • Broker 代理，一个独立的 Kafka 服务实例，多个 Broker 组成集群
    • Topic 主题，生产者发消息到特定主题，消费者订阅主题消费
    • Partition 分区，主题的一部分，一个主题可有多个分区，同一主题的分区可以分布在不同的 Broker 上，主题因此可以横跨多个 Broker

    划重点：Kafka 的 Partition 实际就相当于消息队列里的队列，消息按顺序追加进分区，这也是理解 Kafka 可靠性与顺序性的基础。

    还要理解消费者组，这是消费模型的关键。同一个组内，一个分区同一时刻只能被组内一个消费者消费，组内消费者分摊各分区；消费者数多于分区数时多出的消费者空转，少于分区数时一个消费者可消费多个分区。消费者加入或退出会触发分区再平衡，消费进度以偏移量形式记录并提交。

    除了上面这些，还有两个概念贯穿一致性问题：

    • Replica 副本，分区下的多副本冗余，保证消息存储安全
    • Offset 偏移量，消息在分区内的位置标识，Kafka 靠它保证分区内顺序并记录消费进度

    四、多副本机制

    Kafka 为分区引入多副本。副本分两类：leader 负责对外服务，生产者与消费者只和 leader 交互；follower 从 leader 拉取消息同步，只是 leader 的拷贝，用于保障存储安全。

    leader 故障时从追随者中选举新 leader，其中与 leader 同步程度达不到要求的副本没有竞选资格，这就是 ISR 同步副本集合的概念基础。

    多分区多副本的价值：分区分散在不同 Broker 上，生产者消费负担可以均衡，提升并发；副本数可配，提升容灾能力，代价是占用更多存储。

    五、ZooKeeper 与 KRaft

    Kafka 2.8 之前重度依赖 ZooKeeper。ZooKeeper 为 Kafka 提供元数据管理：

    • Broker 注册，Broker 启动时在 ZooKeeper 的 /brokers/ids 下创建自己的节点，记录 IP 与端口
    • Topic 注册，主题的分区信息与 Broker 的对应关系由 ZooKeeper 维护
    • 负载均衡，根据分区与消费者数量动态调整

    Kafka 2.8 起引入基于 Raft 协议的 KRaft 模式，不再依赖 ZooKeeper，架构显著简化。KRaft 在 3.3.1 版本被标记为生产就绪，想要使用建议选较新的版本。

    Kafka 4.0 起已彻底移除依赖 ZooKeeper 的旧模式，KRaft 成为唯一路径。

    六、如何保证消费顺序

    Kafka 只能保证分区内的消息有序。消息追加到分区时分配递增偏移量，消费按偏移量顺序读取。

    保证全局消费顺序的两种思路：

    • 一个主题只用一个分区，最简单但牺牲了 Kafka 的多分区并行设计
    • 推荐做法，发送消息时指定 Partition 或指定 key，相同 key 的消息会进同一个分区。实践中用业务 ID 当 key，就能保证同一实体的消息严格有序

    七、如何保证消息不丢失

    消息在三个环节可能丢失，分别对症下药。

    1. 生产者发丢

    send 是异步操作，不能默认发送成功。两种方式确认结果：调用 get 拿到结果，这会退化成同步，一般不推荐；更推荐给 send 挂回调，失败时记录日志并重发。

    同时把生产者的 retries 设为合理值，一般 3 以上，网络波动时自动重试。重试间隔也不能太小，否则间隔无意义，几次就在波动瞬间重试完了。

    2. 消费者处丢

    消费者拉取消息后默认自动提交偏移量，若刚拉取还没来得及处理就宕机，消息实际没消费但偏移量已经提交，消息就丢了。

    解决办法是关闭自动提交，处理完消息后再手动提交偏移量。但这会引入新的权衡：处理完再提交虽然不丢，却可能因宕机发生在提交前而重复消费；拉取即提交不重复但可能丢。需要按消息允许延时的程度取舍。

    3. Broker 侧丢

    leader 宕机时，若数据还没有全部同步到 follower，选举出的新 leader 就没有这部分数据，消息丢失。四个配置协同：

    • acks = all，默认是 1，只要 leader 接收就算成功，设为 all 后只有 ISR 里所有副本都写入才返回成功，最安全但延迟高。注意 Kafka 3.0 起开启幂等生产者后，生产者会以 all 语义工作，acks 一般无需再手动调整
    • replication.factor >= 3，每个分区至少三个副本，形成冗余
    • min.insync.replicas > 1，消息至少写入两个副本才算成功，默认值 1 要改掉
    • unclean.leader.election.enable = false，禁止不同步程度不足的副本参与 leader 竞选，从 0.11.0.0 起默认已是 false

    注意高可用约束，要保证 replication.factor 大于 min.insync.replicas，否则一个副本宕机整个分区就无法工作。推荐组合是 replication.factor 等于 min.insync.replicas 加一。

    八、如何保证不重复消费

    重复消费的根因有两个：消费端处理完消息但偏移量未成功提交；或者消费时长过长或网络等原因触发分区重平衡，消费位点回退。

    解决思路核心是消费方做幂等，用 Redis Set 去重或数据库主键天然幂等，这是最有效的手段。配合关闭自动提交、选择合适的提交时机来降低重复概率，但手动提交两侧各有丢消息与重复消费的风险，业界普遍接受至少一次的语义，靠业务幂等兜底。

    九、消费重试机制

    消费异常时默认会重试。以 Spring Kafka 为例，重试逻辑由错误处理器控制：异常消息会进入重试，达到最大次数后跳过当前消息继续消费后续，不会卡住整个队列。

    具体的重试次数与间隔由配置决定且因框架版本而异。Spring Kafka 的默认错误处理器通常在重试达到上限后跳过当前消息、继续消费后续，不会卡住整个队列；可以自定义退避策略注入错误处理器调整次数与间隔。具体数值不作为固定事实，以所用版本的实际行为为准。

    重试失败后的消息有两个去向：一是设置死信队列，把多次失败的消息投递到专门的死信主题供人工分析与重新消费；二是直接跳过。Spring Kafka 推荐用重试主题注解配置，比手写错误处理器更简洁，死信消息可用专门的处理方法消费。

    小结

    Kafka 是面试的重灾区，但主线很清晰：分区是理解一切的钥匙，它既是并发单元也是顺序保证的边界。可靠性四个配置配合 ISR 保证分区不丢，消费端用幂等兜底重复。面试时先讲清模型概念，再按生产者、消费者、Broker 三条线把不丢失讲透，最后落到顺序性与重试，基本能覆盖 Kafka 方向的大多数问题。下一篇看 RabbitMQ 的交换器路由与可靠性。
