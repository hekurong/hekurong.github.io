    MySQL 面试八股（二）：事务、锁与日志

    来源：面试八股资料整理（mysql八股合集.pdf、mysql日志八股.pdf、mysql的MVCC实现八股.pdf），结合 MySQL 官方文档口径校正。 定位：MySQL 面试八股第二篇，管写入与并发侧。事务怎么保证、锁怎么控制、MVCC 怎么实现可见性、三类日志各司其职，是数据库面试含金量最高的部分。 收藏：本系列收录于 后端八股复习指南。

    一、事务与并发问题

    1. 什么是事务

    事务是逻辑上的一组操作，要么全部执行，要么全部不执行。经典例子是转账，扣减转出方余额与增加转入方余额必须作为一个整体，任何一步失败都要回滚。

    数据库事务有 ACID 四大特性：

    • 原子性，事务是最小的执行单位，不允许分割，动作要么全部完成，要么全部不起作用
    • 一致性，执行事务前后数据保持一致，比如转账前后双方总额不变
    • 隔离性，并发访问时一个用户的事务不被其他事务干扰，各并发事务相互独立
    • 持久性，事务提交后对数据的改变是持久的，即使数据库故障也不受影响

    一个值得记住的观点：原子性、隔离性、持久性是数据库的属性，而一致性（ACID 意义上的）是应用的属性。应用依靠数据库的原子性与隔离性来实现一致性，单靠数据库无法包办。所以 A、I、D 是手段，C 是目的。

    2. 并发事务带来的四类问题

    多个事务并发操作同一批数据会产生四类问题：

    • 脏读。一个事务读到另一个事务未提交的修改。事务 1 把 A=20 改成 19 尚未提交，事务 2 读到 19，随后事务 1 回滚，事务 2 读到的就是脏数据
    • 丢失修改。两个事务并发改同一数据，后写者在先写者提交前已读过旧值，提交时把先写者的修改覆盖。事务 1 与事务 2 都读到 A=20，事务 1 改 A=19 并提交，事务 2 仍按读到的旧值 20 把 A 改成 18 并提交，最终 A=18，事务 1 的修改被覆盖丢失
    • 不可重复读。一个事务内两次读取同一记录结果不同。原因是有其他事务在两次读取之间修改并提交了该记录
    • 幻读。一个事务两次执行同一查询，第二次多出一些之前不存在的记录。原因是其他事务在两次查询之间插入了新数据

    不可重复读与幻读的区分：不可重复读针对已有记录的修改或减少，包括 update 和 delete；幻读针对记录的新增，是 insert 造成的结果集扩大。区分二者的意义在于解法不同，修改已有记录可以用记录锁，防插入则需要间隙锁与临键锁。

    3. 并发事务的控制方式

    MySQL 中控制并发事务只有两种思路：锁与 MVCC。

    • 锁是悲观控制，默认冲突会发生，先加锁再访问，共享资源靠显式锁保护
    • MVCC 多版本并发控制是乐观控制，为每一行维护多个版本，靠事务快照的可见性判断读到哪个版本，不加锁也能隔离

    二、事务隔离级别

    1. SQL 标准的四个隔离级别

    隔离级别越高，数据一致性越好，并发性能越低。四个级别以及各问题的暴露情况：

    • READ UNCOMMITTED 读取未提交。允许读未提交数据，脏读、不可重复读、幻读都防不住，实际很少用
    • READ COMMITTED 读取已提交。只能读已提交数据，阻止脏读，仍可能出现不可重复读与幻读，是多数数据库的默认级别
    • REPEATABLE READ 可重复读。同一字段多次读取结果一致，除非数据被本事务修改，阻止脏读与不可重复读，幻读在标准下仍可能发生
    • SERIALIZABLE 可串行化。事务逐个执行，杜绝一切并发干扰

    各级别的问题对照：读未提交三项都防不住；读已提交只防脏读；可重复读防脏读与不可重复读；可串行化全部防住。

    2. 隔离级别如何实现

    MySQL 的隔离级别由锁与 MVCC 共同实现。SERIALIZABLE 通过锁实现；READ COMMITTED 与 REPEATABLE READ 基于 MVCC 实现，但在 REPEATABLE READ 的当前读场景下需要配合加锁读来防止幻读。

    3. InnoDB 的默认隔离级别

    InnoDB 默认使用 REPEATABLE READ。与标准的区别在于，InnoDB 在 RR 级别下通过 MVCC 与 Next-Key Lock 把幻读也基本解决了，因此常被作为 InnoDB 的一个卖点。

    查看方式：MySQL 8.0 之前用 SELECT @@tx_isolation，8.0 及以后用 SELECT @@transaction_isolation。

    SELECT @@transaction_isolation;
-- 输出 REPEATABLE-READ

    三、锁

    1. 表级锁与行级锁

    • 表级锁。锁定粒度最大的锁，直接把整张表锁住，与字段是否建索引无关。实现简单、加锁快、资源消耗少、不会死锁，但锁冲突概率最高，高并发下效率差。表级锁与存储引擎无关，MyISAM 与 InnoDB 都支持
    • 行级锁。锁定粒度最小的锁，针对索引字段加锁，只锁当前操作的行。并发度高、冲突少，但加锁开销大，可能死锁，且只在引擎层实现，MyISAM 不支持，InnoDB 默认使用

    行级锁的一个高频雷区：UPDATE、DELETE 的 WHERE 条件没有命中唯一索引或者索引失效时，行锁退化为对全表记录与间隙加锁，效果等效于全表锁。

    2. 三种行锁

    InnoDB 的行锁通过对索引数据页上的记录加锁实现，分三种：

    • 记录锁，锁单个行记录
    • 间隙锁，锁一个范围，但不包括记录本身，专门防范围插入
    • 临键锁，记录锁加间隙锁，锁范围且包含记录本身，主要用途就是解决幻读

    RR 级别下默认使用临键锁。如果操作的索引是唯一索引或主键，InnoDB 会把临键锁优化降级为记录锁，只锁目标记录，不再锁范围。

    3. 共享锁与排他锁

    不论表级锁还是行级锁，都分共享锁与排他锁两类：

    • 共享锁即读锁，事务读记录时获取，多个事务可以同时获取，互相兼容
    • 排他锁即写锁，事务改记录时获取，与任何其他锁都不兼容

    一句话总结：排他锁与任何锁互斥，共享锁只与共享锁兼容。显式加锁的 SQL：

    4. 意向锁

    判断能否给整张表加上表级锁前，需要快速知道表里有没有行锁，一行行遍历显然不行，于是有了意向锁。意向锁是表级锁，由引擎自动维护，用户无法手动操作。

    • 意向共享锁，事务有意向给表中某些记录加共享锁，加共享锁前必须先取得表的意向共享锁
    • 意向排他锁，事务有意向给表中某些记录加排他锁，加排他锁前必须先取得表的意向排他锁

    意向锁之间互相兼容。意向锁与表级共享锁、排他锁互斥，但不会与行级的共享锁、排他锁冲突。这样表锁与行锁可以共存：给表加锁前，先看表的意向锁，如果存在意向排他锁说明有行锁或即将有行锁，就不能加相冲突的表锁。

    5. 自增锁

    有 AUTO_INCREMENT 列的表在插入时涉及自增锁，是 InnoDB 内部的一种特殊表级锁。行为由 innodb_autoinc_lock_mode 控制：

    • 0 传统模式，插入执行完释放表锁
    • 1 连续模式，MySQL 8.0 之前默认，多条插入语句串联执行，自增值连续
    • 2 交错模式，MySQL 8.0 起默认，插入语句并发执行，速度快，但不保证自增值连续单调

    注意一个约束：如果主从复制的 binlog 格式是 statement，不能用交错模式，否则并发插入顺序无法在从库复现，会导致主从数据不一致。

    6. 当前读与快照读

    • 快照读，即普通 SELECT。InnoDB 基于多版本读一致性快照，读到的是记录的历史版本。即使目标行正被其他事务加排他锁修改，快照读也不会等待，直接读旧版本，不读最新数据。只有读已提交与可重复读两个级别使用一致性非锁定读
    • 当前读，读取记录的最新版本并加锁。SELECT … FOR UPDATE、SELECT … LOCK IN SHARE MODE、INSERT、UPDATE、DELETE 都属于当前读

    快照读适合对一致性要求不高、追求极致性能的场景。快照读与当前读组合起来是 MVCC 与锁协作的核心，下一章展开。

    7. 死锁

    死锁是数据库并发的经典大题。产生死锁需要四个必要条件，互斥、持有并等待、不可剥夺、循环等待。排查用 SHOW ENGINE INNODB STATUS 查看最近一次死锁涉及的事务与等待链。经典案例是两个事务各持一行的锁，又去更新对方持有的行。规避手段有统一加锁顺序、让索引命中减少锁行数量、控制事务长度，必要时对死锁重试事务。

    四、日志

    1. MySQL 的日志分类

    MySQL 日志包括错误日志、查询日志、慢查询日志、事务日志与二进制日志。面试重点集中在三类事务相关日志：redo log 重做日志、binlog 归档日志、undo log 回滚日志。

    2. redo log

    redo log 是 InnoDB 引擎独有的物理日志，内容形如「表空间号、数据页号、偏移量、修改长度、修改的具体数据」。它的作用是让 InnoDB 拥有崩溃恢复能力，保证事务的持久性。

    InnoDB 以页为单位管理数据，查询时把数据页加载进缓冲池，后续读写优先命中缓冲池，减少磁盘 IO。更新时同样先在缓冲池里改数据页，同时把这次页修改记录到 redo log。理想情况事务提交即刷盘，实际刷盘时机由策略控制：

    • 事务提交时刷盘，由 innodb_flush_log_at_trx_commit 控制
    • 重做日志缓存写满约一半时由后台主动刷盘
    • 检查点执行时，脏页刷盘同时伴随 redo log 刷盘
    • 后台线程每隔一秒定期刷盘
    • MySQL 正常关闭时全部刷盘

    innodb_flush_log_at_trx_commit 的三种取值：

    • 0，每次事务提交不主动刷盘，性能最高，但 MySQL 崩溃可能丢最近一秒事务
    • 1，每次提交都刷盘，性能最低但绝不丢数据，是默认值
    • 2，每次提交只把 redo log 写入文件系统缓存，MySQL 进程崩溃不丢，机器宕机可能丢一秒

    由于后台线程每秒刷一次，未提交事务的 redo log 也可能被刷到磁盘，这部分日志在崩溃后没有对应事务，恢复时自然丢弃。

    redo log 以日志文件组的形式存储，用环形数组循环写入。write pos 是当前写到的位置，checkpoint 是当前要擦除的位置，两者之间的空间可写入新日志。write pos 追上 checkpoint 意味着日志文件组写满，此时必须推进 checkpoint 腾空间。MySQL 8.0.30 起用 innodb_redo_log_capacity 参数替代文件组配置，文件数固定为 32。

    为什么不直接把修改后的数据页刷盘，非要 redo log？因为数据页 16KB，只改了其中几个字节，刷整页是随机写、非常慢；redo log 一条记录只有几十字节，且是顺序写，效率高得多。这就是 WAL 预写式日志的思路，先写日志腾出空间，再异步把脏页合并刷盘。

    3. binlog

    binlog 是 Server 层的逻辑日志，记录语句的原始逻辑，数据备份、主从同步都靠它。任何存储引擎只要发生了数据更新都会产生 binlog，且顺序写。

    binlog 有三种记录格式：

    • statement，记录 SQL 语句原文。从库直接重放语句，但遇到 now()、随机数等非确定性函数，重放结果与原库不一致
    • row，记录具体行的变更数据。信息最准确，主从不失真，但占用空间大、同步时更消耗 IO
    • mixed，两者的混合，由 MySQL 判断语句是否可能产生不一致，可能就用 row，否则 statement。实践上通常直接用 row

    写入机制：事务执行过程中日志先写进每个线程私有的 binlog cache，事务提交时才统一写入 binlog 文件，保证一个事务的 binlog 不可拆分。write 只是写入文件系统缓存，fsync 才真正落盘，两者由 sync_binlog 控制：0 表示只 write 不控制 fsync，性能好但宕机可能丢日志；1 表示每次提交都 fsync，最安全；N 表示攒够 N 个事务再 fsync，IO 瓶颈场景可以调大 N 权衡性能与丢失风险。

    4. redo log 与 binlog 的两阶段提交

    redo log 保证引擎层崩溃恢复，binlog 保证集群数据一致性，两者职责互补，但写入时机不同，redo 在事务执行中持续写，binlog 只在提交时写。如果两者各写各的，一旦中间宕机就会不一致，比如 redo 落盘了但 binlog 没落盘，从库和备份就少了这条更新，用 redo 恢复出来的数据和 binlog 对不上。

    两阶段提交把 redo log 的写入拆成 prepare 与 commit 两步，流程是：先写 redo log 到 prepare 状态，再写 binlog，最后把 redo log 改为 commit 状态。崩溃恢复时的处理：

    • 若 redo log 处于 prepare 且没有对应的 binlog，事务回滚，避免只有本地恢复没有主从同步的不一致
    • 若 redo log 处于 prepare 且能找到完整的 binlog，事务补完提交，因为 binlog 存在说明两阶段都走完了

    这样无论在哪一步宕机，两份日志的最终状态都能对齐。

    5. undo log

    undo log 是逻辑日志，主要两个作用，一是事务回滚时把数据恢复到修改前，二是配合 MVCC 记录历史版本供快照读。

    事务执行一条 DELETE，undo log 就记录一条对应的 INSERT；执行 UPDATE 就记录修改前的旧值。回滚时倒着重放 undo 即可。undo log 自身也要持久化，因此它的信息同样会写进 redo log。

    undo log 分两种：

    • insert undo log，insert 产生的记录只对本事务可见，事务提交后即可删除
    • update undo log，update 或 delete 产生的记录可能还要给 MVCC 提供历史版本，提交后不能立即删，进入历史列表等待后台 purge 线程清理

    同一行被多个事务或同一事务多次修改时，这些版本的 undo log 由记录行内的回滚指针串联成一条版本链，链首是最新版本，链尾是最早版本。MVCC 就沿着这条链向前找历史版本。

    6. 主从复制

    binlog 是主从复制的载体。常规主从复制是异步的，主库提交后从库拉取 binlog 回放，存在主从延迟；半同步复制要求至少一个从库确认收到 binlog 才算提交成功，显著缩小延迟窗口。生产通常读写分离加半同步，配合 GTID 标记事务保证主从位点一致。这也是从库读到旧数据的排查切入点。

    五、MVCC

    1. 什么是 MVCC

    多版本并发控制，为每一行数据维护多个版本，同一记录的多个历史版本通过 undo log 保存。写入时生成新版本，读取时按事务快照的可见性选择合适的版本，从而在并发读写时无需相互阻塞，兼顾一致性与并发性能。

    2. 三个依赖

    InnoDB 的 MVCC 依赖隐藏字段、Read View 与 undo log。

    每行数据自带三个隐藏字段：

    • DB_TRX_ID，6 字节，最后一次插入或更新该行的事务 ID，delete 在内部视为更新，只是用记录头标志位标记删除
    • DB_ROLL_PTR，7 字节，回滚指针，指向该行的 undo log 版本链，未被更新过则为空
    • DB_ROW_ID，6 字节，表没有主键且没有唯一非空索引时，用它生成聚簇索引

    Read View 记录创建瞬间与可见性判断相关的信息，核心字段：

    • m_low_limit_id，当前出现过的最大的事务 ID 加一，事务 ID 大于等于它的数据版本不可见
    • m_up_limit_id，活跃事务列表中最小的事务 ID，小于它的数据版本都可见
    • m_ids，创建 Read View 时仍处于活跃状态、尚未提交的其他事务 ID 列表
    • m_creator_trx_id，创建该 Read View 的事务 ID

    3. 可见性判断

    判断一个数据版本的 DB_TRX_ID 是否对当前事务可见，按顺序比较：

    1. DB_TRX_ID 小于 m_up_limit_id，说明修改该行的事务在快照生成前已提交，可见
    2. DB_TRX_ID 大于等于 m_low_limit_id，说明是快照生成之后才修改的，不可见
    3. 若在 m_up_limit_id 与 m_low_limit_id 之间，去活跃事务列表 m_ids 里查，能找到说明修改者尚未提交或自己之后才改，不可见，找不到说明修改者已提交，可见
    4. 不可见则沿回滚指针 DB_ROLL_PTR 取上一个版本，重复以上判断，直到找到可见版本或取完整个链

    4. RC 与 RR 的差异

    两个隔离级别都用 MVCC，差别只在 Read View 的生成时机：

    • 读已提交级别下，每次 SELECT 都生成一个新的 Read View，活跃事务列表实时刷新。两个 SELECT 之间若有其他事务提交，后一次查询就会看到新数据，造成不可重复读
    • 可重复读级别下，只在事务第一次 SELECT 时生成 Read View，之后一直复用，其他事务提交与否都不影响后续读取，从而实现了可重复读

    同样在 RR 下，快照读靠复用一个 Read View 防止了幻读，但当前读每次读到最新数据，仍需加锁防插入，所以要在当前读场景使用 Next-Key Lock 锁住记录及间隙，防止其他事务在范围内插入新记录，彻底解决幻读。

    5. 与前面知识点的串联

    串起来看整条线：普通 SELECT 走快照读，靠 MVCC 的隐藏字段、undo 版本链与 Read View 判断可见性；RR 下快照读复用一次 Read View，可重复且有防幻读能力。SELECT … FOR UPDATE 这类当前读走锁，RR 下默认加临键锁锁范围防止插入。redo log 保证已提交数据不丢，undo log 支撑回滚与多版本，binlog 保障主从一致，两阶段提交把 redo 与 binlog 对齐。这就是 InnoDB 并发与可靠性的完整拼图。

    小结

    本篇收拢了 MySQL 并发侧的全部核心考点。事务章节讲清 ACID 与四类并发问题，注意 A、I、D 是手段、C 是目的的视角。隔离级别章节记住 InnoDB 默认 RR 且能防幻读这个特殊卖点。锁章节掌握表级行级、三类行锁、S/X 与意向锁的分工，牢记当前读与快照读的差别。日志章节吃透 redo 的 WAL 思路与两阶段提交的两种异常处理。MVCC 章节能默写 Read View 的可见性算法和 RC 与 RR 的生成时机差异，就足以应对数据库方向的大多数深挖。
