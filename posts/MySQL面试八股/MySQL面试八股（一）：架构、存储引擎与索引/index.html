    MySQL 面试八股（一）：架构、存储引擎与索引

    来源：面试八股资料整理（mysql八股合集.pdf、mysql索引八股.pdf、mysql中sql语句执行过程.pdf），结合 MySQL 官方文档口径校正。 定位：MySQL 面试八股共两篇。本篇管查询侧，讲清数据怎么存、SQL 怎么跑、索引怎么让查询变快。下一篇管写入与并发侧，讲事务、锁、日志与 MVCC。

    一、MySQL 基础

    1. 关系型数据库与 MySQL

    关系型数据库建立在关系模型之上，数据以表的行来组织，行与行之间表达一对一、一对多、多对多等联系。主流关系型数据库通过 SQL 操作数据，并普遍支持事务的 ACID 特性。常见的例子有 MySQL、PostgreSQL、Oracle、SQL Server、SQLite。

    MySQL 开源免费、成熟稳定、社区活跃，成为最流行的关系型数据库之一。它的默认端口是 3306，默认存储引擎是 InnoDB。

    2. 常用字段类型速记

    MySQL 字段类型三大类：数值型、字符串型、日期时间型。面试常考的是几个细节：

    • UNSIGNED 属性。整数类型加 UNSIGNED 表示不允许负值，正数上限翻倍。TINYINT 范围从 -128 到 127 变成 0 到 255，INT UNSIGNED 可以达到约 42 亿。从 0 开始递增的 ID 列非常适合用 UNSIGNED
    • CHAR 与 VARCHAR。CHAR 定长，存储时右侧补空格，检索时去掉；VARCHAR 变长，额外用 1 或 2 字节记录长度。CHAR 适合长度稳定的数据如 MD5 密码、身份证号，VARCHAR 适合昵称、标题这类长度不定的数据
    • VARCHAR(100) 与 VARCHAR(10)。两者存相同的字符串占用相同的磁盘空间，很多人误以为大的更浪费磁盘，其实磁盘占用看实际内容。但 VARCHAR(100) 在内存操作（如排序）时按声明长度分配，会消耗更多内存
    • DECIMAL 与 FLOAT/DOUBLE。DECIMAL 是定点数，精确存储小数，适合金额；FLOAT/DOUBLE 是浮点数，只能近似存储。Java 中 DECIMAL 对应 BigDecimal
    • 为什么不推荐 TEXT 和 BLOB。不能设默认值，无法用内存临时表只能在磁盘建临时表，检索效率低，不能直接建索引需要前缀，且大字段会拖慢表上的 DML 并消耗网络 IO
    • DATETIME 与 TIMESTAMP。DATETIME 8 字节无时区，范围 1000 年到 9999 年；TIMESTAMP 4 字节与时区相关，且范围只到 2038 年
    • NULL 与空串。NULL 表示缺失未知，不等于任何值，包括 NULL 自身，判断必须用 IS NULL；空串是已知的空字符串，可以正常比较。聚合函数会忽略 NULL，COUNT(*) 统计全行而 COUNT(列) 统计非空。因此不建议用 NULL 作为列默认值
    • 布尔值。MySQL 没有真正的布尔类型，用 TINYINT(1) 存 0 或 1 表达
    • 手机号存储。用 VARCHAR 而非整数。手机号不做算术运算，本质是标识符，而且可能带前导零、国家码、分隔符，加密后的密文也只能存进字符串类型，VARCHAR 才能按号段 LIKE 查询

    二、基础架构与 SQL 执行流程

    1. 一条 SQL 在 MySQL 里怎么走

    MySQL 分成两层。Server 层包含连接器、查询缓存、分析器、优化器、执行器以及通用日志 binlog，所有跨存储引擎的逻辑都在这一层。存储引擎层提供插件式的数据存储读写，InnoDB 拥有自己的 redo log。

    各组件职责：

    • 连接器。负责登录认证与权限校验。登录成功后，本次连接内的权限判断都依赖连接时读取到的权限数据，即使之后管理员修改了权限，已建立的连接也不受影响
    • 查询缓存。以 SQL 文本为 key 缓存结果集，MySQL 8.0 之后整体移除。早期版本的命中条件极其严格，任何字符差异都不命中，而且表一旦更新整表缓存全部失效，对写密集应用反而有害
    • 分析器。先做词法分析，提取关键字、表名、字段、条件；再做语法分析，判断 SQL 是否符合语法
    • 优化器。决定执行方案，比如多个索引时选哪个，多表时选什么连接顺序。优化器选的是它认为最优的方案，不保证绝对最优
    • 执行器。执行前再次校验权限，然后调用存储引擎接口取数据

    查询语句的大致流程：先做权限校验（命中缓存时），再查查询缓存，随后依次经过分析器与优化器，再一次校验权限，最后由执行器调用存储引擎取数。

    2. 更新语句与两阶段提交

    更新语句在查询的基础上多了日志环节。以 InnoDB 为例，流程是：先找到目标行，在内存中修改数据页并记录 redo log，此时 redo log 处于 prepare 状态；执行器再写 binlog；然后调用引擎把 redo log 提交为 commit 状态。

    之所以要两阶段提交，是为了保证 redo log 与 binlog 的一致性。如果先写 redo 后写 binlog，写完 redo 后宕机，机器靠 redo 恢复出了这条数据，但 binlog 里没有，主从同步与备份会少这一条。如果先写 binlog 后写 redo，反过来本机恢复不了但 binlog 有记录，同样不一致。两阶段提交让两份日志要么都生效要么都回滚，具体判断逻辑在下一篇日志部分展开。

    三、存储引擎

    1. 插件式架构

    MySQL 的存储引擎采用插件式架构，按表指定，互不影响。可以通过 SHOW ENGINES 查看所有引擎，SHOW VARIABLES LIKE ‘%storage_engine%’ 查看默认引擎。InnoDB 最初是第三方引擎，因表现优秀被收购整合，从 MySQL 5.5.5 起成为默认引擎。在 InnoDB 之前，MyISAM 是默认引擎。

    2. InnoDB 与 MyISAM 的对比

    两者都用 B+ 树做索引，但实现方式和特性差别很大：

    • 锁粒度。MyISAM 只有表级锁，一锁锁整表，并发写性能差；InnoDB 支持行级锁与表级锁，默认行级锁，并发写好得多
    • 事务。MyISAM 不支持事务；InnoDB 支持事务，实现 SQL 标准的四个隔离级别，且默认的 REPEATABLE READ 级别能通过 MVCC 与 Next-Key Lock 防止幻读
    • 外键。MyISAM 不支持，InnoDB 支持。生产环境一般不用外键，由应用层做约束，外键会有性能损耗
    • 崩溃恢复。MyISAM 崩溃后无法安全恢复，InnoDB 依赖 redo log 在重启后恢复到崩溃前状态
    • MVCC。MyISAM 不支持，InnoDB 支持。MVCC 可以看作行级锁的成本优化，减少加锁开销
    • 索引实现。MyISAM 的索引叶节点存放数据记录的地址，是典型的非聚簇索引；InnoDB 的表数据文件本身就是按主键组织的 B+ 树，叶节点存完整数据，是聚簇索引
    • 缓存策略。InnoDB 用缓冲池缓存数据页和索引页，MyISAM 用键缓存只缓存索引页

    实用结论：几乎找不到用 MyISAM 的理由，老老实实用 InnoDB。因此新配置文件里的默认引擎是 default_storage_engine=InnoDB。

    四、索引

    1. 索引的作用与代价

    索引是排序好的数据结构，相当于书的目录，可以大幅减少扫描的数据量、降低磁盘 IO。但索引不是免费的：建索引和维护索引要花时间，增删改时索引要跟着更新，索引本身也要占物理空间。

    用索引一定能提升性能吗？不一定。数据量很小的表，全表扫描本身很快，索引收益有限，优化器也可能不用索引。

    2. 为什么选 B+ 树

    面试常从数据结构选型切入，逐个排除：

    • 哈希表。等值查询接近 O(1)，但不支持排序与范围查询，每次 IO 只能取一个，MySQL InnoDB 不直接用哈希索引，只有自适应哈希索引作为 B+ 树的加速补充
    • 二叉查找树。平衡时查询 O(logN)，但插入有序数据会退化成斜树，复杂度恶化到 O(N)
    • AVL 树。严格平衡，查询效率稳定，但为了保持平衡频繁旋转，写开销大，而且每个节点只存一个数据，磁盘 IO 次数多
    • 红黑树。大致平衡，插入删除只需常数次旋转变色，内存场景表现出色，但树高高于 B+ 树，数据在磁盘时需要更多次 IO
    • B 树（多路平衡查找树）。节点同时存 key 与 data，树矮、IO 少。但范围查询要中序遍历，非叶节点也存数据导致单页能存的 key 变少
    • B+ 树。非叶节点只存 key，一页能装更多 key，树更矮、IO 更少；数据全部落在叶子节点，且叶子之间用链表相连，范围查询和排序只需沿链表遍历；所有查询都要走到叶子，查找性能稳定

    结论：B+ 树在磁盘数据库场景下，用更少 IO、更稳定的查找和更快的范围查询胜出，所以 MySQL 和绝大多数数据库都选它。

    3. 聚簇索引与非聚簇索引

    • 聚簇索引。索引结构和数据一起存放。InnoDB 的主键索引就是聚簇索引，表数据文件本身按主键 B+ 树组织，叶子节点存完整行数据。查询快、范围检索快，但数据依赖有序插入，主键更新代价大，所以主键一般不可改
    • 非聚簇索引。索引与数据分开存放，叶子节点存数据地址或主键值。MyISAM 不管主键还是普通索引都用非聚簇；InnoDB 的辅助索引也属于非聚簇，叶子节点存主键值，查询时先找主键再回表

    InnoDB 表没有显式主键时，会先找唯一非空索引当主键，都没有则隐式生成一个 6 字节的自增主键。建表时建议用不长、单调递增、不随机、含业务意义更好的字段做主键。

    4. 索引的分类

    从应用维度看：

    • 主键索引。加速查询，列值唯一且非空，一表一个
    • 普通索引。仅加速查询，允许重复与 NULL
    • 唯一索引。加速查询并约束值唯一，允许 NULL，可建多个
    • 前缀索引。对字符串列的前几个字符建索引，占用更小，只适用于字符串
    • 全文索引。对 CHAR、VARCHAR、TEXT 文本分词检索，一般场景直接用搜索组件替代
    • 覆盖索引。查询需要的字段全部包含在索引里，不用回表
    • 联合索引。多个字段组成一个索引，等价于多个左前缀索引

    MySQL 8 的新特性：隐藏索引，不被优化器使用但仍维护，适合灰度与软删除场景，主键不能设隐藏；降序索引，真正按降序存储；函数索引，索引里可以放函数或表达式，8.0.13 起支持。

    5. 覆盖索引

    辅助索引叶子节点存的是主键值，查非索引字段时要回主键树再查一次，叫回表。如果查询的字段恰好都在索引里，那直接沿索引取数据即可，无需回表，这就是覆盖索引。

    1
2
    -- 假设 name 上有索引，这条查询只取 name，直接命中索引无需回表
SELECT name FROM user WHERE name = 'anne';

    判断命中：EXPLAIN 输出的 Extra 列出现 Using index，说明用了覆盖索引。

    6. 联合索引与最左前缀匹配

    联合索引按字段声明顺序组织。命中规则是最左前缀匹配：从左到右依次匹配查询条件，一直匹配到范围查询为止。需要注意一个常见误区，对于大于等于、小于等于、BETWEEN 以及前缀 LIKE，不会中断匹配，只有大于、小于这种严格范围查询才会中断。

    CREATE TABLE student (
  id int NOT NULL,
  name varchar(100) DEFAULT NULL,
  class varchar(100) DEFAULT NULL,
  PRIMARY KEY (id),
  KEY idx_name_class (name, class)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

    假设联合索引是 (a, b, c)：

    • 查询 a=1 AND c=1，按最左匹配在 a 上走索引，再用 c 过滤，部分命中
    • 查询 c=1，不含最左列 a，整个索引用不上
    • 查询 b=1 AND c=1，同样缺最左列，索引用不上

    实践建议：把区分度高的字段放最左边。MySQL 8.0.13 引入的索引跳跃扫描可以在某些不满足最左前缀的场景下避免全表扫描，但效果有限且有历史缺陷，了解即可。

    7. 索引下推

    索引下推是 MySQL 5.6 的优化，把部分 WHERE 判断下推到存储引擎层，在索引遍历时就过滤掉不满足条件的记录，减少回表次数与引擎层到 Server 层的数据传输。

    1
2
    -- zipcode 与 birthdate 建联合索引，birthdate 用函数导致无法继续走索引范围
SELECT * FROM user WHERE zipcode = '431200' AND MONTH(birthdate) = 3;

    没有索引下推时，引擎层先按 zipcode 找到所有目标主键，全部回表取完整数据交给 Server 层再过滤出生日期；有索引下推时，引擎层在索引遍历中就判断 MONTH(birthdate)，只对满足条件的记录回表。下推适用于 InnoDB 与 MyISAM 的 range、ref、eq_ref 等查询，且只对非聚簇索引有意义，子查询和存储过程场景不支持。

    8. 索引失效的常见场景

    • 联合索引查询不遵守最左匹配
    • 在索引列上做计算、函数、类型转换，比如 WHERE MONTH(birthdate)=3
    • 以 % 开头的 LIKE，比如 LIKE ‘%abc’
    • OR 前后有一个条件的列没有索引，全部索引都不生效
    • IN 的取值范围过大时可能全表扫描，NOT IN 同理
    • 发生隐式类型转换，比如字符串列与数字比较
    • SELECT * 本身不阻断索引，但可能让覆盖索引失效并产生多余的数据传输

    9. 索引的使用建议

    • 给不为 NULL、被频繁查询、常作 WHERE 条件、频繁排序、频繁连接的表字段建索引
    • 频繁更新的字段慎建索引
    • 单表索引不建议超过 5 个，索引过多会拖慢插入更新，也增加优化器评估执行计划的开销
    • 尽量用联合索引代替多个单列索引，省空间、提更新效率
    • 避免冗余索引，(a, b) 与 (a) 重复时保留前者
    • 字符串用前缀索引代替普通索引
    • 定期清理长期未使用的索引，MySQL 5.7 可查 sys.schema_unused_indexes

    10. 如何分析 SQL 是否走索引

    用 EXPLAIN 分析执行计划，它不真正执行语句，而是让优化器给出分析结果。关键字段：

    • type，表的访问方式，常见由好到坏有 system、const、eq_ref、ref、range、index、ALL，出现 ALL 就是全表扫描
    • key，实际使用的索引
    • possible_keys，可能用到的索引
    • rows，预计扫描的行数
    • Extra，附加信息，Using filesort 表示需要额外排序，Using index 表示覆盖索引，Using temporary 表示用了临时表
    1
    EXPLAIN SELECT score, name FROM cus_order ORDER BY score DESC;

    五、查询缓存（了解即可）

    MySQL 5.6 起查询缓存默认禁用，8.0 起彻底移除。弃用的原因在前面架构部分讲过：命中条件苛刻、表更新即全量失效、写密集场景净添负担。回答面试题时说明它存在的年代、为什么被移除即可，不必深究配置。

    小结

    本篇回答了 MySQL 查询侧的三件事。数据怎么存，取决于存储引擎，InnoDB 用聚簇索引把表数据与本组织成同一棵 B+ 树。SQL 怎么跑，走连接器到执行器的固定流水线，更新语句额外经历 redo 与 binlog 的两阶段提交。怎么查得快，靠索引，选型逻辑从哈希一路排除到 B+ 树，然后是聚簇与覆盖、联合同最左前缀、索引下推这些连环考点。下一章转入写入与并发侧，事务隔离、锁、MVCC 与三类日志都将在其中展开。
