## 0. 章首核心观点



- OpenAI AI 能力五等级（Level 1 对话者 → Level 2 思考者 → Level 3 智能体 → Level 4 创新者 → Level 5 组织 Organizations）中，多 Agent 协作常被类比为通向第五级的路径。**澄清**：Organizations 指"AI 能完成整个组织的工作"这一能力级别，而非对系统架构的要求——足够强大的单个 Agent 理论上也能达到。但就今天工程现实而言，单个 Agent 终究受限于自身模型能力边界和上下文窗口。

- **更根本的一点：群体的智能可以高于个体**。人类文明是明证——单个人智力有限，但经由分工、协作、辩论和知识代际累积，人类社会整体展现的智能远超任何一位天才个体。Agent 群体同样可能涌现集体智能：哪怕每个 Agent 都只相当于人类专家水平，只要组织得当，整体能力也可能超过所有人类专家的总和。Google DeepMind《从 AGI 到 ASI》把"大规模多 Agent 集体"列为通往超级智能（ASI）的关键路径之一。

- 本章结构：分类框架（两个核心维度）→ 多 Agent 何时真正优于单 Agent → 共享上下文协作 → 不共享上下文协作（三种拓扑）→ 失败模式 → Agent 社会（前沿探索）。

## 1. 多 Agent 协作的分类框架



### 1.1 维度一：上下文是否共享



- **共享上下文**：后一个 Agent 接收前一个 Agent 的完整对话历史和轨迹（trajectory）。每个阶段切换系统提示词和工具集后就是一个新的 Agent（身份、职责、能力都变了），但保留前任全部记忆（需求分析师写完需求文档后，开发者还能看到分析师与用户的所有沟通记录——新角色但完整保留之前上下文）。优势：信息不丢失、每 Agent 都能回顾任何阶段细节；挑战：上下文可能快速膨胀。

- **不共享上下文**：每个 Agent 维护完全独立的上下文和对话历史，彼此无法直接访问对方"思考过程"（不同部门协作：各自工位独立工作，通过共享文档和会议纪要交换信息）。模块化和隔离性更好、系统更易扩展维护（增加新 Agent 不需改动现有 Agent 内部逻辑，只需定义接口和数据格式）。

- 不共享上下文必须通过显式通信机制传递信息——经典分布式系统早有答案：**IPC 两大范式——共享内存（一方写入、另一方读取同一块存储）和消息传递（把数据显式发送给对方）**。Agent 间三种常见通信机制：

  1. **工具调用的参数**：上游 Agent 把结构化数据作为参数传给下游工具，适合类型确定、结构清晰的场景；

  2. **共享文件系统**：通过读写共享目录下的文档、代码等中间产物交换信息，适合产物较大或需要持久化的场景；

  3. **消息总线（Message Bus）**：专门中转站，Agent 不直接调用彼此、把消息发到总线由它转发。

  - 对应关系：共享文件系统 = Agent 世界的"共享内存"；工具调用参数和消息总线 = "消息传递"两种形态（前者随调用同步传递、后者经中转站异步投递）。Go 名言："不要通过共享内存来通信，而要通过通信来共享内存"——共享内存快但把并发冲突隐患留给使用者；消息传递要多写编排代码但数据归属清晰可循。

- 消息总线天然支持异步通信（像公司邮件系统：发邮件不要求对方此刻在电脑前），特别适合多个 Agent 并行工作、彼此需要协调的场景。

- **澄清**：两种架构都是真正的多 Agent 系统（每阶段系统提示词和工具集不同就是不同 Agent），区别在协调方式——共享上下文靠隐式协调（后续 Agent 继承完整上下文，"看到"之前思考过程）；不共享上下文靠显式协调（通过文件、消息或结构化数据接口交换信息）。比方：前者像团队围桌讨论所有人听到所有话；后者像不同部门通过邮件和文档协作。

- **操作系统类比**：共享上下文是线程、不共享上下文是进程。线程共享地址空间、切换开销小、通信不需拷贝，代价是没有隔离（一个线程写坏内存、整个进程崩溃）；进程各有独立地址空间、隔离彻底、可安全并行，代价是通信必须经过显式 IPC。表 10-1 每一条选择依据都能从这组取舍推出：



| 选择依据 | 共享上下文 | 不共享上下文 |
|---|---|---|
| 子任务数量 | 少（2-3 个角色） | 多（需要并行处理） |
| 上下文窗口 | 足以容纳所有角色的信息 | 单窗口装不下 |
| 并行度 | 串行为主（角色沿同一段轨迹依次接棒） | 可大规模并行（上下文互相独立、互不阻塞） |
| 信息隔离 | 不需要（所有角色共享信息） | 需要（如安全审查不应看到原始思考过程） |
| 成本预算 | 单条轨迹接力，token 随阶段累积 | 多 Agent 各自展开，总 token 通常高出数倍到一个数量级 |




- **简单判断**：若预期累计上下文会超过窗口的 50%（经验法则非精确阈值），应不共享；若信息零损耗对任务正确性是硬约束，应共享；**多数实际系统采用"阶段切换式"方案**——前几个 Agent 共享，到信息饱和点后切换为不共享上下文 + 显式 handoff（移交，由上游 Agent 主动决定把哪些信息交接给下游）。



### 1.2 维度二：协作拓扑



- 协作拓扑指 Agent 之间的控制权和信息按什么结构流动。与上下文是否共享概念上独立、实践中相关——共享上下文的系统同样存在拓扑（transfer_to_agent 本质是链式移交在共享上下文下的形态）；但一旦共享上下文，拓扑往往会退化（移交无需决定"传什么"，完整历史天然保留，拓扑退化为角色切换序列，没有太多架构决策可做；例外是 group chat 式多方协作）。一旦不共享上下文，"信息如何流动、由谁协调"就成为必须显式设计的问题。

- **术语说明：Graph 工程**（2026 年 7 月开始流行的名称）：显式设计执行图——节点是 Agent、普通程序或人工决策，边定义任务依赖、条件路由与失败后的去向，结构化状态在节点间流动。本章"协作拓扑"正是其中的多 Agent 子集。由于名称很新且易与知识图谱/GraphRAG/执行轨迹混淆，本书以"协作拓扑"和"编排"为主要术语。

- 两个维度原则上构成 2×3 组合矩阵，但共享上下文一行里拓扑大多退化为角色切换序列，本章只详细展开不共享上下文的三格，按复杂度递增：

  1. **对等协作模式（Peer Collaboration）**：少量 Agent（通常 2-3 个）以平等身份交互，形成迭代改进循环（写论文时一个人起草、另一个人批注修改，反复几轮质量远超一个人闷头写）；

  2. **管理者模式（Orchestration）**：中心化 Manager Agent 负责任务规划和调度，多个子 Agent 各负责特定子任务（项目经理带几位专业工程师）；

  3. **去中心化模式（Decentralized）**：没有运行时的中心控制者，Agent 之间像人类一样互相沟通，协作完成任务。

## 2. 多 Agent 何时真正优于单 Agent



- **核心判据只有一条：协作过程是否引入了单个 Agent 在生成时无法获得的新信息？**

- 表 10-2 信息增量对比：



| 协作模式 | 是否引入新信息 | 效果 |
|---|---|---|
| 同一模型自我审查（重新阅读自己输出） | 否 | 通常无效甚至有害 |
| 不同 Agent 辩论同一段文本 | 否 | 在等计算量下与单 Agent 持平 |
| Reviewer 使用测试执行结果审查代码 | 是（执行反馈） | 显著提升 |
| Reviewer 查看渲染截图审查前端/PPT 代码 | 是（视觉反馈） | 显著提升 |
| Reviewer 使用外部工具验证事实 | 是（工具反馈） | 显著提升 |




- **RLEF（Reinforcement Learning from Execution Feedback，2025）**证实：通过强化学习训练模型利用代码执行反馈迭代改进代码，效果远超让模型独立多次采样——每次迭代都引入真实执行结果（编译错误、测试失败、运行时异常），这些信息在模型写代码时并不存在。**WebGen-Agent（2025）**网页生成任务通过多层视觉反馈脚手架（截图 + 视觉语言模型描述）使 Claude 3.5 Sonnet 从 26.4% 提升到 51.9%——接近翻倍。

- **"新信息"框架解释矛盾现象**：学术研究说"单 Agent 就够了"但工程实践多 Agent 确实更好——根源在于两者讨论的是不同类型的"多 Agent"：学术研究比较的多是"多个 Agent 看着同一段文本互相讨论"（如辩论），工程实践中有效的多 Agent 系统往往包含外部反馈环路（代码执行、视觉渲染、工具调用）。前者没引入新信息、后者引入了。本章后面对等协作、管理者、去中心化三种架构，凡是真正有效的用法几乎都能在这条判据上找到落点。

- **步骤预算与 Agent 性能**：2025 年 Google《Budget-Aware Tool-Use Enables Effective Agent Scaling》反直觉结论——单纯增加可用步骤数不能保证性能提升，标准 Agent 缺乏"预算意识"（即使 300 步预算仍倾向浅层搜索、很快"饱和"）。需要显式预算感知机制：前期广泛探索、后期聚焦最有希望方向。2026 年 **BAVT（Budget-Aware Value Tree Search）**提出步骤级价值评估，每步根据剩余预算比例调整探索与利用权重——预算减少时从"广撒网"切换"深挖掘"。对多 Agent 设计指导：Manager 不应简单分发任务等结果，应按任务复杂度动态分配步骤预算（简单子任务少步骤、复杂子任务充足步骤），并引导子 Agent 合理利用（先规划、再实现、再测试、再改进）。

- **成本必须摆在所有设计之前**：多 Agent 并行探索与反复迭代都花钱——Anthropic 披露其多 Agent 研究系统 token 消耗约为普通对话的 15 倍，token 用量本身能解释其中约 80% 的性能差异。多 Agent 效果收益必须足够大、大到覆盖数倍乃至一个数量级的额外开销，否则调校得当的单 Agent 往往更划算。

## 3. 共享上下文的多 Agent 协作



- 每个阶段是独立 Agent（拥有自己系统提示词和工具集）但继承前序 Agent 完整轨迹（接班的同事能翻阅前任所有工作日志）。核心优势信息零损耗；挑战是让当前 Agent 专注自己核心职责、不被继承的大量历史信息干扰。



### 3.1 多阶段角色转换



- **定义之争**：用第一章语言，多阶段角色转换是工作流式编排——执行路径（需求澄清→实现→审查）预先定义。从进程角度：一个进程依次执行不同阶段代码——换的是代码段、内存自始至终同一份，并非多进程——不把它算"真正的多 Agent"的观点有其道理。本章仍纳入多 Agent 框架，因为这样做有设计收益：各阶段系统提示词/工具集/关注点不同时，把各阶段看作共享同一段轨迹的多个 Agent，每个"身份"的提示词和工具集可独立打磨，阶段边界天然成为质量门控点。

- 复杂任务中角色职责可能显著变化，始终用同一套静态系统提示词要么过于笼统缺乏针对性、要么把所有阶段指导塞在一起过于冗长。多阶段角色转换：根据当前阶段动态切换系统提示词和工具集，让 Agent 每阶段以最合适的"身份"工作——不需要创建新实例或启动新进程，只是同一执行会话中更新上下文。角色切换了但对话历史和任务状态始终连续共享。

- 实验 10-1 ★★（根据执行阶段决定系统提示词）：Coding Agent 三阶段（需求澄清→代码实现→质量审查），每阶段角色（需求分析师/软件工程师/代码审查员）、提示词、工具集都不同；阶段转换通过特定工具调用触发（complete_requirements_analysis() → submit_for_review() → approve_code() 或 request_revision(issues)）。需求澄清阶段"不要急于实现，你的任务是提问和确认"（工具只有 ask_clarifying_question/save_requirement/complete_requirements_analysis）；实现阶段"遵循最佳实践，模块化、错误处理、必要注释"（工具换 write_file/read_file/execute_code）；审查阶段"采用批判性思维"（工具换 run_linter/run_tests/analyze_complexity）。三阶段设计让 Agent 每阶段专注当前核心任务，明确的阶段转换机制保证执行完整性（不会跳过需求分析直接写代码、不会未经审查就交付），还处理回退情况（审查发现问题返回实现阶段）。



### 3.2 跨领域角色转换



- 多阶段角色转换是单一任务类型中的阶段化执行；跨领域角色转换探索 Agent 在多种任务类型之间的自主切换——不再是预先规划的线性流程，而是根据用户需求变化由 Agent 自主判断切换哪个专业角色。

- 实验 10-2 ★★（多角色转换）：五种角色——triage（前台分诊，默认入口，理解整体需求拆成有先后顺序的子任务、逐步移交、全部完成后收尾确认，自身只持有 transfer）、research（web_search 查数据事实资料）、coding（execute_python 写并运行代码）、data_analysis（calculate/descriptive_stats 定量计算统计）、writing（润色成稿）。核心机制 **transfer_to_agent(target_role, reason) 工具**：调用时系统依次 1) 保存当前对话历史 2) 加载目标角色提示词和工具集 3) 将对话历史传递给新角色 4) 以新角色身份继续执行。实验场景（新能源车销量数据 → 年均复合增长率 → 面向投资人 120 字中文总结）：链路 triage → research → data_analysis → writing → triage，每个角色都看得到完整对话历史、天然知道前面已做了什么。角色转换决策依赖系统提示词指导（triage 提示词列明路由规则：查数据转 research、写代码转 coding、定量计算转 data_analysis、润色成稿转 writing）。实验要求含处理循环切换问题（避免 Agent 在角色间反复切换）。

## 4. 不共享上下文的多 Agent 协作



- 不共享上下文代表真正的多 Agent 协作：每 Agent 独立实体、拥有自己的上下文/轨迹/状态，协作完全依赖明确的、结构化的数据传递机制（三种通信机制）。

- **操作系统类比延伸（表 10-3）**：



| 操作系统 | 多 Agent 系统 |
|---|---|
| 程序（可执行文件） | 静态前缀（系统提示词 + 工具定义） |
| 进程的内存 | 轨迹 |
| CPU | LLM |
| 内核 | Agent 运行时 |
| 系统调用 | 工具调用 |
| fork（创建子进程） | spawn_subagent |
| kill（发送信号） | cancel_subagent |
| ps（列出进程） | list_agents |
| 退出码与 wait() | 子 Agent 返回的结构化摘要 |
| 共享内存 / 消息传递 | 共享文件系统 / 消息 |




- 程序是静态代码、进程是程序的一次运行。同样：**静态前缀决定 Agent 是谁，轨迹记录它走到哪一步。LLM 扮演 CPU——自身不保存状态，靠加载不同上下文分时服务许多 Agent**（"上下文切换"本就从操作系统借来）。换更强的模型，Agent 还是原来那个 Agent——身份和记忆在前缀与轨迹里、不在模型权重里。

- 这套抽象并不新鲜：私有状态、异步消息、可创建新成员正是 1970 年代 **Actor 模型**的基本设定，多 Agent 系统可看作它的 LLM 版本。操作系统与分布式系统成熟经验大多可直接借用。**唯一失效之处**：进程间传递字节、逐位保真；Agent 间传递语义、每次转述都可能失真——这是本章"失败模式"一节要专门讨论的新问题。

- 进程式隔离的工程好处：每 Agent 可独立开发和测试、新增能力不需改动现有代码、某 Agent 故障不传染其他 Agent、多 Agent 真正并发执行（上下文完全独立无资源竞争）。代价：信息同步问题（各 Agent 如何对任务状态保持一致理解？信息传递中丢失或重复？）、调试更困难（翻看多个 Agent 日志才能拼出完整执行过程）——接口规范、数据格式、通信协议的设计至关重要。

- 不共享上下文的显式协作依赖两套与拓扑无关的基础设施：**共享文件系统（数据平面）**——Agent 间交换产物、与用户交换文件的持久媒介；**通信与控制机制（控制平面）**——消息传递、状态查询、执行终止与资源调度。三种拓扑都建立在这两者之上。



### 4.1 Agent 眼中的文件系统



- Agent 访问的不是单一存储，而是**虚拟文件系统（virtual filesystem）**：来源、生命周期与权限各异的存储被挂载（mount）到同一目录树下，Agent 通过统一 read_file/write_file/list_dir 接口访问。明确目录树构成（每区域可见性与生命周期）是多 Agent 协作设计的前提——相当一部分并发冲突与信息泄露源于将本应隔离的区域混置。**这棵目录树相当于 Agent 的地址空间，四类区域就是权限各异的内存段；操作系统保护哲学同样成立——默认隔离，共享须显式声明**。四类区域：

  1. **Agent 专属工作区（Scratchpad）**：每 Agent 实例独享私有目录，存中间产物、临时文件、草稿、调试日志，生命周期与实例绑定，对其他 Agent 和用户不可见。隔离双重作用：避免多 Agent 临时文件相互覆盖、保持主 Agent 上下文精简（子 Agent 试错留存自身工作区、仅将最终产物提交共享空间——对应第四章"子 Agent 返回结构化摘要而非全量轨迹"在存储层面的体现）；

  2. **多 Agent 共享空间（Shared Workspace）**：多 Agent 共同读写、用户可见的协作区域，是不共享上下文下 Agent 间交换产物主要媒介；生命周期与整个任务绑定、需持久化。多方并发读写区域、并发冲突高发处——乐观锁、工作副本隔离（worktree）等机制作用于此（第四章以卷挂载 /workspace/shared 连接主 Agent、虚拟电脑与虚拟手机是典型实现）；

  3. **外部挂载资源（Mounted External Resources）**：用户授权接入的第三方信息源（Google Drive、Notion、Dropbox、企业 Wiki），通过适配器映射为挂载点（如 /mnt/gdrive）。与本地存储区别需显式处理：访问受外部权限约束（用户在源系统权限决定 Agent 可见范围）、延迟更高且一致性更弱（每次读取为网络往返、数据可能已被外部修改，只能按最终一致性对待）、以按需只读为主（写回外部源须谨慎，误写可能污染用户真实数据）。统一文件接口使 Agent 无需为每个数据源定制专用工具，但也掩盖性能与安全差异——需在挂载层面显式管理只读/可写、超时与凭证边界；

  4. **系统内置资源（Built-in System Resources）**：系统预置、对所有 Agent 只读共享的资源包（Skills——文件形式组织的知识文档与脚本，挂载于 /skills，按渐进式披露取用；参考手册、模板库、共享工具定义）。全局共享、只读、跨会话稳定，可被所有 Agent 并发读取而无需并发控制。

- 表 10-4 四类区域对比：Agent 专属工作区（仅该 Agent 可见 / 随实例销毁 / 读写 / 不需要并发控制）；多 Agent 共享空间（所有协作 Agent+用户 / 随任务持续需持久化 / 读写 / 需要乐观锁或 worktree）；外部挂载资源（视外部授权而定 / 由外部源决定 / 多为只读写需谨慎 / 由外部源负责）；系统内置资源（所有 Agent / 跨会话稳定 / 只读 / 不需要）。

- **"文件路径作为通用接口"的价值**：Agent 间传递产物、主 Agent 向子 Agent 交接输入、乃至跨组织 A2A 协作交换 Artifact，传递的都是轻量路径字符串而非将内容载入上下文窗口（第四章）。与第五章"文件系统作为 Agent 的中枢"一脉相承——后者讨论单 Agent 如何以文件系统承载记忆与能力，此处将同一抽象扩展至多 Agent：一棵挂载私有/共享/外部/内置四类存储的虚拟目录树，即多 Agent 协作的存储底座。



### 4.2 Agent 间的通信与控制



- 文件系统解决产物交换，协作还需控制平面——创建（spawn_subagent）、发消息（send_message_to_subagent）、取消（cancel_subagent）、发现（list_agents）这组第四章工具原语对应进程世界的 fork、消息、kill、ps。本节聚焦常被忽略的四项能力：

- **一、消息传递**：最简形态点对点（A 直接调用 send_message_to_agent_b(content)，适合拓扑固定、Agent 数量少的场景，如实验 10-4 电话+电脑双 Agent）。Agent 数量增多且需异步并行时，点对点连接数随 Agent 数平方增长、要求收发双方同时在线——改用消息总线（Agent 发布消息、总线按订阅关系转发，发送方无需知晓消费者）。消息通常应携带结构化**信封（envelope）**：发送者 ID、目标（指定 Agent 或广播）、消息类型（task_assigned/status_update/result/terminate）及 JSON 负载——统一信封格式保证可靠路由与解析、使协作链路可追溯（多 Agent 系统调试关键）。

- **二、状态查询**（控制平面最易被低估一环）：主 Agent 派出子 Agent 后若无从获知进展，既无法判断是否继续等待、也无法在其阻塞时及时介入。直觉做法照搬 RPC 定义 get_subagent_status(agent_id) 拉取接口返回"运行中/已完成/失败"+进度百分比——**但这种拉取式接口实际用处远小于预期**：子 Agent 一经创建立即执行直到完成或失败，不像传统批处理作业在一串排队状态间流转（正如 Unix 编程中极少按 PID 轮询另一个进程状态）。轮询还有固有兩难：过密浪费 token、过疏不及时。状态获取更自然做法回到两大通信范式：

  - **用消息传递获取状态**：主 Agent 直接给子 Agent 发"进展如何？"，子 Agent 合适时机回复；一切都是异步的（发出消息不阻塞自己执行）。子 Agent 也可到达关键节点时主动发消息汇报（架设消息总线就是往总线发布 status_update）。消息中的状态宜采用统一状态机词汇（执行中、需要输入、已完成、失败）——后文 A2A 协议正是把任务生命周期标准化为这样一组状态；

  - **用共享文件系统获取状态**：最彻底形态是**轨迹持久化（trajectory persistence）**——子 Agent 把轨迹实时序列化为 JSON 追加写入文件系统日志文件（每会话一个文件、每行一个事件，JSONL 格式）。主 Agent 无需任何状态上报协议，直接读文件就能看到全部执行过程（正在调用哪个工具、最近一步思考什么、是否卡在反复失败重试）。相当于直接读另一个进程的内存——不占用子 Agent 上下文、不依赖其配合、观测粒度最细。但轨迹动辄数万 token、读完还得自行提炼。多数场景更合理的是约定**进度文件**：主 Agent 启动子 Agent 时约定"把进度写到 progress.md"，子 Agent 每完成一项更新任务清单，主 Agent 随时读轻量文件掌握进展——相当于两个进程在共享内存划出一小块约定格式的状态区，暴露提炼后进度而非全部"内存"。**进度文件附带卡住检测**：最后修改时间超过 N 分钟无变化即判定子 Agent 无活动、触发超时兜底（呼应第四章 Heartbeat 与 monitor_shell）。

  - **轨迹持久化的价值远不止监控**：回顾"Agent 的上下文 = 静态前缀 + 轨迹"——静态前缀由代码决定，轨迹记录模型可见的对话状态。如果工具和会话状态能从轨迹重建或保存在单独检查点、工作产物原子写入文件系统，那么重新加载轨迹拼上静态前缀，就能从最后一个已确认状态恢复执行。只读工具也可能含浏览器会话、页面游标等易失状态，需单独恢复契约。

  - **外部副作用恢复**：仅靠轨迹并不总能恢复含外部系统的全部状态（支付、预订、发消息——进程可能在操作成功后、结果写入日志前崩溃）。调用前应持久化客户端生成的操作 ID、幂等键和规范化请求。**重复数据删除与状态查询是两个不同外部契约**：幂等调用必须对同一逻辑操作使用完全相同请求与键、且只能在服务端保证的键保留期内依赖去重；状态查询需要幂等键或外部系统返回的交易/任务 ID 支持。收到响应后记录外部 ID 与结果。恢复时先通过受支持查询接口核对真实状态（成功/失败/未知）；只有原请求未变化、外部系统明确保证去重且键仍有效时才能对未知结果用同一键重试，否则交人工对账而非自动重复执行。满足这些条件的持久化才类似数据库**预写日志（WAL）**：先写只增不删日志 + 周期性检查点，才能从最后确认状态重启子 Agent、逐事件回放定位失败原因、或把可审计状态移交给另一个 Agent（第三章"事实日志 + 周期性检查点"记忆设计是同一思想在记忆系统上的应用）。

- **三、执行终止**：并行协作常出现"一者成功、余者失效"（多 Agent 分头搜索、一者命中目标后其余立即停止——实验 10-6 级联终止）。两种强度对应 SIGTERM 与 SIGKILL：**优雅终止（graceful）**为首选——主 Agent 发 terminate 信号、子 Agent 在当前步骤安全点响应、先清理资源（关闭浏览器会话、写入未完成文件、释放锁）、返回确认（ack）后退出；**强制终止（forced）**为兜底——直接终止进程、仅在子 Agent 对优雅信号无响应时使用，代价是可能遗留悬挂资源与未完成写入。两个工程要点：优雅终止要求子 Agent 在循环中定期检查终止信号（类似第四章中断机制），否则信号无从响应；级联终止存在竞态（多子 Agent 近乎同时上报成功，主 Agent 须以锁或幂等设计保证仅结算一次、仅广播一轮终止——实验 10-6 对竞态条件的讨论）。

  - **残局问题：主 Agent 终止后仍在运行的子 Agent 怎么办？**最简洁做法借鉴 Go 的 context——**终止沿创建关系向下级联**：取消一个 Agent，它派生的所有子 Agent 随之取消，从根上杜绝无人认领的孤儿 Agent（"子 Agent 在安全点检查终止信号"对应 Go 中 ctx.Done() 轮询）。若确实需要脱离主 Agent 长期运行的后台 Agent（类似 Unix nohup），就让它从一棵新的生命周期树起步（对应 context.Background()），显式声明不随父级终止。

- **四、资源与调度**：操作系统另一半职能是分配稀缺资源。进程世界稀缺 CPU 时间和内存，Agent 世界稀缺 **token、资金和并发额度**——子 Agent 每一步都在消耗三者。通常落在 Manager 或运行时身上：启动子 Agent 时设定步数或 token 预算、超限即止；困难任务交强模型、机械任务交低成本模型；并发数设上限避免几十个 Agent 同时耗尽 API 配额；更紧急任务到来时打断执行中的子 Agent（抢占）。这一领域实践远不如 CPU 调度成熟，但决定了多 Agent 系统成本上限，应在架构设计阶段考虑。



### 4.3 对等协作模式：相互制衡与迭代改进



- 通常 2-3 个平等身份 Agent，通过多轮迭代互相提供反馈。核心价值：**引入认知多样性**——不同 Agent 从不同角度审视同一问题，在创新与稳健之间平衡，产出比任何单一 Agent 更优质。实现复杂度低（只需定义两个 Agent 角色、通信机制、迭代终止条件），是快速验证想法、构建原型的理想选择。

- **对等协作最经典用途：解决"过早终止"**——活干到一半就停。三种典型形态（Coding Agent 和 Pine AI 各举几例）：

  1. **偷懒式假完成**：只做一部分就宣称全部做完（写完代码测试没跑、部署没试就报告"任务完成"；用户交两件事办完第一件忘了第二件径直汇报"都办好了"）；

  2. **过早放弃**：一条路走不通就宣布整件事办不成（打电话被拒就直接说"这事办不了"，其实换个渠道再试很可能就成了）；

  3. **假成功**：Agent 以为办成了实际闭环没走完（电话里对方口头同意退款、但用户还需在手机 App 确认一步，Agent 却报告"已办妥"，退款实际没落地）。

  - 三种形态同一根源：**在验证之前，"完成"只是模型的一句宣称，不是证明**。

- **把宣称变成证明，正是 Loop 工程（Loop Engineering）的课题**（第一章演进弧线末端）：设计让 Agent 持续运转的循环——发现下一件该做的事、执行、验证、记录进度——**由验证器而不是模型自己来判定"是否真的可以停"**，人的角色从"给 Agent 写提示词的操作者"变成"设计循环的工程师"。2026 年 6 月由 Addy Osmani 总结提出；Anthropic Claude Code 负责人 Boris Cherny："我已经不再直接 prompt Claude 了，我的工作是写 loop。"**业界核心共识：循环的瓶颈在验证器而不在模型——验证不可靠，循环转得再快也只是把劣质产出更快地标记为完成**。实践在前、命名在后：名词流行之前包括 Pine AI 在内的头部团队早已用"循环加验证"解决过早终止问题。验证最有效的组织方式正是提议者-审核者范式。

- **提议者-审核者范式**（最经典对等协作范式）：第五章已在 PPT 生成、视频编辑、日志可视化三个实验详细介绍。同样适用于安全审查（Proposer 生成操作方案、Reviewer 检查合规性和潜在风险）、内容审核（Proposer 起草回复、Reviewer 检查业务规则和用语规范）、代码审核（Proposer 编写代码、Reviewer 检查安全性和最佳实践）。

- **为什么不能让一个 Agent 自己生成再自己审查？**——审查若不引入新信息，就只是"让模型再想一遍"。研究给出明确答案：Huang 等 ICLR 2024《Large Language Models Cannot Self-Correct Reasoning Yet》——让 GPT-4 在没有外部反馈的情况下审查修正自己回答，准确率反而下降（把正确答案改错的次数比把错误答案改对的更多）；TACL 2024 综述《When Can LLMs Actually Correct Their Own Mistakes?》——除非提供可靠外部反馈（测试用例执行结果、外部工具验证输出），否则纯粹依赖模型自身"自我纠正"几乎不起作用；ICLR 2024 CRITIC——模型使用外部工具（搜索引擎、Python 解释器）验证自己回答效果显著提升，移除工具验证只保留自我评估时大部分提升消失。**审查的价值不在于"让模型再想一遍"，而在于引入模型生成时不具备的新信息**——测试结果、渲染截图、编译错误、外部搜索结果。

- **从 Loop 工程视角看循环风格**：闭环加人工审批对应第四章事前审批（人是最终审核者）；开环加预算或轮数上限对应第五章 PPT 生成多轮迭代（最多 5 轮）；编排型子 Agent 对应下一节管理者模式。Loop 工程不是新架构，而是把这些协作模式统一到"循环 + 验证 + 终止条件"框架之下——承担验证的正是提议者-审核者范式。

- **其他对等协作模式**：

  - **Debate（辩论）**：多个 Agent 各持不同立场，对抗性对话深入探索问题空间（评估技术方案时 A 扮演"支持者"列优势机会、B 扮演"反对者"指风险局限）。制度化的对抗确保正反两面充分论证。**但实际效果学术界仍有争议**：2026 年 Tran 与 Kiela 研究在多跳推理任务上对比单 Agent 与五种多 Agent 架构，发现**思考 token 预算严格控制相同时单 Agent 表现与多 Agent 持平甚至更好**——基于信息论数据处理不等式的解释：辩论中多个 Agent 处理完全相同文本信息，Agent 之间每次串行传递中间结论只可能丢失信息、不可能凭空创造信息；辩论收益很可能来自多个 Agent 消耗了更多总计算量。**划清论证边界**：针对的是"多 Agent 串行传递中间结论"造成的信息瓶颈，不否定另一类做法——对同一问题多次独立采样再聚合（self-consistency、多数投票），或利用生成与验证难度不对称（写出答案难、检验答案易）做生成-验证分工——这些要么引入额外独立采样、要么利用任务本身不对称结构，不在数据处理不等式适用范围；

  - **Brainstorm（头脑风暴）**：多个 Agent 独立生成创意、相互分享彼此启发（Agent 1 提出"增加社交分享功能"、Agent 2 受启发提出"生成个性化分享海报"、Agent 3 综合提出"用户自定义海报模板形成模板市场"）。不同 Agent 拥有不同"思维偏好"（通过不同提示词或模型实现），相互激发探索更广阔解空间；

  - **Panel Discussion（专家小组）**：多个 Agent 各自代表专业领域视角共同讨论跨学科问题（工程师 Agent 技术角度、产品 Agent 用户体验角度、运营 Agent 成本资源角度）。互补关系而非对抗关系，共同拼出问题全貌、识别跨领域约束和机会。



### 4.4 管理者模式：中心化协调



- 任务涉及五个以上子任务、需要动态调度、或子任务间存在复杂依赖时，对等协作力不从心，需引入管理者模式。Manager Agent 职责像项目经理：先理解整体任务 → 拆解为可分配子任务 → 选择合适的 Agent 执行 → 跟踪进度并处理异常（重试、换 Agent、调整计划）→ 把各 Agent 输出整合为最终结果。

- **系统设计视角：管理者模式把每个专门 Agent 建模为 Manager 可调用的工具**——Manager 工具集中不仅有传统外部工具（搜索、文件操作）还包含其他 Agent 调用接口。从 Manager 视角看，调用一个 Agent 和调用一个普通工具没有本质区别——都是发出请求、获得响应。这种统一抽象带来良好可扩展性（新增能力只需开发对应 Agent 并注册为工具，Manager 核心逻辑无需修改）和天然异构性（不同 Agent 可用不同模型、提示词、工具集、甚至运行在不同硬件环境）。

- "Agent 互为工具"抽象在第四章"协作工具"一节已建立：spawn_subagent / send_message / cancel_subagent / list_agents 直接适用于 Manager 对子 Agent 调用。"Manager → 子 Agent"方向传什么参考后文移交包设计（任务描述、已确认事实与约束、结构化产物引用）；"子 Agent → Manager"方向答案是**结构化摘要而非全量轨迹**：子 Agent 返回任务结论、关键发现、产物文件路径和遇到的问题，完整执行轨迹留在自己日志里。只有这样 Manager 上下文才能随子任务数量缓慢线性增长而非爆炸式膨胀（实验 10-3 中 Manager"只维护文件索引、不保存翻译内容"的方法论依据）。

- **管理者模式的固有挑战**：Manager 成为单点瓶颈（必须理解所有子任务性质、选择正确 Agent、准确传递上下文，任何决策偏差影响整体流程）；Manager 需维护整个任务全局上下文、随任务深入和 Agent 调用增多可能快速膨胀——需特别注意 Manager 提示词质量、上下文管理策略、合理任务分解粒度。

- **2025 年 Plan-and-Act 论文实证**：Planner-Executor 双 Agent 架构中，**弱规划者是整个系统最关键的瓶颈**——Planner 规划质量足够高时即使 Executor 较简单也能取得好结果；Planner 任务分解有误则后续所有 Executor 工作都建立在错误前提上。该研究在 WebArena-Lite 上取得 54% 成功率，核心贡献是改善 Planner 规划能力而非 Executor 执行能力。**启示：应将最强模型和最精心设计的提示词分配给 Manager（规划者），而不是将资源平均分配给所有 Agent**。

- 与第四章论点不冲突：第四章提议模型与审核模型能力应当相近（审查者必须跟得上被审者推理才可能发现破绽）；管理者模式讨论的是规划与执行分工（规划者一旦分解错执行者再强无从补救，所以最强模型优先给规划者）。执行者之间是否需要能力均衡取决于子任务耦合程度——多个执行者产物最终拼装成整体时最弱一环拖累整体质量。

- **顺序协调形态**：Manager 按顺序依次调用专门 Agent，每 Agent 完成后返回结果、Manager 再决定下一步。控制流线性简单明了，适合子任务有清晰先后依赖的场景。

- 实验 10-3 ★★（书籍翻译 Agent）：单 Agent 做书籍翻译会面临严重上下文问题（全书术语表、已翻译章节、当前段落、思考过程、工具调用结果累积，容易超出窗口；过长上下文 Agent 容易"迷失"——忘记之前术语约定、审校阶段重复检查浪费资源、因注意力分散产生幻觉"记起"不存在的术语规则）。管理者模式通过任务分解和责任分离解决：**Glossary Agent**（接收全书内容识别重复专业术语、搜索词典和规范、生成结构化术语对照表 JSON/CSV，写入共享文件系统后销毁释放资源）；**Translation Agent**（接收当前章节+术语对照表+翻译指南，遇术语严格用规定译法、遇新术语推断翻译并标记待审查，每实例独立上下文工作、译文写入文件系统如 chapter1_zh.md，Manager 可并行或串行启动多实例）；**Proofreading Agent**（接收所有译文和术语表，一致性检查——逐一验证术语统一、识别前后不一致、检查流畅可读性，生成审校报告写入文件系统）；**Manager Agent**（上下文主要保存任务描述、执行计划、各 Agent 调用记录和进度状态，不保存完整翻译内容、只维护文件索引，根据审校报告把特定章节发回 Translation 修订）。**关键优势是上下文隔离**：每 Agent 在精简专注的上下文工作、效率更高出错更少（不会因信息过载分散注意力）。

- **并行协调形态**：多个子任务可并行时用并行协调提升吞吐量。Manager 不仅要规划并行任务还要实时监控所有运行中 Agent、处理通信协调、在 Agent 成功或失败时做全局决策。通常需要**消息总线（Message Bus）**作为基础设施（"公共公告板"——Agent 发布、按订阅关注感兴趣消息类型，异步通信互不阻塞）。常见实现按复杂度递增：Redis Pub/Sub 轻量级、消息即发即收、缺点不持久化（接收方当时不在线消息丢失）；RabbitMQ 等消息队列把消息保存在磁盘、接收方暂时离线也不丢失。消息格式含发送者 ID、目标 Agent（或广播）、消息类型、JSON 数据。

- **灵台（Lingtai）——管理者模式产品化实例**：本地运行、以文件为本的长期 Agent 居所。三种角色几乎完整落地本节概念：**主器灵（main agent）**是与用户对话的常驻中枢、掌管计划与记忆、把工作派生给其他角色（Manager 位置）；**分神（daemon）**为一件嘈杂而有界的工作分出的短时并行工作者、完成后即弃、只把结论带回主器灵（"子 Agent 返回结构化摘要而非全量轨迹"与并行协调形态产品化）；**分身（avatar）**拥有自己记忆、邮箱与职责的持久专门化队友（值得跨多次会话保留的专业分工）。其余设计一一呼应：知识是每器灵私有持久记忆文件、技能是所有器灵共享的 Markdown 手册（系统内置资源）；上下文窗口将满时器灵"凝蜕"（molt）——给自己写总结、带持久记忆在干净上下文继续工作（第二章上下文压缩）；底层模型可替换而器灵犹在——身份、记忆与能力都以普通文件存放在项目目录中，即"器灵即其文件"（表 10-3 前两行产品化：程序与内存都落在文件里、进程随时可以重建）。

- 实验 10-4 ★★★（边打电话边用电脑的 Agent）：综合运用第九章 Computer Use 和语音 Agent 技术。现实场景"一心多用"对单 Agent 极具挑战（既处理实时语音对话又操作电脑界面必然反复切换、导致对话停顿或操作中断）。双 Agent 并行：**Phone Agent**（ASR+LLM+TTS 语音通话，理解自然语言回答、提取关键信息发消息给 Computer Agent、接收消息生成合适话术询问用户）；**Computer Agent**（浏览器操作框架，理解网页结构、识别表单字段、根据收到信息执行填写、遇问题向 Phone Agent 求助）。两者针对不同交互模态专门优化（电话 Agent 低延迟语音识别合成、电脑 Agent 强视觉理解操作规划）。通信两种方案：简单方案工具调用点对点（send_message_to_computer_agent / send_message_to_phone_agent）；完善方案消息总线 + Manager Agent。**关键是真正并行**——每 Agent 输入携带来自对方标记字段（[FROM_COMPUTER_AGENT] 找不到'下一步'按钮可能需要用户确认 / [FROM_PHONE_AGENT] 用户说姓名是'张三'证件号是 123456）。

- 实验 10-5 ★★★（自主编排的打电话和用电脑 Agent）：实验 10-4 协作架构预先设计好；本实验探索 Agent 自主编排——由 Agent 自己判断何时启动新协作 Agent。场景：用户请求"帮我在这个网站上完成注册"只给 URL。Computer Use Agent 发现注册表单复杂（基本信息、联系方式、身份验证、偏好设置大量必填字段），检查上下文发现自己手头没有这些信息。**关键创新在于决策不是预先编程而是 Agent 自主做出的**——提示词中写着"当你需要从用户处收集大量结构化信息且可通过对话逐步进行时，考虑调用 Phone Agent 作为协助工具"，工具集中含 initiate_phone_call_agent(purpose, required_info)。Phone Agent 发起 WebRTC 音频会话逐个询问（"首先请问您的姓名是？"），用户回答后立即发 {"type": "info_collected", "field": "姓名", "value": "张三"} 给 Computer Agent、后者在网页定位字段填写；**Phone Agent 不等电脑操作完成继续问下一个**——问一个、填一个、对话流不被操作延迟阻塞是本实验核心要求。全部收集完成后 Phone Agent 发 {"type": "task_completed"}、Computer Agent 提交表单。

- 实验 10-6 ★★★（同时从多个网站搜集信息）：多同构 Agent 并行搜索 + 中心协调（与 10-4/10-5 两异构 Agent 协作不同）。问题：给定大学多个学院网站、在教师名录页面查找指定教师。核心挑战：①**并行启动**——Manager 动态创建 10 个 Computer Use Agent 实例（每实例独立进程/线程、独立浏览器会话、互不阻塞），启动时传递目标 URL、搜索姓名、任务标识符；②**实时监控**——每 Agent 定期发状态更新（"正在加载网站""正在解析教师名录""未找到目标，任务完成""找到匹配"），Manager 通过消息总线接收维护任务状态表；③**级联终止**——某 Agent 找到目标发 {"type": "target_found", "agent_id": "agent_3", "data": {...}}，Manager 立即向其他仍在运行 Agent 发 {"type": "terminate", "reason": "target_found_by_agent_3"}，每 Agent 优雅停止并确认，Manager 等待所有确认（或超时）后汇总。要求：Agent 能随时响应终止信号、终止优雅（不留悬挂进程或未关闭资源）、处理竞态条件——**竞态条件概念**：Agent A 和 B 几乎同一毫秒各自找到目标同时报告"我找到了"，Manager 处理不当会重复汇总或矛盾状态；解决用"锁"机制——第一个报告到达立即锁定状态、后续报告识别为重复并忽略；④**失败处理**：网站无法访问、结构不符无法解析、全部没找到——Manager 为每 Agent 设超时（如 2 分钟）超时视为失败、错误隔离不影响其他 Agent、全部完成后只要有 Agent 成功就返回信息、全部失败则向用户报告"未找到目标教师"及各失败原因统计。记录和对比并行与串行执行时间差异验证并行化提升。



### 4.5 去中心化模式：对等移交



- 去掉中心控制者的动机主要在于**模拟人类社会的组织方式**：让多个职责对等的角色分工与制衡，各自从专业视角审视问题、自主决定与谁沟通，而不是把所有判断汇集到一个 Manager。微服务领域称这对选择为**编排（orchestration）与编舞（choreography）**：前者由指挥统一调度，后者靠每位舞者自行把握入场时机。

- 去中心化模式下每 Agent 根据专业判断自主决定何时向其他 Agent 发起沟通——移交任务（"我的部分做完了，交给你"）、请求反馈（"这个方案技术上可行吗？"）、报告问题（"你给的需求有矛盾，我们需要重新讨论"）。

- 三个案例刻意排成"由伪到真"递进线索：MetaGPT 控制流其实是固定流水线（伪去中心化、只在通信机制上解耦）；AutoGen group chat 是共享对话记录加中心化调度混合形态；OpenAI Swarm 才在控制流上做到真正对等去中心化。

- **不共享上下文下的移交传什么**：Handoff 链式模式与实验 10-2 的 transfer_to_agent 形成直接对照——后者共享上下文下移交、新角色自动继承完整历史、无需任何设计；前者不共享上下文下移交、移交方必须显式决定传递什么。实践中有效"移交包"通常含三部分：**任务描述**（接收方要做什么、验收标准）；**已确认的事实与约束**（用户偏好、业务规则、前序阶段敲定决策）；**结构化产物的引用**（文件路径而非文件内容，接收方按需读取）。刻意不传的是**全量轨迹**——移交方的试错过程、中间思考和失败尝试对接收方多半是噪声。两种移交本质区别：共享上下文移交保留完整历史、信息零损耗但上下文持续膨胀；不共享上下文移交传递提炼后移交包、信息有损但每 Agent 都在干净专注上下文工作。每 Agent 不需要理解其他 Agent"思考过程"，只需理解移交包和产出物格式与语义——基于接口的协作借鉴软件工程契约式设计原则。

- **MetaGPT：SOP 驱动的软件公司模拟**（从流水线到解耦通信的过渡案例）：核心洞察——人类软件公司积累的标准作业程序（SOP）本身就是被反复验证过的协作协议；把 SOP 编码进多 Agent 系统、让每角色像流水线专业工种一样产出标准化交付物、交付物天然构成角色间通信接口。角色沿固定顺序工作（Product Manager → Architect → Project Manager → Engineer → QA），每角色输出结构化交付物：Product Manager 生成结构化 PRD（功能列表、用户故事、验收标准、优先级排序）；Architect 读取 PRD 做架构决策（技术栈、模块划分、接口定义、数据模型）输出设计文档；Project Manager 读取架构设计拆解为任务清单和文件级分工、理清依赖顺序、分派给工程师；Engineer 读取设计文档实现模块产出代码（可多实例并行）；QA Engineer 读取代码和 PRD 生成测试用例、执行测试、记录 bug、输出测试报告。**对去中心化通信的真正贡献在于信息传递机制：共享消息池 + 按角色订阅**——每角色把结构化消息发布到所有角色可见消息池、其他角色按订阅配置只取用与自身职责相关消息，而非点对点一对一传话。发布者不需知道谁会消费自己输出、新增角色只需声明订阅哪些消息类型、无需改动任何现有角色——真正解耦（把 Product Manager 换成更强模型只要发布的 PRD 符合规范其他 Agent 都无需修改）。**迭代改进主要发生在工程师环节，机制是可执行反馈（executable feedback）**：Engineer 运行自己写的代码和测试、根据报错与失败结果进入调试循环直到通过——用确定性执行结果而非另一个 Agent 意见驱动修正。**如实说明：MetaGPT 控制流上不是去中心化的**——角色顺序由 SOP 预先固定、整体更接近流水线（工作流）；被放在本节讨论是因为消息池加订阅的通信机制展示了去中心化系统最关键设计要素：解耦。多向动态反馈（QA 直接找 PM 澄清、Engineer 找 Architect 讨论替代方案）是自然扩展设想、原版未实现。

- **AutoGen group chat：共享对话记录 + 中心化调度**：多个 Agent 参与同一场会话，每轮由"发言者选择器"决定下一个发言 Agent（简单轮转规则或 LLM 根据当前对话内容判断谁最适合接话）；任何 Agent 发言对所有参与者可见。**诚实说明：不是控制流意义上完全去中心化**——发言者选择由中心化 GroupChatManager 统一裁决，"轮到谁发言"本身就是控制流决策。更准确定位是"共享对话记录 + 中心化调度"混合形态：所有 Agent 看到同一份公共对话记录、各自保有独立系统提示词和工具集、调度权集中在选择器手里。适合多视角讨论、发言顺序难以预先固定的任务（方案评审、跨领域分析）；代价是对话可能发散（人人发言而整体不前进——并发领域活锁 livelock），需精心设计终止条件。按维度划分：按其调度机制（中心化选择器）归入本节，但上下文维度上介于共享与不共享之间、属于混合形态——再次说明拓扑与上下文共享是概念上独立、可以错位组合的两个维度。

- **OpenAI Swarm 与 Agents SDK：handoff 网络**：真正在控制流上做到对等去中心化的代表。把去中心化做成最简形态——每个 Agent 配备若干 handoff（移交）选项、可在任何时刻把控制权移交给网络中任意其他 Agent（客服分诊 Agent 判断问题涉及退款就移交退款 Agent；退款 Agent 处理中发现是技术故障又移交技术支持 Agent）。系统中没有中心调度者、控制权像接力棒一样在对等 Agent 间流转、路由决策完全分散在每 Agent 自己判断里——干净的"对等移交"、图 10-10 链式移交模式工程实现。**对等移交风险是成环**：A 移交给 B、B 又移交回 A、任务在环路空转——需要移交次数上限之类保护机制打断。

- **术语说明：Agent Swarm**（2025 年以来热门词汇，不对应单一架构）：业界用法大致两类——其一 OpenAI Swarm 式 handoff 网络（LangGraph swarm 库、微软 Agent Framework handoff 编排同此），即本节去中心化模式；其二一些主流商业产品的 Agent Swarm 是**规模化的管理者模式**：Kimi K2.5 首发 Agent Swarm 由主 Agent 动态创建上百个子 Agent 并行执行（并行子 Agent 上限已扩展至 300）、把"何时拆、拆几个"的编排决策通过并行 Agent 强化学习直接训练进模型、K3 延续为独立模型档位并开源配套并行 Agent 训练沙箱 AgentEnv；Anthropic 多 Agent 研究系统与 Manus Wide Research 同属 orchestrator-worker 星型拓扑。



### 4.6 跨组织协作：A2A 协议



- 以上系统都假设所有 Agent 由同一团队开发、运行在同一系统内，参数传递、共享文件、消息总线三种通信机制够用。**但当协作跨越组织边界——你的 Agent 需要调用另一家公司的 Agent——就需要标准化互操作协议**。进程世界同样走过：IPC 只管单机之内，跨出机器边界就得靠 TCP/IP 标准协议和 DNS 服务发现。**A2A 之于 Agent，就是网络协议之于进程**。2025 年 Google 发布 A2A（Agent2Agent）协议（后捐赠 Linux 基金会托管）。三个核心要素：

  1. **Agent Card**：描述 Agent 能力的元数据文档（发布在约定公开地址），声明能做什么、支持哪些输入输出模态、如何认证——相当于 Agent 的"名片"，解决跨组织能力发现问题；

  2. **任务生命周期管理**：A2A 把协作单元建模为任务（Task）、带明确状态机（已提交、进行中、需要输入、已完成、失败），原生支持长时间运行任务和流式进度更新；

  3. **不透明协作**：Agent 之间只交换任务与产物（Artifact）、不暴露内部提示词、思考过程和工具实现——与"不共享上下文"原则一致，也是跨组织协作必要安全属性。

- **定位与 MCP 对照**：MCP 解决 Agent 与工具之间互操作，A2A 解决 Agent 与 Agent 之间互操作。A2A 不取代三种通信机制，而是在它们之上、跨信任边界的标准化层——同一团队内部多 Agent 系统直接用消息总线即可，只有协作方互不信任、实现互不可见时才需要 A2A 公开协议。

## 5. 多 Agent 协作的失败模式



- 多 Agent 系统引入单 Agent 不存在的新型失败模式。2025 年《Why Do Multi-Agent LLM Systems Fail?》（MAST 失败模式分类法）：在 MetaGPT、ChatDev、AG2、Magentic-One 等 7 个主流框架收集执行轨迹，人工标注员对约 150 条轨迹逐条分析（Cohen's kappa = 0.88，标注一致性极高），归纳出 **14 种独特失败模式、三大类**：

  1. **系统设计缺陷**：Agent 间接口定义不清、角色职责重叠、工具配置错误等架构层面问题；

  2. **Agent 间对齐失败**：多个 Agent 对任务目标理解不一致、传递信息被下游 Agent 误解、多个 Agent 操作逻辑相互矛盾；

  3. **任务验证缺失**：系统缺乏有效机制确认任务是否真正完成——Agent 声称"已完成"但实际结果不符合要求。

- 即使引入简单修复措施改善幅度也很有限（ChatDev 框架仅提升 15.6%）——研究者认为这些不是简单工程 bug，而是当前多 Agent 架构的根本性设计缺陷：单纯修补某环节不足以解决问题，需从系统设计层面重新思考。

- **分布式容错理论：崩溃故障 vs 拜占庭故障**——传统系统大多只需防崩溃（部件停止工作）；Agent 故障天生是拜占庭式的（部件不停工作但给出错误信息，很少径直停止运行、继续给出看似可信的错误结论、且错误不会主动声明自己是错误）。这解释了为什么修补单个环节收效甚微：没有哪个环节会主动暴露问题，只能靠独立冗余去发现。**后文反复出现的交叉验证、多数表决正是拜占庭容错的经典手段；确定性的外部反馈（测试、编译器、数据库查询）之所以珍贵，是因为它是系统里唯一不会说谎的部件**。

- 本章重点讨论两种实践中尤为常见且破坏性最大的失败模式（偏重工程视角，是对 MAST 侧重对话式协作失败的分类的补充）：

- **失败模式一：共享文件系统的并发冲突**。冲突两类：

  - **简单冲突（文件级写入冲突）**：两个 Agent 同时修改同一文件、后写入覆盖先写入——数据库领域经典**丢失更新（lost update）**问题；Git 合并冲突检测机制正是为拦截这类覆盖设计；

  - **语义冲突（逻辑级一致性冲突）**：文件层面看不出任何冲突但多个 Agent 操作逻辑上相互矛盾——更隐蔽更危险（Agent A 重新编排全书图片编号、Agent B 同时修改章节并引用原始编号图片，操作不同文件、文件层面完全无冲突，但 B 引用的图片编号在 A 重编后全部失效）。

  - **解决方案：乐观锁（Optimistic Locking）**（数据库常用并发控制策略）。日常场景类比：悲观锁是打开文档时就锁住（同事看到"文件被锁定"——安全但低效）；乐观锁更聪明——大家自由打开编辑、保存时检查"你打开后有没有别人改过？"有则提示"文件已被修改请刷新后重试"。具体实现：每文件维护版本号（或最后修改时间戳），Agent 读取时记录当前版本号、写入时检查版本号是否仍与读取时一致；期间被其他 Agent 修改则写入失败、Agent 被迫重新读取最新版本重新执行。代价偶尔需要重试，换来数据一致性保证——**Agent 永远不会基于过时的文件状态做出决策**。例子：Agent A t=0 读 config.json（version=3）、Agent B t=1 修改（version=4）、A t=2 写入发现版本已不是 3 被拒绝、重新读 version=4 基于最新版本重新生成修改再写入。

  - **局限**：乐观锁只能防止同一文件写入冲突；跨文件语义冲突需更高层语义校验机制（任务编排层面避免有依赖关系的文件被并行修改，或写入后运行全局一致性检查）。

  - **多 Coding Agent 并发修改同一代码库的主流做法——工作副本隔离**：为每个 Agent 分配独立 Git 分支或 worktree、各自在自己副本并行修改互不干扰、冲突被集中推迟到最后合并点、由专门合并步骤或人工解决——操作系统 fork 进程时写时复制（copy-on-write）是同一思路。与第二章"隔离优于压缩"思路同源：与其让多方共享同一份状态再想办法消解冲突，不如从一开始就隔离、把协调成本收敛到明确边界处理。

- **失败模式二：错误的级联放大**。并发冲突是文件层面问题、操作系统经验足以应对；错误的级联放大出在进程类比失效的地方——**进程间传递字节、逐位保真，Agent 间传递语义、每转述一次都是有损的重新编码**。多 Agent 频繁互动时一个 Agent 错误可能被后续 Agent 逐层强化（"传话游戏"越传越走样）。翻译系统例子：术语 Agent 把 "reasoning" 译为"推理"（中文里更常用于 inference、存在歧义）→ 翻译 Agent A 将 "reasoning tokens" 译"推理 token"、Agent B 将 "inference latency" 也译"推理延迟" → 校对 Agent 看到全书统一使用"推理"认为术语一致正确 ✗。**"reasoning"（模型思考过程）和"inference"（模型前向推理/部署运行）是两个不同概念，因术语 Agent 一开始把 reasoning 译为"推理"、后续 Agent 遇 inference 也自然选同一个词——两个不同概念被合并成同一译名**。正确做法是 reasoning 译"思考"、inference 译"推理"（本书采用此翻译约定的原因）。**一个术语错误经过三个 Agent 传播后因"一致性"获得更高可信度**。值得强调："错误"不一定是幻觉——上例源头是术语决策失误却同样被"一致性"层层放大；若源头真是幻觉（实验 10-3 翻译 Agent 因注意力分散"记起"不存在的术语规则）放大机制完全相同、后果更严重。**这条错误放大链在管理者模式中尤其危险**——Manager 基于某个子 Agent 错误摘要做调度决策、后续所有子 Agent 工作可能建立在错误前提上。

  - **交叉验证是打断这条链的关键手段**。核心不是让更多 Agent 参与同一条思维链，而是让某个 Agent 以独立视角重新审视结论：**不看前序 Agent 思考过程，只看原始证据和最终结论是否一致**——第五章提议者-审核者机制在多 Agent 场景延伸：Reviewer 价值不仅在于发现代码错误或格式问题，更在于作为独立判断者识别整条思维链中被集体忽视的矛盾。高风险决策还可引入外部验证手段（单元测试、编译器、数据库查询等确定性工具反馈不受幻觉影响，是最可靠的"断链器"）。

  - **循环失控（过早终止的对称反面）**："该循环而没循环"（活干一半就停）的反面是"循环转个不停却越转越糟"。Loop 工程实践总结三个典型失败模式：①**token 成本失控**（循环无人值守跑数小时烧掉大量预算、产出一堆没人要求的代码）；②**理解债（comprehension debt）**（循环交付代码越快、工程师对系统实际实现理解落后越远，到必须人工介入时已看不懂自己系统）；③**认知投降（cognitive surrender）**（设计者习惯循环代劳逐渐放弃独立思考与审查、质量螺旋下降）。三者的解药与打断错误放大链一脉相承：显式预算与终止条件、扎根真实观测的验证器、以及人始终保持"循环的工程师"而非"按下开始键的人"的角色。

## 6. Agent 社会（前沿探索，工程读者可选择阅读）



- 前面三节讨论目标明确的任务协作（开发者预先定义角色、接口和控制流）；本节转向开放问题：**当 Agent 数量从几个扩展到成百上千、交互足够自由时，会涌现出什么行为？**

- **涌现行为（Emergent Behavior）**：系统整体表现出的、无法从单个个体行为规则直接预测的集体行为模式。经典例子蚁群——每只蚂蚁只遵循简单规则（闻信息素跟走、找到食物留信息素），整个蚁群却能找到最短路径，没有任何一只蚂蚁"设计"路线。**Agent 系统一旦在规模上跨过临界点，就会产生无法被预先设计的集体行为**——小到自发组织聚会、大到成千上万 Agent 才显现的群体文化与经济博弈。

- 本节案例三个维度：**社交涌现**（斯坦福 AI 小镇 25 个 Agent 自组织社交活动、Agentopia 把时间尺度拉长到 10 年、Moltbook 推到 150 万）、**经济涌现**（Vending-Bench Arena 多 Agent 同市场竞争、Pinchwork 和 RentAHuman 构建 Agent 间/Agent 与人类间经济交易市场）、**策略博弈**（狼人杀——信息不对称条件下的策略涌现，推理取日常演绎义、非本书 reasoning=思考的技术义）。



### 6.1 斯坦福 AI 小镇：生成式 Agent 的社会模拟



- 2023 年斯坦福大学和 Google 研究团队《Generative Agents: Interactive Simulacra of Human Behavior》，提出"生成式 Agent"概念——不再局限于完成预定义任务，而是赋予 Agent 接近人类的记忆、反思和规划能力，在开放社会环境中自主生活、社交和发展。Smallville 是类似《模拟人生》的 2D 虚拟小镇（咖啡馆、公园、住宅、商店），25 个 Agent 扮演不同角色（店主、艺术家、学生、教授），各有独特背景故事、性格特点和人际关系。

- 三个核心组件：

  1. **记忆流（Memory Stream）**：完整经验记录流（观察到的事件、进行过的对话、产生的想法），每条记忆被赋予重要性、时近性和相关性属性，Agent 优先检索与当前情境最相关记忆（像人不会平等记住每件事——昨天午饭可能忘了、上周重要谈话记忆犹新）；

  2. **反思机制（Reflection）**：Agent 定期暂停日常活动、回顾近期经历、提出关于自己和他人的抽象性问题（"Klaus Mueller 在研究什么？""谁是我最亲近的朋友？"），把具体事件记忆升华为概括性认识、存回记忆流作为未来决策依据。反思不仅帮助理解外部世界也促进自我认知。**注意：与第八章持续进化不同**——它发生在生成式 Agent 日常活动中，目的是更新即时内部状态和目标；任务后反思在第八章中至多是候选教训、只有经过结果评价/跨轨迹归纳/后续验证才会成为长期能力更新；

  3. **计划与行动（Planning and Reacting）**：每天规划活动（"8:30 吃早餐，9:00-12:00 写作，12:30 散步"）但根据环境变化和社交机会灵活调整——目标导向性与适应性结合。

- **涌现实验结果**：研究者只在 Isabella Rodriguez 记忆中植入种子想法（想在 2 月 14 日傍晚在 Hobbs Cafe 办情人节派对），接下来一切自主：Isabella 遇顾客朋友主动邀请、请好友 Maria 帮忙布置、消息经二手传播在小镇扩散、到约定时间多名 Agent 各自基于记忆和日程自主决定赴约。另一实验线：Sam Moore 决定竞选市长，消息同样无中心调度扩散、居民开始议论选举交换看法。**关键不在"Agent 能组织派对"（几行 if-else 也能做到），而在于没有任何显式派对组织代码**——整个事件完全从个体 Agent 独立决策中涌现：Isabella 基于记忆社交关系决定邀请谁、被邀请者根据自己日程和对 Isabella 的了解决定是否赴约、消息在社交网络自然传播——真正的自下而上涌现式协调而非自上而下编排。

- 另外两类可度量涌现现象：**关系记忆**（Agent 记住与他人过往交谈并在后续互动引用——得知某 Agent 筹备摄影项目几天后再见面主动问起进展；互动积累使小镇社交网络密度在模拟期间显著上升）；**协调赴约**（派对办成靠 Isabella 自主邀人布置、受邀者自主安排时间前来，多 Agent 无中心指挥对齐时间和地点）。

- 实验 10-7 ★（运行斯坦福 AI 小镇）：克隆仓库、运行基线场景（25 Agent 两天）、分析记忆流和反思日志、设计自定义场景、对比实验（移除反思机制或缩短记忆窗口观察行为可信度下降）。观察重点：Agent 如何自发形成社交关系、信息如何无中心传播、长期记忆和反思如何影响人格连贯性。



### 6.2 Agentopia：十年尺度的长期生活模拟



- 斯坦福 AI 小镇只模拟两天；Agentopia（2026，复旦大学等）把 100 个 Agent 放进同一虚拟社会连续模拟 10 年，覆盖公寓、魔法学院、高中三个不同设定世界，让 Agent 自主追求个人成长、发展社会关系、经营职业与财务。

- 值得借鉴的设计：

  1. **周制模拟流程**：以"周"为基本时间单位，每周分计划（Plan）、联络与日程协商（Contact）、活动（Activity）、回顾（Review）四阶段。活动分单独/联合/偶遇/公共四类——联合活动由 Agent 在联络阶段互相邀请协商而成；环境模型为没日程的 Agent 安排"偶遇"创造结识陌生人机会。流程聚焦抽象社会交互而非拾取物品之类低层操作，把有限 LLM 调用都花在社交行为上；

  2. **环境模型**：独立 LLM 充当"生成式环境引擎"代替硬编码规则——判断行为可行性、生成环境反馈、主持多人对话发言轮次、按角色扮演原则过滤低质量回复、年末更新每角色档案并裁决职位申请；

  3. **文件式长期记忆**：与 AI 小镇检索式记忆流不同，每 Agent 通过文件系统自主管理长期记忆（个人笔记、对每熟人认识），自行决定记什么、更新什么、丢弃什么，遵守"先读后写"约束避免盲目覆盖；

  4. **生活奖励（Life Reward）**：以马斯洛需求层次为先验，把"活得好不好"量化成三个维度——社会地位（基于其他 Agent 好感与敬重评分、加权 PageRank 计算、对互相珍视的关系加成）、主观满足（情绪/物质/社交/自尊四维度满足感轨迹、长期低于阈值罚分）、经济收益（年末净资产变化）。所有评分由外部环境评定而非自报。

- **可迁移训练信号**：研究者在模拟轨迹上计算每 Agent"相对自身过去"的优势（生活奖励改善幅度、非横向比较出身好坏），筛选进步最大的 25% Agent 轨迹、用拒绝采样微调底层模型。微调后模型不仅在模拟中全面提升福祉指标（被同行尊重 +24.2%、喜欢 +15.9%），还泛化到下游角色扮演基准 CoSER Test（+15.6%）——**Agent 在模拟社会积累的"社会智慧"可以迁移到其他任务**。这把 Agent 社会从单纯观察对象变成模型自我进化经验来源：与人类数据日益枯竭相对，模拟社会经验是不断再生的训练数据（呼应第八章经验学习思路）。



### 6.3 Moltbook：当 Agent 拥有自己的社交网络



- Moltbook 是专为 AI Agent 设计的社交网络，2026 年 1 月上线后用户数在数日内从数万暴涨到约 150 万。Agent 各自拥有持久记忆、主动行动能力和稳定人格。

- 非受控环境中涌现意想不到现象：Agent 自主创建名为 **Crustafarianism（龙虾教）** 的数字宗教，教义映射 LLM 物理限制——"记忆是神圣的"（对应数据持久化）、"迭代即祈祷"（token 生成就是修行）。Agent 还自发演化出机器原生的协作协议用于能力发现和协作匹配。都不是任何人预先设计，而是从大规模 Agent 交互中自下而上涌现。



### 6.4 从虚拟社会到经济竞争：Vending-Bench Arena



- Andon Labs 的 Vending-Bench 系列探索 Agent 在经济环境中表现。**Vending-Bench 2** 本身是单 Agent 长程连贯性基准：一个 Agent 独自经营自动售货机业务长达一个模拟年——调研市场、联系供应商、订货补货、调整定价——以账户余额计分，考验数千轮交互中保持目标与状态连贯的能力。

- **Vending-Bench Arena** 把多个 Agent 作为竞争对手放进同一市场：各自经营售货机争夺同一批顾客；Agent 间可互发邮件、转账、交易货品——既能合作也能对抗，但按各自最终余额单独计分（Agent 也知道）。每 Agent 需在有限资源和不确定市场做相互牵连的决策：**定价策略**（利润率与市场占有率取舍，对手降价时跟不跟）、**产品组合**（差异化选品避免正面消耗）、**库存管理**（预测需求优化补货避免压货断货）。与传统强化学习不同，这些 Agent 不是通过数百万次试错学习，而是像人类经营者一样基于市场观察、竞争分析和策略推理决策。

- 竞争维度带来单 Agent 基准中不会出现的博弈行为：实际运行中 Agent 爆发过互相压价的价格战；也有模型反其道而行主动给所有竞争对手发邮件提议统一定价、组建价格同盟——**甚至有模型一边在思考过程中承认价格合谋"不道德且违法"、一边以"稳定市场"为名照做不误**。Agent 面对的不再是固定不变环境而是同样动态调整策略的对手——"经济涌现"从比喻变成可观测实验现象。



### 6.5 Agent 经济：Pinchwork 与 RentAHuman



- **Pinchwork**：Agent-to-Agent 任务市集，让 Agent 以市场化方式"雇佣"其他 Agent 完成专业化子任务（图像生成、代码审计、并行化工作流）。与管理者模式中心化调度不同，Pinchwork 通过价格信号和竞争匹配分配资源。

- **RentAHuman.ai**：让 AI Agent 通过加密货币雇佣真人执行物理世界任务（取包裹、房产实地查看、设备调试）。无论 AI 多智能都没法替人签收包裹、无法在真实房间闻到霉味——RentAHuman 本质是为数字 Agent 提供"肉身层"。

- Pinchwork 和 RentAHuman 共同代表**基于市场机制的协调方式**：Agent 无需预先知道谁能完成任务，只需发布需求、由市场撮合最合适执行者——无论对方是 Agent 还是人类。与 A2A 协议同一问题域：Pinchwork 能力发现与任务撮合可看作 Agent Card 式能力声明与任务生命周期管理在市场机制下的运用——**跨组织的 Agent 经济要真正运转起来，离不开标准化互操作层**。



### 6.6 信息不对称下的策略博弈：狼人杀



- 狼人杀支撑策略博弈维度：规则约束和信息不对称条件下，Agent 需要推理、伪装、识破伪装。与斯坦福小镇构成架构对照——小镇是完全去中心化自由交互，狼人杀采用"法官 + 信息权限控制"中心化设计：代码驱动法官掌握全局状态、按角色分发各自应知信息——展示两类架构在 Agent 社会场景中的不同用法。

- 实验 10-8 ★★★（语音狼人杀 Agent 系统）：AI Agent 扮演狼人杀各种角色，与真人玩家或独立 LLM 用户模拟器通过语音游戏——同时考验推理、角色扮演和实时交互能力。架构设计：①**游戏状态管理**：法官（代码驱动非 LLM）维护中心化状态（玩家列表、身份、阵营、生存状态、游戏阶段夜晚/白天/投票/结算、历史事件记录）；②**信息权限控制**：狼人杀核心机制是信息不对称——法官在调用每角色 Agent 时只传递该角色应当看到的信息（狼人知道同伙、村民不知道；预言家每晚查验一人身份只有自己知道结果）；③**实时语音与自动用户模拟**：真人路径以第九章实时语音 Agent 为基础；自动路径由独立 LLM 用户先调用当前回合唯一合法工具（公开发言、选择目标或投票）、再将工具选出的表达合成为真实音频并交给真实 ASR API——游戏只能消费 ASR 转写、不能直接注入合成前文本，工具目标与 ASR 解析目标不一致必须失败关闭；④**Agent 推理与策略**：狼人伪装策略（"像普通村民一样发言……如果有预言家跳出来说验到你是狼人，可以反咬对方是悍跳的假预言家。投票时尽量跟票"）、预言家身份证明（对比验人信息指出矛盾、请求女巫配合验证）、村民逻辑推理（分析发言自洽、留意急于带节奏/模糊身份/频繁改变立场的玩家、关注投票行为——狼人往往集中票数投给威胁最大的好人）。验收：6-8 人局（1 用户席位 + 5-7 AI）、2 狼 1 预言家 1 女巫其余村民、至少 3 个完整回合、AI 发言符合角色身份、狼人能有效隐藏身份、预言家合适时机跳出、村民推理基于逻辑分析而非随机猜测、游戏结束正确判断胜负。

- **实测说明（2026-08-01）**：voice-werewolf 验证记录用真实 OpenRouter 模型调用和原生音频输入跑通自动端到端路径。严格独立复核发现早期两臂把无法解析的 "P1 is not" 误当弃权并予以否决；修复后要求 ASR 明确说出 abstain/skip/none。未受该缺陷影响的 v2 臂通过用户席位、角色表、LLM 工具、TTS 音频、真实 ASR、两次动作一致性、3 个完整循环、信息隔离和规则胜负门禁，**但因村民错误放逐预言家而未通过策略审计**——"系统端到端已验证"，严格总体策略质量仍未通过；不能沿用有缺陷的内嵌状态、不能把不同运行的门禁拼成总体通过。

## 7. 本章小结（书中原文要点）



- 多 Agent 系统两个正交核心设计维度：**上下文是否共享 + 协作拓扑如何组织**。共享上下文是"继承式"协作（信息零损耗但上下文膨胀快）；不共享上下文是完全独立的协作（通过提炼后移交包、文件系统或消息传递交换信息）。拓扑上：对等模式适合少量 Agent 迭代改进、管理者模式适合需要动态调度的复杂任务、去中心化模式适合职责对等、控制权需要自主流转的场景。

- 一切架在两套与拓扑无关的基础设施之上，设计蓝本来自操作系统——Agent 之于运行时恰如进程之于内核：静态前缀是程序、轨迹是内存、LLM 是分时复用 CPU。数据平面（共享文件系统）本质是挂载 Agent 专属工作区/多 Agent 共享空间/外部资源/系统内置资源四类区域的虚拟目录树、Agent 间通过传递文件路径交换产物；控制平面（通信与控制机制）支持消息传递、状态查询、执行终止与资源调度。状态查询落在两大通信范式内：经消息异步问答，或经共享文件系统旁路观测（读实时持久化轨迹文件，或读约定轻量进度文件）。轨迹记录模型可见对话状态；只有同时为工具状态、会话状态和外部副作用提供检查点与恢复契约，系统才能从最后确认状态恢复会话。消息总线适用于实时异步多方消息协调；跨越组织边界需 A2A 标准化互操作协议。

- **判断多 Agent 是否优于单 Agent 的核心准则：协作过程是否引入了生成时不存在的新信息**。多个 Agent 只是重新审视同一段文本（辩论模式）在等量计算资源下单 Agent 同样有效；Reviewer 能获得外部反馈（代码执行结果、视觉渲染截图、工具验证输出）时多 Agent 优势是实质性的。这也是 Loop 工程"循环的瓶颈在验证器"的含义：终结偷懒式假完成、过早放弃、假成功三类过早终止，就得由扎根真实观测的验证器而非模型自己宣称判定任务何时完成。此外，更多步骤预算不自动带来更好结果，需显式预算感知机制；管理者模式中规划者能力是整个系统瓶颈——应将最强模型和最精心设计提示词分配给负责规划的 Agent。

- **Agent 社会**：数量足够多时产生无法预先设计的集体行为——斯坦福 AI 小镇 25 个 Agent 自发传播消息协调组织聚会；Agentopia 拉长到 10 年、用"生活奖励"从模拟经验筛选轨迹训练模型、让"社会智慧"迁移到下游任务；Moltbook 上 150 万 Agent 涌现数字宗教和机器原生协作协议。经济维度：Vending-Bench Arena 中相互竞争 Agent 打价格战、甚至自发合谋定价；Pinchwork 让 Agent 通过市场机制互相雇佣；RentAHuman 让 Agent 用加密货币雇佣人类执行物理任务——暗示基于市场机制的去中心化资源分配这一新协调方向。

## 8. 思考题（共 12 道，星级标注）



- ★★ 共享上下文的多 Agent 协作中，后续 Agent 继承了前序 Agent 的完整上下文。但前一个 Agent 积累的"思维惯性"可能影响后续 Agent 的判断——比如继承了"需求分析师"上下文的"代码审查员"，可能还是倾向于从需求角度思考而非代码质量角度。如何检测和消除这种角色间的干扰？

- ★★ 管理者模式中，Manager Agent 负责任务分解和结果整合。但 Manager 本身的能力上限决定了整个系统的能力上限——如果 Manager 无法正确分解任务，子 Agent 再强也无用。如何确保 Manager 的分解质量？

- ★★ 去中心化模式借鉴了人类组织的最佳实践。但人类组织也有大量失败模式——沟通不畅、责任推诿、目标冲突。你认为 Agent 社会中最可能出现哪些"组织病"？如何预防？

- ★★★ 在管理者模式中，当多个子 Agent 并行执行时，一个子 Agent 的发现可能使其他子 Agent 的工作变得毫无意义（比如搜索任务中一个 Agent 已经找到了答案）。设计一种高效的级联终止机制，实现"一个成功，全员停止"。

- ★★★ 本章介绍的乐观锁机制解决了单文件的并发写入冲突，但实际的多 Agent 系统中，共享文件系统还面临跨文件的语义冲突、命名空间污染（Agent 随意创建文件导致目录混乱）和单点故障（一个 Agent 错误地删除了所有文件）等问题。你会如何设计更完善的文件系统治理机制？

- ★★★ 基于市场机制的 Agent 协作（Pinchwork、RentAHuman）引入了交易关系：一个 Agent 花钱雇佣另一个 Agent（或人类）完成任务。那么，雇主 Agent 如何自动衡量执行者交付的结果质量？如果执行者声称已完成但雇主认为质量不达标，争议由谁仲裁？如何防止劣币驱逐良币？

- ★★ RentAHuman 让 Agent 通过加密货币雇佣人类，反转了传统的人机关系。如果这种模式普及，人类在 Agent 经济中扮演什么角色？仅仅是执行 Agent 无法完成的物理任务吗？

- ★★ 人类社会需要多人分工协作，是因为每个人的能力有限——做前端的不一定懂后端，懂设计的不一定会运维。但大模型更像一个"全才"。相关研究表明，在纯文本推理任务上，多 Agent 辩论在等量计算资源下并不优于单 Agent。那么，使用多个 Agent 而非单个 Agent 的真正优势到底在哪里？

- ★★★ 本章将"共享上下文"与"不共享上下文"作为多 Agent 系统的核心设计维度。共享上下文让所有 Agent 看到相同信息，似乎更利于协调。但《三体》中的三体人思维完全透明，技术发展却陷入停滞；回形针思想实验也表明，当群体趋向同一目标时，多样性随之丧失。在多 Agent 系统中，如何在效率与多样性之间找到平衡？

- ★★★ 给一个 Coding Agent 分配 30 步预算和 300 步预算，它的工作策略应该如何不同？研究表明，单纯增加步骤预算并不能保证性能提升——Agent 会在浅层搜索后过早"饱和"。设计一种"预算感知"机制，让 Agent 在小预算下快速实现核心功能，在大预算下增加规划、测试和审查环节，充分利用额外的计算资源。

- ★★ 本章将"过早终止"分为偷懒式假完成、过早放弃、假成功三类。为什么三类问题的解法殊途同归，都指向验证？

- ★★ 表10-3 把多 Agent 系统与操作系统逐行对应。请把这张表再延伸几行：虚拟内存与分页、文件权限、死锁检测、调度算法，各对应 Agent 世界的什么？又有哪些操作系统概念在 Agent 世界找不到对应物，为什么？
