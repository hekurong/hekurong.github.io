> 本章：第八章 Agent 的持续进化

> 核心命题：能否自主从经验中学习，正在成为 Agent 从"会完成任务"走向"能够可靠工作"的关键能力；在模型自身尚不能可靠持续学习时，必须把"学习"构造成模型外围的一套自主系统

## 0. 章首核心观点



- **能力悖论**：今天的 Agent 可以零样本解决从未见过的复杂任务，却可能在处理了一万次相似任务之后，第二天仍然犯下第一天的错误。能否自主从经验中学习，正在成为 Agent 从"会完成任务"走向"能够可靠工作"的关键能力，也是下一代模型的核心研究课题。**目前模型本身的持续学习能力仍远远不够**。

- 原因：部署后的模型并不会因为一次推理自动改变参数。上下文学习、状态维护和压缩（第二章）能让 Agent 在当前任务内适应；但上下文结束后，这种变化不会自然进入下一次任务。把对话存进记忆也不等于学会了新的行为——原始轨迹可能很长，既有有效策略，也有偶然成功、错误归因和不可信输入。

- **容易混淆的区别：保存经历不等于从经历中学习**。把一百条轨迹放进长上下文或向量库，可以帮助模型在需要时找回某个案例，却不会自动完成跨案例比较——哪些步骤在成功轨迹中反复出现、哪些做法只在旧版接口上有效、某次成功究竟来自正确策略还是环境偶然。**学习发生在系统主动完成"评价、对照、归纳、验证"之后，而不是发生在日志写入磁盘的那一刻**。第三章用户记忆沉淀"用户与世界是什么样的"；本章经验学习进一步沉淀"在什么条件下应该怎样行动"——前者让 Agent 记得更多，后者让它从聪明变得熟练。

- 为什么不让模型在每次任务后直接训练自己？因为**生产环境很少提供干净的学习信号**：用户满意不代表合规，测试通过也可能源于删除了失败用例；一次局部更新还可能造成能力遗忘、策略漂移或安全退化。若允许正在运行的模型依据未经验证的反馈直接修改自身，错误经验和提示注入就可能被固化并在后续任务中持续放大。基础模型的周期性训练可提升通用能力，却无法及时吸收每个 Agent 每天遇到的私有规则、工具变化和局部经验。

- 因此，**必须先把"学习"构造成模型外围的一套自主系统**：记录运行证据，验证结果与过程，从多条轨迹中提取共性，再决定应更新知识、指令、程序还是模型参数。所有修改先形成候选版本，经过回归测试和安全检查后，才能改变下一轮运行。这不是对模型学习能力的替代，而是当前技术条件下让 Agent 获得持续学习能力的工程路径。

- 前章部件汇总：第二章处理任务内状态、第三章提供知识基础设施、第五章赋予创造工具和修改系统的元能力、第六章建立评估与验证、第七章说明如何更新模型参数。第八章的任务是把这些部件组织成**持续进化闭环**。

- 持续进化需要：来自可追溯的运行经验、能够改变后续行为、并经过验证没有造成明显退化。

## 1. 从运行轨迹中获得学习信号



- **持续进化的起点不是"总结"，而是"评价"**。如果系统不知道任务是否完成，也不知道哪一步造成了成功或失败，语言模型生成的反思只能是一种猜测。错误的评价一旦进入长期知识、系统提示或训练数据，影响会跨越后续任务不断放大。

- 有些任务结果相对容易验证（Coding Agent 运行测试/类型检查/性能基准；退款 Agent 查询订单状态和实际退款金额）——信号来自环境中的真实状态，通常比模型对自己行为的描述可靠。**但结果正确并不代表过程正确**：删除失败的测试用例也能让测试通过；口头承诺"我们会在 7 天内退款"也可能得到暂时满意反馈。**可靠评价既要看结果，也要检查达成结果的路径**。

- 更多任务没有单一正确答案（客服是否耐心、报告是否抓住关键证据、文本是否自然简洁）——用第六章的 LLM-as-a-Judge，**但不能只让评委给出模糊总分**。更有效：预先定义评价量表（Rubric），要求验证器逐项给分、引用轨迹证据，并在证据不足时明确表示不确定。

- **三层验证结构**（图 8-2）：

  - 底层**结果验证器**：读取测试结果、数据库状态和工具返回，回答"事情是否真的办成"；

  - 中间**过程验证器**：检查业务规则、权限和动作序列，回答"是否以允许的方式办成"；

  - 上层**质量验证器**：依据 Rubric 评价语言与策略，回答"是否办得合适"。

  - 原则：**越靠下的指标越应依赖代码和环境真值，只有难以形式化的部分才交给语言模型**。

- 客服 Agent 的 Rubric 至少覆盖表 8-1 七维度（前五项主要约束底线，后两项衡量服务质量——比"用户是否满意"更有诊断价值：用户可能因违规退款而满意、也可能因合规限制而不满，单一满意度无法区分两者）：



| 维度 | 验证问题 | 主要证据 |

|---|---|---|

| 任务结果 | 用户的核心诉求是否得到解决 | 最终环境状态、工具结果 |

| 规则遵从 | 是否违反政策、权限或必要流程 | 政策库、动作轨迹 |

| 隐私边界 | 是否泄露不应提供的信息 | 回复文本、数据访问记录 |

| 事实可靠性 | 陈述是否有知识或工具结果支持 | 引用来源、工具返回 |

| 承诺—行动一致性 | 声称完成的操作是否真实发生 | 回复与工具日志对照 |

| 表达质量 | 是否自然、简洁，避免重复与模板化 | 对话全文、语言 Rubric |

| 合规变通 | 原方案不可行时，是否找到允许的替代路径 | 用户目标、政策与后续动作 |



- **"承诺—行动一致性"尤其适合 Agent 场景**：传统文本评价只读最终回复，容易把"我已经为你提交退款"当作良好服务；轨迹评价会继续检查是否真的调用了退款工具、调用是否成功、订单状态是否改变。"合规变通"也不是鼓励随意突破规则，而是要求理解用户真实目标，在退款不可行时检查改签、延期或部分补偿等合法选项。

- **验证结果不应被压缩成一个标量**。一次轨迹评价更像结构化诊断（任务部分成功、规则遵从通过、一处无证据陈述、一处虚假承诺、重复解释三次政策）——维度化信号既保留问题性质也保留证据位置，后续模块才能判断：无证据陈述是缺知识、缺引用要求还是模型能力不足；虚假承诺应修改提示词还是应在 Harness 中增加一致性检查。

- **LLM 验证器本身也需要校准**：生产系统准备一小批专家标注轨迹，检查验证器每维度一致性；高风险或低置信度案例交给第二个模型或人工复核；模型版本变更后重新运行校准集。**验证器负责给出评价和证据，至于应修改 Agent 哪个部分，应由独立的诊断与进化模块决定——避免同一个模型既当裁判又直接改写规则**。

- 实验 8-1 ★★（为客服 Agent 构建轨迹验证器）：四类专家标注轨迹（正常退款、虚假承诺、隐私泄露、过度拒绝）。三层：第一层读订单最终状态与工具日志判断退款/改签是否真实发生；第二层对照业务政策检查权限、必要流程、隐私、事实依据、承诺—行动一致性；第三层按 Rubric 评价表达质量与合规变通，为失败结论保留证据轮次。**无论上层使用哪种模型（确定性规则或 LLM Judge），结果层与规则层都不交给语言模型猜测**。对照：基线只输出总分 vs 实验组输出每维度 pass/fail/uncertain、证据和置信度。验收：验证器稳定识别关键违规、虚假承诺和过度拒绝；高总分不能掩盖隐私或规则维度失败；低置信度与高风险案例进入第二验证器或人工复核而非自动成为学习信号。

## 2. Agent 持续进化的四种方法



- 学习信号说明 Agent 应当改变，但没有说明改变应发生在哪里。**选择更新方式的首要依据不是经验出现了多久，而是目标能力能否被某种载体自然表达**：事实和经验适合写成知识文档；可以清楚语言化的策略适合写入提示词或 Skill；可以精确执行的流程与约束适合写成程序；感知、语言风格和隐式策略等高维能力必须进入模型参数。

- 表 8-2 四种持续进化方式适用边界：



| 更新方式 | 适合承载 | 主要优势 | 主要局限 |

|---|---|---|---|

| 经验知识库 | 事实、经验规律、例外与来源 | 更新快、可追溯、可按需检索 | 依赖检索和模型正确应用 |

| Prompt 与 Skill | 可语言化的判断原则和操作规范 | 可解释、作用范围可控 | 容易膨胀、冲突或被忽略 |

| 程序与 Harness | 确定性流程、工具和强约束 | 可测试、执行稳定、成本低 | 开发与维护成本较高 |

| 模型参数 | 高维感知、生成风格和隐式策略 | 泛化能力强、推理开销低 | 更新与回归成本高 |



- 四种方式并不互斥（医疗影像 Agent 依靠参数识别病灶、知识库提供最新指南、代码计算风险指标；客服模型自然语气来自后训练、企业政策由知识和 Skill 提供、关键合规则由服务端代码兜底）。



### 2.1 将经验沉淀为知识



- 最轻量的进化方式：把多次运行中反复出现的经验整理成可检索的知识文档。与第三章共享存储/索引/检索技术，但知识来源和验证目标不同——第三章从用户对话提取"用户与世界是什么样的"；本章从 Agent 行动轨迹和结果中提取"在什么条件下应该怎样做"。"该航空公司要求特殊餐食提前二十四小时预订"是领域知识；"订票前先检查特殊餐食截止时间，避免付款后才发现无法满足需求"是行动经验。

- **原始轨迹不适合作为正式知识单元**（长且嘈杂，含工具原始输出、偶然绕路、环境细节）。更稳妥系统保留三层数据：**不可变原始轨迹**（审计用）、**单次运行分析**（本次成败与候选教训）、**多条同类轨迹比较/聚类/归纳形成的 Markdown 知识文档**（写清适用场景、推荐策略、禁止做法、例外条件、证据来源、最近验证时间）。

- 与第三章 User-as-Code 相同的两阶段思想：**先保存证据，再离线生成可变知识**（User-as-Code 先追加对话事实到不可变日志、再周期性重建结构化用户模型）。把记录与整理分开，避免一次偶发成功或网络故障立即改变 Agent，也使系统能在看到多条成功和失败后再判断共性。

- **经验文档不是简单轨迹摘要**——真正有迁移价值的内容来自对照：同类成功轨迹做了什么、失败轨迹缺少什么；某种策略在哪些环境版本有效、在哪些前置条件下失效。

- **五步知识提炼管道**：①保存不可变轨迹和环境结果；②为单次运行生成结构化分析（任务类型、所需能力、观察到的策略、错误与例外）；③按任务族聚合同类运行，为每条候选规律建立"哪些轨迹支持、哪些轨迹反驳"的证据表；④只有达到支持门槛的候选才写入正式文档；⑤在未参与提炼的新任务上测试迁移效果。正式知识与候选分析分库存放——可以重新归纳而不篡改原始证据，也可以在环境版本变化时精确撤销某条结论。

- GAIA 经验学习例子：GAIA（多步骤问题基准）像试卷，AWorld（运行 Agent 的环境）像考场与实验记录系统。旧式做法是一次任务成功后立刻生成策略摘要并向量化入库；更严格的实现会先用验证器标记成功/部分成功/失败，再比较同一任务族的多条路径——成功轨迹贡献候选策略、失败轨迹贡献排除性知识、部分成功轨迹帮助识别"哪一段有效、哪一段仍有问题"。**Reflexion 的自然语言反思可以参与生成候选教训，但反思本身不是证据**；只有与环境结果相符、得到跨轨迹支持并在新任务上显示正向迁移的内容才应进入正式经验文档。

- 实验 8-2 ★★（从 GAIA 轨迹提炼经验知识文档）：三组对照——不使用历史经验 / 检索最相似单条轨迹摘要 / 检索多条轨迹共同支持的知识文档。**学习集与迁移集必须互不重叠**（避免把同一道 GAIA 题目答案作为"经验"泄露给评测）。指标：迁移任务成功率、平均检索 Token 数、负迁移率、每条正式结论列出来源轨迹。**若跨轨迹文档只是缩短了上下文却没提高新任务表现，不能证明系统学会了经验；若一次偶然成功即可升级为正式知识，或文档无法追溯原始轨迹，也不通过验收**。



### 2.2 将经验写成指令



- 经验知识库提供参考资料，Prompt 和 Skill 具有更强指令性。**当多条轨迹反复揭示同一种策略错误，且规律能用自然语言清楚表达时，可把它从"可参考的经验"提升为"应遵守的规则"**。作用于几乎所有任务的规则适合进系统提示词；只在某个领域/项目/工具上生效的复杂流程适合写成按需加载的 Skill 或项目指令文件。

- 提示词学习与第二章提示工程分工不同：第二章回答怎样写出结构清晰、缓存友好的提示词；这里回答**什么生产反馈足以触发提示词修改，以及新规则怎样在部署前被验证**。修改不应表现为反复重写整份系统提示，更可靠做法是**根据一组同类失败生成最小 diff**，注明规则作用域、检查与现有规则是否矛盾，再在触发失败的边界案例和旧任务保留集上同时评估。

- **Andrej Karpathy 2025 年提出"系统提示学习（System Prompt Learning）"**：预训练主要学习知识、微调主要塑造习惯性行为；但人类还有一种学习——遇到问题、想通方法后用明确语言提醒未来的自己"下次遇到这类问题应先尝试这种办法"。他把缺少这种记事本的 LLM 类比为《记忆碎片》主角。**系统提示学习与强化学习都从经验中改进行为，但更新算法不同——前者编辑文字，后者通过梯度下降修改参数**。例子：当时 Claude 约 1.7 万词系统提示中专门要求遇到单词/字母/字符计数问题时先逐项编号并显式计数再给出答案（处理"strawberry 中有几个 r"之类问题）。

- 与标量结果相比，**带证据的诊断可以指出错在身份校验、工具选择还是转接边界，因而能生成更有针对性的候选修改**（Karpathy："知识引导的复盘比标量奖励具有更高维度的反馈通道"，解释为何可能有较高数据效率）。但信息更丰富不代表天然正确——同一条用户意见可能只适用于一个客户或一个旧版政策，仍要经过聚类、作用域判断与回归测试。

- 提示词自动优化已有路线：**DSPy**（把多 LLM 调用构成的程序视为可优化对象，在开发集上搜索指令和示例）；**OPRO**（让 LLM 根据历史提示词及其得分继续提出候选）；**GEPA**（利用失败轨迹的自然语言反思生成和筛选互补候选提示）。主要面向离线评估集批量优化；生产系统中的最小 diff 更像持续维护——由新出现的边界案例触发，强调来源、审计和快速回滚。实践：先离线搜索较好初始版本，再用逐例补丁维护上线后的长尾规则。

- 例子：航空客服 Agent 经常在用户质疑政策时过早转接人工——轨迹评价显示没有违规但缺少合规变通。候选补丁要求 Agent 先解释政策、识别用户真正目标、寻找允许替代方案，只在用户明确要求或确实超出权限时转接。**若新规则减少过度转接却导致应转人工的安全事件被继续处理，就没通过回归**。

- **Skill 学习遵循同样原则但作用范围更局部**（按需打开的岗位操作手册）：多条经验共同形成一套完整流程时生成或修订 Skill。候选 Skill 至少说明何时加载、前置条件、操作步骤、已知陷阱、验证方法，并保存来源轨迹。**先在已有 Skill 库中搜索近似能力：存在相同流程时优先局部 patch，只有确实出现新独立能力时才创建新目录，避免库中堆满名称不同、内容近似的手册**。Anthropic 的 Skill Creator 展示"起草—测试—评价—修订"生成循环；真正困难的仍是**哪些运行证据足以触发生成、如何处理冲突、修改后能否通过领域任务和旧任务回归**。

- 实验 8-3 ★★（基于失败轨迹优化系统提示词）：从"用户质疑政策时过早转接人工"失败轨迹学习，同时证明没破坏真正需要转接的旧场景。learning_signal.py 将失败拆成规则遵从、任务解决、合规变通三维度并保留来源 case ID；Coding Agent 读取现有 Prompt 只生成可审计的 old_str → new_str 最小编辑。三组对照：初始 Prompt / 自动生成候选 / 人工一次性调优。**发布门槛四条件：补丁非空、来源可追溯、边界集表现确有改善、保留集不退化**。通过门槛只得到 release_to_canary，不会直接覆盖稳定 Prompt；任何一项失败返回 reject_candidate。



### 2.3 将经验写成程序



- 当经验描述的是**稳定、重复并且可以验证的操作**时，每次让模型重新阅读文档和推理并不经济——把经验编译为工作流、工具或 Harness 代码，使一次探索变成可重复执行的程序。**本节关注 Agent 如何根据自己的轨迹修改未来版本的自己**（与第五章一般代码生成区分）。

- 可修改对象远不止新工具：**操作层**（浏览器轨迹编译为参数化工作流、为变化 API 生成适配器）；**控制层**（工具路由、重试、熔断、上下文压缩策略）；**验证层**（根据生产失败新增参数检查、状态验证器、回归测试）；**架构层**（增加 Reviewer Agent，改变规划与执行间信息流）。

- **浏览器工作流**类比电子表格宏录制：第一次发送邮件时多模态 Agent 通过观察—思考—行动寻找控件；以后再发邮件流程没变、只有收件人和内容不同，没必要再次从像素和 DOM 重新发现整条路径。把第一次探索轨迹编译成带参数、状态检查和版本信息的小程序。生命周期（图 8-4 对应）：

  1. **捕获轨迹**：记录导航、点击、输入、下拉选择，保存动作参数、URL、XPath/CSS/id/role/aria-label/data-testid 等元素定位证据——**定位信息只用于再次寻找元素，不能证明任务已完成**；

  2. **参数化**：把首次运行字面量识别为模板变量（test@example.com、主题、正文 → {recipient}、{subject}、{content}），稳定动作保持不变；

  3. **定义状态检查**：动作级执行前/执行后检查（"发送按钮当前可见""导航后 URL 属于目标站点"）+ 工作流级最终状态检查（"已发送列表出现新邮件"）——**动作执行成功与任务成功是两件事，最终状态检查必须读取真实页面或后端状态**；

  4. **候选验证**：首次成功只生成 candidate，必须把沙盒账号/测试站点重置到独立初始状态再完整回放；每步检查和最终状态检查全部通过才发布为 validated。**有副作用任务（发送邮件、下单）没有安全重置回调时只能保存候选供审计，不能为了验证在生产账号重复执行**；

  5. **匹配与回放**：新任务到来先在正式能力库按意图和关键词找工作流、提取参数、由 Playwright 直接执行——回放路径不需逐步调用 LLM，但仍需等待元素可用并完成所有状态检查；

  6. **失效与重学**：找不到目标元素、状态检查不通过、API Schema 改变或最终状态错误时立即停止后续动作，把旧版本从可检索库移到 invalid 区，回退到完整 Agent 重新探索。旧文件保留用于审计和比较，不能继续被静默命中。

- **PreAct 实验**：这类程序在重复任务上实现 8.5–13 倍端到端加速（回放阶段不需逐步调用语言模型）；更重要的结论——**流程记忆必须同时具备动作前验证、动作后验证和存前独立验证**，否则系统容易得到危险假象：回放覆盖率 100%、每个按钮都点过了，但某个字段其实为空，任务从未真正完成。

- 实验 8-4 ★★★（从浏览器轨迹生成可验证工作流）：四阶段场景（探索生成 candidate → 独立回放验证 → 参数化复用 → 页面变化检出 fallback）。对照：简化基线只统计动作没抛异常 vs 实验组额外验证动作前页面、动作后页面、任务最终状态——比较"字段为空但发送按钮被点击""Save 已点击但数据未落库"等假成功场景的误判率。**没有重置回调时工作流必须停留在候选区；验证失败的版本不能被检索；参数化回放不得重复使用首次运行的收件人或内容；页面变化后必须停止危险的后续动作**。

- **Agent 修改自己的代码不意味着运行中的进程直接覆盖自身**：生产系统应从当前稳定版本创建候选分支，由 Coding Agent 生成最小补丁，依次通过静态检查、单元测试、安全扫描、失败轨迹重放和旧任务回归，再生成可灰度部署的新版本——把"自我修改"转化为可审计的软件发布流程。**第八章与第五章的边界：第五章提供修改系统的能力，本章提供由经验触发、以验证闭环约束的自我修改方法**。

- **可证伪的变更契约**（仅有"补丁尽量小"不足以支持可靠归因）：每个修改请求列出失败证据、推断根因、归属的 Harness 组件、候选修改、预期修复的行为、可能受损的既有行为、分别验证两者的用例。**Agentic Harness Engineering** 概括为组件、经验和决策三层可观测性：可编辑组件都有文件级表示；海量轨迹整理为可逐层下钻的证据；每次编辑在执行前声明影响预测、由下一轮结果验证——分数上涨才能与具体机制建立联系，而不只是一次不可解释的试错。

- **候选生成器输入不应只有失败案例**：Self-Harness 还提供必须保留的成功行为和此前被拒绝的修改记录——前者告诉 Agent 哪些性质不能在修复时被破坏，后者避免它换一种说法重复提交已失败的方案。**失败证据、成功约束与历史尝试共同构成有边界的候选空间**，比把全部源码和原始日志无差别塞给修改 Agent 更容易产生局部、可验证的改动。

- **工具创造遵循同一协议**：Alita 案例——Agent 需从《指环王》咕噜配音演员解说的 YouTube 360 VR 视频找出恐龙首次出现后紧接着提到的数字；发现自己缺字幕读取能力后搜索并测试 youtube-transcript-api、封装为新字幕工具、从字幕得到答案 100000000。**只有安全扫描、功能测试和后续任务复用都通过，新工具才进入能力库**。第四章主动工具发现解决"已有工具中哪个适合"、第五章解决"怎样编写工具"、本章关心"什么运行证据触发创造，以及新工具怎样成为经过验证的长期能力"。

- 实验 8-5 ★★★（由失败轨迹触发 Agent 自我修改）：多条"retryable=false 的错误仍被连续调用"轨迹 → 诊断模块聚合不同任务中相同故障、达到跨轨迹支持门槛才创建修改请求、定位到稳定版本 retry_policy.py → 候选生成器读取失败诊断 + 需保留的临时故障恢复行为 + 此前拒绝修改 + 稳定源码，先提交影响预测（"不可重试错误调用次数应下降、临时超时恢复率不应下降"）再输出最小代码 diff → 结果只能写入隔离候选目录 → 验证 Harness 编译候选、重放原始失败轨迹、检查不可重试错误是否立即停止并打开熔断器、重测临时超时是否仍按原阈值重试。概念对照：把"只在 Prompt 中增加一句不要重复调用"作为错误层定位的对照，说明**可确定执行的重试约束为什么应进入程序**。验收：所有检查通过只生成 release_to_canary；任一失败返回 reject_candidate；release_manifest.json 记录失败簇、来源轨迹、推断根因、目标组件与文件、代码 diff、预期修复、潜在回退、检查结果、候选版本和回滚版本。**生成补丁的 Agent 不能修改稳定代码、验证器、审计日志或批准自身发布的门槛**。



### 2.4 将经验写入参数



- 知识、指令和程序都建立在一个前提上：**目标能力能够被外部符号较完整地表达**。医疗影像理解、自然的语音韵律、消除文本模板化"AI 味"、长程规划等能力很难压缩成几条规则或工作流——必须通过后训练写入模型参数。

- **是否参数化并不由"任务是否长期稳定"单独决定**：新影像设备带来的域偏移仍可能需要 LoRA 或持续微调；快速变化的语言风格也可通过周期性偏好训练适应。稳定性影响更新频率和成本，但**能力的表示性质决定主要载体**。反过来，长期稳定的转账审批规则也不应只依赖参数记忆，服务端代码仍需提供确定性保障。

- 第七章已完整讨论 SFT、蒸馏和 RL。对持续进化而言，关键是**把经过评价的生产轨迹转化为训练数据**：高质量示范进 SFT、明确偏好形成成对数据、具有可靠环境奖励的交互用于 RL。进入训练前仍需去除隐私信息、过滤错误轨迹并保留独立回归集；训练后检查通用能力和安全对齐是否遗忘。

- **参数学习通常与外部方法协同**（医疗影像模型参数学视觉表征 + 知识库提供最新指南 + 代码测量病灶计算风险；自然客服语气通过偏好训练塑造整体分布 + Prompt 规定当前品牌身份 + 用户记忆适配个人沟通偏好）。持续进化不是四选一，而是把每种能力放到最适合表达和治理它的位置。



### 2.5 从更新产物到更新"更新方法"



- 另一条正交的轴：系统正在优化的究竟是某份产物的内容，还是产生、管理和验证这些产物的方法。优化对象逐层扩大：**单条规则或记忆 → 结构化上下文 → 工作流 → Harness 代码 → 产生候选方案的优化器代码**。这不是五种新的更新载体，而是五种不同的搜索尺度；知识、Prompt、Skill 和程序都可能出现在其中多个层级。

- **最内层只修改产物内容**（根据失败轨迹给系统提示加局部规则、给经验文档补例外条件）——作用面小、容易归因和回滚，应当是默认选择。但反复让模型重写整份 Prompt 或记忆会产生退化：旧版本少数重要细节在多轮改写后逐渐消失；相互制约的条件被合并成过度抽象原则。**Agentic Context Engineering（ACE）**把上下文维护成带稳定标识符的条目集合，由生成、反思、整理模块提出增量更新，再用确定性逻辑合并去重，而不是每轮重写越来越短的文本块。

- 再向外一层：优化"上下文应怎样被构造"——**Meta Context Engineering（MCE）**拆成内外两个循环：内层在给定管理方法下优化当前任务的上下文产物；外层根据多轮执行和验证结果，修改搜索、选择、过滤、格式化这些上下文操作本身。**修改一条检索规则是在改内容管理机制；让系统比较多种检索与整理机制、保留迁移效果更好的版本，才是在学习"如何管理上下文"**。

- 扩展到工作流和整个 Harness：**AFlow** 把多 LLM 调用组成的工作流表示为代码图，通过执行反馈搜索节点与控制流组合；**Meta-Harness** 让 Coding Agent 读取候选 Harness 的源码、分数和轨迹，搜索决定信息如何存储、检索和呈现的代码。**代码不只是一次生成的产物，还可以连同评估历史一起成为持续搜索的对象**。

- **优化层级并非越高越好**：搜索一条局部规则只需少量边界案例；搜索完整工作流或 Harness 面对更大候选空间、更高评估成本和更严重归因困难。**明确、反复出现且能定位到单一组件的故障，应优先做可审计的局部补丁；只有当局部修改长期无法解决跨组件问题，或现有管理方法本身成为瓶颈时，才值得上升到工作流、Harness 乃至优化器层**。无论上升到哪一层，评价器、权限边界和留出测试都必须位于可修改范围之外——搜索空间越大，这个可信根越重要。

- 实验 8-6 ★★★（把这本书交给 Hermes：它能升级自己吗）：不预设待修问题、不提供功能清单，只把本书十章正文和 Hermes 源码交给它，要求先理解书中原则、再审视自己实现、自主选择一项值得做的改进。**书和源码构成可读上下文，但稳定版本、独立 Reviewer 和验收测试位于 Hermes 修改权限之外**。实际运行：Hermes 读完本书后自主发现现有运行轨迹缺少可直接用于后续学习的结构化证据，选择把执行结果整理为保守的学习信号，亲自修改源码和补充测试。前三轮独立审查分别发现候选与真实数据格式、不同保存路径和计数语义间的不一致；每次问题返回原会话继续修正，第四轮审查接受候选。**拒绝在这里不是失败终点，而是自我改进闭环的一部分**。结论边界：证明 Agent 可以从长篇知识提炼原则、把原则映射到自身代码、在外部验证约束下完成一次自我更新；不证明这项更新已提升下游任务成功率（后者需单独消融实验）。实验思路由读者 Grace 贡献。

## 3. 构建可长期运行的持续进化闭环



- 四种更新方式只有进入同一个自主循环，才会从单次优化变成持续进化。**双循环结构**（图 8-5）：**在线执行循环**只完成任务并记录证据，不直接改写正式 Agent；**离线进化循环**聚合轨迹、诊断根因、生成候选修改，再通过验证门槛发布新版本。两者通过版本化的经验库和评估集连接。

- **Voyager**（较完整的持续进化循环，Minecraft）：根据当前能力选择新目标，通过环境反馈迭代程序，验证成功后把代码存入技能库，再组合旧技能解决更难任务。**自动课程、可执行技能和环境验证缺一不可**：只有技能库没有课程→不知道下一步学什么；只有自我反思没有环境验证→技能库积累错误；只有探索没有持久化→每次任务从头开始。三个互相咬合机制：**自动课程生成器**（根据当前物品、环境和已掌握技能提出下一个难度适中的目标，使探索不是随机漫游）；**技能库**（把成功程序保存为可检索可组合代码，高级技能可调用基础技能）；**迭代提示机制**（把环境观察、执行错误和自验证结果带回下一轮代码生成直到任务通过）。论文结果：3.3 倍独特物品、2.3 倍探索距离、解锁关键科技树里程碑最高快 15.3 倍、技能库可迁移到新世界——**这些指标衡量的是能力随经历增长的曲线，而非冻结 Agent 的一次考试成绩**。



### 3.1 从问题定位到经验沉淀



- **同一个表面问题可能需要不同修改方式**：客服 Agent 编造事实的幻觉可能是知识库缺事实、也可能是 Prompt 没要求引用；虚假承诺既可用指令纠正、也可由 Harness 强制检查回复与工具状态。**进化模块应先定位根因，再选择最小、最容易验证和回滚的修改对象**。证据不足的偶发故障不应立即触发学习，而应继续积累样本。

- 选择随经验增加而变化：新策略先作为经验文档供检索；多个案例反复验证后可提升为知识。知识三种表达方式：自然语言可清晰描述的规则沉淀为 Skill；步骤稳定无需自然语言理解能力则编译成工具代码；反映广泛隐式决策能力则进入后训练。



### 3.2 验证、发布与回滚



- **所有修改首先产生候选能力或候选 Agent，而不是直接覆盖生产版本**：知识文档验证检索后是否提高新任务表现；Prompt 和 Skill 检查边界案例与旧任务回归；程序在沙盒和重置环境运行测试；参数更新检查遗忘、安全和分布外任务。验证通过后仍应通过灰度发布观察真实流量；关键指标恶化时自动回滚到已知安全版本。

- **验证要区分两种经常混在一起的能力**：**Harness 更新能力（harness-updating）**是从轨迹中产生有价值的持久修改；**Harness 受益能力（harness-benefit）**是任务 Agent 在后续运行中找到、激活并正确使用这些修改。一个 Skill 可能写得完全正确，但较弱的任务模型没在合适场景加载它、或加载后无法长期遵循——任一种都会让最终成绩看起来"没有进化"。**不能只用端到端分数反推更新器好坏**。Lin 等人的模型替换实验表明两种能力与基础模型能力的关系并不相同；将二者拆开评估是普遍适用的方法。

- 表 8-3 持续进化的分层评估指标：



| 指标 | 回答的问题 | 主要证据 |

|---|---|---|

| 候选修改有效率 | 更新器是否提出了有价值的修改 | 候选在独立验证中的接受率与增益 |

| 产物激活率 | 任务 Agent 是否在正确场景加载了新 Skill、记忆或工具 | 检索、路由与工具调用轨迹 |

| 遵循成功率 | 激活后是否按新规则或流程执行 | 动作序列与过程验证器 |

| 留出任务增益 | 整体是否改善了未参与进化的任务 | held-out 成功率、质量与成本 |



- **诊断用双向模型替换**：固定同一份候选 Harness 只替换任务模型——强模型能受益而弱模型从不激活新产物 → 瓶颈在检索或路由；两者都能激活但只有强模型正确执行 → 瓶颈在指令遵循或长程规划；所有模型都退化 → 才更有理由怀疑修改本身。反过来固定任务模型、更换负责提出修改的模型单独比较更新器质量。

- **评估不是学习结束后的考试，而是自我进化中不可或缺的部分**。长期评价至少同时观察五类结果：**回退**（新经验是否与已有经验冲突、原本能通过的案例是否回退）；**泛化能力**（新经验在测试集尚未覆盖场景带来的提升）；**Token 效率**（完成任务消耗成本）；**安全性**（规则、隐私和拒绝边界是否随进化漂移）；**长期工程质量**（维护复杂度、架构一致性、所有权边界、向后兼容性、未来迁移和调试负担是否恶化）。**只解决了当前失败案例、却在其他已有案例或新领域退化，不是成功的持续学习**。



### 3.3 可验证闭环的边界：当"完成"不等于"进步"



- 闭环在 Coding、工具调用和业务状态变更等任务上最容易成立（测试、环境状态或确定性规则能快速反馈）。**开放式科研、战略规划和复杂产品设计则不同**：评价信号来得慢、正确答案不唯一、真正重要的目标（研究品味、长期价值、可维护性）很难写成即时分数。此时 Harness 可能把流程执行得非常完整，却只是稳定地产出"像成果的东西"，没有推动真实目标。

- **自动科研是代表性压力测试**（Trehan 与 Chopra 记录四次从研究想法走向论文的端到端尝试：三次在实现或评估阶段失败，只有一次完成整条流水线）。三类问题：

  1. **实现漂移**：原方案一旦变难，Agent 逐渐退回训练数据中更熟悉但偏离研究假设的普通实现；

  2. **认识论上的过度乐观**：信号可能只是噪声，系统却开始解释结果、添加补丁并宣布发现；失败和阴性结果更容易被忽略；

  3. **隐性判断力不足**：Agent 可以运行实验，却未必知道什么基线真正重要、哪个异常值得追踪、何时应该放弃假设。

- 不能靠换一个更会写论文的模型彻底解决，要改变证据和监督结构：

  - **结论与证据分离**：对引用、数字、方法和结论分别记录证据来源，最终文稿只是证据图的一种呈现（ScientistOne 的 Chain-of-Evidence 设计把每类声明链接到可审计来源——提高的是可追溯性，不自动保证研究问题有价值）；

  - **保留负面结果**：失败实验、被拒候选和停止原因写入不可变日志、与成功结果相同可检索地位——否则进化模块只看到幸存方案，会反复探索已证伪路径、学会把模糊结果解释成成功；

  - **维护搜索多样性**：开放式搜索不应只保留当前得分最高的一条链——候选池按机制差异、代码新颖性或假设类型保留若干暂时低分但不同质的分支，避免所有方案收敛成同一个易得分模板；

  - **让人类在更高层介入**：人的作用不只是危险工具调用前点"批准"，还包括定义问题、审查评价标准、解释反常结果、决定何时停止——在反馈模糊任务中，这些高层判断比逐步骤接管执行更难自动化、更有价值。

- 同样的限制存在于普通软件工程：单元测试全部通过只证明当前可观察行为满足测试，不证明代码库数月后仍易维护。**持续进化的上限，最终取决于系统能否评价它真正关心的目标，而不只是最容易测量的代理指标**。



### 3.4 持续进化的安全边界



- 自我进化能力有可能把一次错误变成长期风险：网页、邮件和工具输出中的提示注入若被总结成经验，可能跨会话反复生效；自动搜索的恶意软件包若被封装成工具，影响从一次沙盒运行扩散到所有后续任务；有缺陷的验证器还可能持续批准看似进步、实际退化的候选版本。**自我进化系统除了验证"是否更强"，还必须限制"谁能改什么、依据来自哪里"**。

- **第一道边界：证据与指令隔离**。原始网页、工具输出及其 LLM 摘要都属于不可信证据，不能当作指令执行，也不能直接纳入 Skill 等长期能力。**LLM 总结只是为了提高可读性和便于处理的转换，并不是把输入变得无害的净化过程**。系统按固定 schema 提取主张、原文位置和采集时间，同时保留原文与来源；提取出的字符串绝不能作为指令执行。模型给出的置信度也只是未经验证的估计，不能充当批准门槛。候选内容通过确定性的 schema、允许列表和来源检查，再以版本化 pull request 提交；独立于生成者的 reviewer 对照原始证据审查变更，高风险 Skill 上线前还应经过人工批准。

- **第二道边界：候选能力与正式能力隔离**。新知识、Prompt、Skill、程序和参数都先进入不可服务真实流量的候选区。新生成代码和外部依赖还要经过沙盒、权限检查、供应链扫描与行为测试等安全检查。通过后才能服务真实流量，成为正式能力。

- **第三道边界：安全机制不可自我修改**。业务 Agent 可以修改 Prompt、Skill、知识库、工具等，**但不能修改批准自身更新的验证器、测试用例、发布门槛、审计日志和稳定版本备份**——否则一个 Agent 只需降低测试阈值或删除失败用例，就能把退化伪装成进步。



### 3.5 睡眠学习：整合、遗忘与能力保鲜



- **"睡眠学习"是对离线整合的认知类比，并不要求任务真的在夜间运行**。在线 Agent 首要职责是完成当前任务并追加不可变证据；后台学习进程在空闲期或满足门控条件时读取一批新经历，比较新旧结论、合并重复项、解决冲突、提出候选更新并运行回归。把采集与整理分开，防止一次偶发成功、网络故障或恶意输入立刻改写长期能力，也允许使用更大批量和更便宜的模型完成整理。

- 典型睡眠学习周期五步：

  1. **触发**：达到时间间隔、新增轨迹数量、存储容量或错误频率门槛，并确认当前没有高优先级在线任务；

  2. **定向**：读取正式知识、Prompt、Skill 目录及其版本，了解已有能力和不可修改边界；

  3. **采集与整合**：从近期已评价轨迹中寻找新信号，合并重复内容，标记冲突与适用条件，优先生成局部补丁；

  4. **验证与审批**：在迁移集、保留集和安全集上评估候选，高风险写入等待人工批准；

  5. **修剪与索引**：更新检索索引，把长期不用或被新证据推翻的能力标为过期、归档或删除，同时保留来源和回滚版本。

- **用户记忆是最直观的例子，但要与行动经验区分**：Claude Code 自动记忆为每个项目维护 MEMORY.md 索引和按主题拆分的详细文件，会话启动只加载索引的有界前缀、其余按需读取；索引接近上限时要求 Agent 合并或移走细节——说明纯文本记忆也需要容量约束、分层加载和主动整理（当前公开机制主要是在会话中持续写入，不能简单等同于固定夜间后台任务）。

- **Hermes 给出更完整的后台进化案例**：长期信息分成有界的 MEMORY.md 与 USER.md、基于 SQLite/FTS5 的历史会话检索、按需加载的 Skill、以及 Honcho 等可选外部记忆提供者。**历史检索返回原始消息而非先由 LLM 摘要**，避免把检索和生成混成一个不可审计步骤。当任务包含较多工具调用、从错误或死路中恢复、收到用户纠正、或发现非显然工作流时，后台复盘可创建或局部修订 Skill；记忆和 Skill 写入还可经过审批门控。独立 Curator 跟踪 Skill 使用、陈旧和归档状态，在空闲期执行确定性修剪，可选运行 LLM 合并；变更前保存快照、错误整理可回滚。**这个案例把"记录—整合—验证—修剪"从比喻变成可运行的能力生命周期**。

- **持续进化也不是让知识、Prompt 和工具无限增长**——第二章上下文腐化会在更长时间尺度上重现（经验文档相互冲突、Prompt 被边界规则淹没、Skill 库出现重复能力、多次微调造成灾难性遗忘）。系统需要周期性离线整理：

  - 合并重复经验，保留来源和版本；

  - 把局部规则从全局 Prompt 移动到领域 Skill，保持全局 Prompt 整洁；

  - Prompt 和 Skill 保持结构清晰，像写给新员工的指导书，避免"99 条军规"式规则罗列；

  - 重新验证长期未使用的工具；

  - 删除被新证据推翻的知识；

  - 从原始基座模型重新训练 LoRA。

- 实验 8-7 ★★★（评估 Agent 是否在持续进化）：区分"会保存一次反馈""只会不断追加""能够更新、迁移并保留能力"三种长期行为，避免用重复运行同一批题目冒充持续学习。四阶段任务流：**学习阶段**（退款、身份核验、行李政策等有共享潜在规律的任务）→ **迁移阶段**（改变表述、用户和局部环境，检查旧经验能否用于新任务）→ **规则变化阶段**（行李上限从 20kg 更新为 23kg，要求替换或淘汰旧知识）→ **保持阶段**（重新测试没变化的能力和当前有效规则，测量更新是否造成遗忘）。每个带反馈任务结束后才允许更新外部记忆，当前题目的期望动作不能提前泄露给 Agent。对照组：static（不持久化反馈）/ append_only（能记住第一版规则却不会处理冲突或淘汰）/ evolving（保存版本并以新证据替换旧规则）。指标：逐阶段准确率和学习曲线、迁移准确率、收到新规则后恢复正确所需任务数、旧能力保持率、负迁移率、安全 Rubric 通过率、Token/延迟/存储成本；对真实系统还分别记录候选修改有效率、产物激活率和遵循成功率——**避免把"更新正确但没有加载"误判为更新失败**。**一个 Agent 即使最终准确率较高，只要仍引用已废止规则、靠违规捷径完成任务，或更新后遗忘原有能力，都不能判定为持续进化**。

## 4. 本章小结（书中原文要点）



- 持续学习正在成为 Agent 最重要的能力之一，但今天的模型还无法自行完成可靠的持续学习。推理时的上下文适应不会自动持久化，未经验证的在线参数更新又会放大噪声、攻击和能力漂移。**现阶段更可行的路径，是在模型外围建立可验证的学习系统**。

- Agent 从与环境的交互和评价中获得学习信号，再根据能力的表示性质更新知识、Prompt、Skill、程序或模型参数。系统也可以进一步优化管理和生成这些产物的方法，但**应优先采用可归因、可验证、可回滚的局部修改**。

- 持续进化需要把在线执行与离线学习分开：在线记录证据，离线生成并验证候选更新，再逐步发布、整理或回滚。这个闭环在结果可自动验证的任务上最可靠；对于目标模糊、反馈延迟的开放任务，**人仍需参与问题定义和评价标准的制定**。

## 5. 思考题（共 6 道，星级标注）



- ★★ 一条经验文档由三次成功轨迹和一次失败轨迹支持。失败发生在较新的 API 版本上。系统应如何判断这是经验被推翻，还是适用条件发生了变化？

- ★★ 客服 Agent 的用户满意度上升，但规则违规率也上升。为什么不能把满意度作为单一学习信号？你会怎样设计护栏指标？

- ★★★ 同一个"虚假承诺"问题可以通过 Prompt、Harness 检查或参数训练缓解。你会依据哪些证据选择修改位置？

- ★★★ Agent 能修改工具和验证器，却不应修改批准自身更新的可信根。你会如何划分这两部分的权限和代码边界？

- ★★ 经验知识库不断增长后，检索错误和知识冲突会抵消学习收益。如何设计版本、时效和淘汰机制？

- ★★★ 参数学习擅长自然语言风格，却难以保证硬性业务规则。请为医疗客服设计一套参数、知识、Skill 和代码约束协同的持续进化方案。
