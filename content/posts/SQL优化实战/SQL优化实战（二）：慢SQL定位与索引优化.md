## 一、慢 SQL 从哪来

MySQL 把执行时间超过阈值的语句记录到慢查询日志。第一步是确认慢查询日志开没开、阈值设了多少：

```sql
-- 查看慢查询日志是否开启、日志文件位置与阈值
SHOW VARIABLES LIKE 'slow_query_log';
SHOW VARIABLES LIKE 'slow_query_log_file';
SHOW VARIABLES LIKE 'long_query_time';
```

long_query_time 默认 10 秒，对绝大多数业务都太宽松。生产上通常调到 1 秒甚至更低，让更多「不健康但没到秒级」的语句也浮出来。打开方式：

```sql
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 1;
```

日志积累到一定程度，用系统自带的 mysqldumpslow 按执行次数或耗时排序，把最该优化的前几条捞出来：

```bash
mysqldumpslow -s t -t 10 /var/lib/mysql/xxx-slow.log
```

定位到具体某条 SQL 后，EXPLAIN 一把，对照上一篇讲的 type、key、Extra 三列判断问题出在哪。

## 二、索引设计的原则

索引能提速，但维护有成本，数量多了反而拖慢写入与优化器决策。建不建、建在哪几列，有一套通用原则。

### 1. 哪些字段值得建索引

- 不为 NULL 的字段，NULL 值让优化器更难处理，建议用短值替代
- 被频繁查询的字段
- 常作为 WHERE 条件的字段
- 频繁排序的字段，索引有序，能直接利用索引序省掉 filesort
- 经常用于连接的字段，比如外键列，注意外键可不建，但连接条件列值得建

### 2. 哪些字段要谨慎

- 频繁更新的字段慎建，更新要同步维护索引，代价大
- 区分度低的列慎建，比如性别字段，一查出来大半张表，索引意义不大

### 3. 数量与形态

- 单表索引建议控制在 5 个以内，MySQL 8.0 是超过 16 个才告警，但索引越多，优化器评估执行计划的开销也越大
- 尽量用联合索引代替多个单列索引，省空间、提更新效率
- 避免冗余索引，能命中(a, b) 的查询必然能命中 (a)，那么 (a) 就是冗余的，保留 (a, b) 即可
- 字符串字段用前缀索引代替普通索引，只取前几个字符，占用更小
- 定期清理长期未使用的索引，MySQL 5.7 可查 sys.schema_unused_indexes

## 三、七种索引失效场景逐一拆解

索引设计了，查询却吃不上，多半是踩了下面这些坑。每一条都配一句能落地的解法。

### 1. 联合索引不遵守最左匹配

联合索引按字段声明顺序组织，命中规则是最左前缀匹配，从左到右依次匹配，直到遇到严格范围查询。假设有联合索引 (a, b, c)：

- 查询 a=1 AND c=1，按最左在 a 上走索引，再用 c 过滤，部分命中
- 查询 c=1，缺最左列 a，整个索引用不上
- 查询 b=1 AND c=1，同样缺最左列，索引用不上

注意一个误区：大于等于、小于等于、BETWEEN 以及前缀 LIKE 不会中断匹配，只有大于、小于这种严格范围查询才中断。实践上把区分度高的字段放最左边可以过滤更多数据。

### 2. 在索引列上做计算、函数、类型转换

索引存的是原始值，对索引列套函数或运算后，优化器没法直接使用索引。比如 birthdate 是索引列，但写了 MONTH(birthdate)=3，索引就失效了。

```sql
-- 索引失效的写法
SELECT * FROM user WHERE MONTH(birthdate) = 3;
-- 改写为范围查询，能吃上索引
SELECT * FROM user WHERE birthdate >= '2026-03-01' AND birthdate < '2026-04-01';
```

### 3. 以 % 开头的 LIKE

LIKE 'abc%' 能走索引，LIKE '%abc' 无法利用索引的有序性，只能全表扫。这类需求通常要靠全文索引或搜索组件支撑。

### 4. OR 前后有一个条件的列没索引

WHERE a=1 OR b=2 这种，如果 a 有索引、b 没索引，OR 会让整个查询退化成全表扫。解法是给 b 也建索引，或者拆成两条查询用 UNION 连接。

### 5. IN 或 NOT IN 取值范围过大

IN 的取值多到覆盖了表的大部分行，优化器会权衡后放弃索引改全表扫。NOT IN 同理甚至更差，需要时尽量改写成等值或范围查询。

### 6. 隐式类型转换

索引列是字符串，拿数字去比较，MySQL 会做隐式类型转换，导致索引失效。比如手机号列 VARCHAR 存 '13812345678'，写成 WHERE phone = 13812345678 就不走索引，必须写成字符串字面量。

### 7. SELECT * 带来的连锁问题

SELECT * 本身不完全阻断索引，但会让覆盖索引失效并产生多余的数据传输。只取需要的列，让查询能落在覆盖索引上，是顺手就做的优化。

## 四、深分页与排序优化

线上最常见的两类慢查询，一类是深分页，一类是要排序。

### 1. 深分页的代价

LIMIT 1000000, 10 看着只取 10 条，但前面 100 万行都要扫过跳过。数据量大了两次方案：

- 延迟关联，先用覆盖索引把主键取出来，再凭主键回原表取完整数据。先走索引拿到小结果集，再关联回表，扫描量大幅下降
- 游标式分页，记住上一页最后一条的 id，用 WHERE id> 上页末尾 代替 LIMIT 偏移，适合自增主键的列表

```sql
-- 低效写法
SELECT * FROM t ORDER BY id LIMIT 1000000, 10;
-- 延迟关联写法
SELECT t.* FROM t
JOIN (SELECT id FROM t ORDER BY id LIMIT 1000000, 10) tmp
ON t.id = tmp.id;
```

### 2. 排序的优化思路

ORDER BY 出现 Using filesort 时，排序没吃上索引序。两个方向：一个是让排序列进索引，依靠索引天然有序免排序；另一个是建覆盖索引，让排序字段与查询字段都在索引里。上一篇文章的 cus_order 案例就是典型示范。

GROUP BY、ORDER BY 一起用时，如果字段顺序与联合索引顺序不一致，会额外出现 Using temporary，量大了要把两者凑到一个索引序里。

## 五、完整优化流程

把前面串成一套可执行的 SOP，面试时按这个顺序讲，既完整又显功力：

1. 开慢查询日志，定合理阈值，用 mysqldumpslow 捞出最慢的几条
2. 对目标 SQL 执行 EXPLAIN，看 type 是否落到 ALL、key 是否吃上索引、Extra 是否有 filesort 或 temporary
3. 若索引没吃上，对照七种失效场景逐一排查，修正写法
4. 若索引已吃上仍慢，看 rows，数据量确实大就上延迟关联或游标分页
5. 结构层面仍有瓶颈，才轮到分区、分库分表与读写分离这些架构手段
6. 每步优化后都要重新 EXPLAIN 对比 rows 与 Extra，确认收益，别凭感觉收工

## 小结

慢 SQL 优化的完整链条是「定位、诊断、设计、改写、验证」五环。定位靠慢查询日志，诊断靠 EXPLAIN，设计遵循「区分度高的列、别太多、联合替代单列、字符串用前缀」这几条原则，改写要避开七种索引失效场景，深分页与排序有专属解法，最后一步验证必须用 EXPLAIN 数据说话。
