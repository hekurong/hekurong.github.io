## 一、项目背景

面向变电站运维场景，把「识别故障、定位根因、给出检修建议」的人工排查流程自动化。人工方式要翻阅大量规程、逐条比对日志，慢且依赖经验。项目做成多 Agent 协作系统：Manager 负责拆解任务，取证类 Agent 并行收集设备信号、规程、波形证据，Auditor 审核收口，最后输出诊断结论。

多 Agent 链路长、角色多，两个问题最致命：任务状态与消息可靠性。进程一崩，跑到一半的任务是不是就丢了？消息发的重了、丢了怎么办？这些是运行时设计最先要回答的问题。

## 二、轻量运行时内核：消息信封与状态机

### 1. 消息信封统一协作语义

Agent 之间用消息通信，消息必须有一个统一的信封结构，把消息类型、载荷、来源、目标、请求 ID 全部包进去。统一信封让所有角色遵守同一套协作语义，路由与追踪都有抓手。

```go
type Envelope struct {
    ID        string          // 消息唯一 ID
    Type      string          // 消息类型：派活/回复/取消/心跳
    From      string          // 来源 Agent
    To        string          // 目标 Agent
    Payload   json.RawMessage // 载荷
    CreatedAt time.Time
}
```

消息带唯一 ID 是可靠投递的起点：接收方靠 ID 做去重，发送方靠 ID 做确认回执。

### 2. 五态状态机管理任务生命周期

每个任务都有清晰的生命周期，用五态状态机严格管理。状态的迁移是确定性的，任何时刻任务落在哪个状态都能回答。这是保证「消息不丢不重、链路全程可回溯」的底气。

状态机核心理念：状态迁移必须显式、可审计，非法迁移直接拒绝，杜绝任务在奇怪的半途状态里悬着。

### 3. Manager 原语：spawn、send、cancel

Manager 通过三个原子原语驱动整条链路：spawn 创建子任务，send 派发消息，cancel 撤销任务。原语化之后，任务编排变成对原语的组合调用，语义清晰且可观测。

```go
type Kernel struct {
    st *StateStore
}

func (k *Kernel) Spawn(agent string, job Job) (TaskID, error)
func (k *Kernel) Send(env Envelope) error
func (k *Kernel) Cancel(taskID TaskID) error
```

## 三、消息不丢不重：SQLite 单写者持久化

### 1. 为什么需要持久化

纯内存运行时在进程崩溃后什么都没了。多 Agent 链路动辄几十轮协作，任何一轮崩溃丢状态，整条链路就得重来。要让任务状态跨进程存活，必须落盘。

### 2. 单写者模型的取舍

选 SQLite 做状态存储，并且坚持单写者模型。为什么单写者：多 Agent 并发写同一份状态会互相覆盖，引入复杂的一致性协调。让状态只在主协程或主写者手里更新，其他节点通过消息请求状态变更，写冲突就没了。

```go
type StateStore struct {
    db *sql.DB
}

// 仅主写者调用，串行化所有状态变更
func (s *StateStore) Apply(change StateChange) error {
    // 单写者保证下，这里天然串行
    tx, _ := s.db.Begin()
    defer tx.Rollback()
    tx.Exec(`UPDATE tasks SET state = ? WHERE id = ?`, change.To, change.TaskID)
    return tx.Commit()
}
```

### 3. 崩溃恢复：未完成任务自动重发

进程崩溃重启后，从 SQLite 读回所有任务状态。未完成的任务识别出来后自动转入失败并重发，保证链路继续执行而不是静默中断。配合每条消息的唯一 ID，重发不会造成重复处理，接收方按 ID 幂等去重。

这条设计把两个可靠性指标都兜住了：至少一次交付靠持久化与重发保证，不重靠消息 ID 幂等保证。

## 四、Auditor 审核收口：确定性优于模型

### 1. 为什么审核不交给大模型

诊断结论直接指导检修决策，正确性要求高。大模型有幻觉风险，让模型自己审自己不可靠。Auditor 角色不接大模型，改用确定性规则引擎，对照行业规程卡掉不合规的推理路径。同样的输入必有同样的输出，行为的可预期性是大模型给不了的。

### 2. 本地规则与外部复核双重校验

链路尾部经 A2A 协议调用外部审核服务复核诊断报告。外部复核失败或超时降级处理，不阻断主链路。本地规则引擎保证基本合规，外部复核提供第二道防线，两道校验各有侧重。

降级是这里的设计精华：外部服务依赖网络，网络不可靠是必然，所以把外部复核设计成「尽力而为、失败不阻断」，主链路的可用性不被第三方拖垮。

## 五、MCP 工具服务器：把专业数据接进来

### 1. 三个 MCP 工具服务器

基于 MCP 协议实现三个电力专业工具服务器，随 Agent 容器以 stdio 子进程方式启动：

- **设备关联查询**。按设备实体展开关联的检修知识，取证 Agent 查一台设备能顺带拿到它的关联信息
- **混合检索**。走向量与关键词双路召回，RRF 重排合并结果，支撑 RAG 检索增强，规程检索质量明显好于单一检索
- **波形分析**。从录波文件里提取故障特征，供取证环节使用

三类专业数据源统一接入，Agent 用统一接口调用，不用关心底层是哪种数据。

### 2. 新增工具只加 server 不动编排代码

MCP 的可插拔是架构亮点：工具能力全部收敛到独立 server，Agent 编排代码只认 MCP 协议。要加新能力就新增一个工具 server，注册即可用，编排逻辑完全不用改。工具生态是横向展开的，不是纵向打补丁。

### 3. RRF 重排要点

混合检索的合并用 RRF（Reciprocal Rank Fusion）而非简单加权。RRF 不看检索分绝对值，只看排名位次，把多路检索结果按名次融合，规避了不同检索器的打分尺度不一致问题。实现简单、鲁棒性高，是面试里值得展开讲的细节。

## 六、可观测与成本优化：Langfuse 与 KV Cache

### 1. OTLP 链路观测

多 Agent 链路环节多、模型调用深，故障定位靠翻日志几乎不可能。项目接入 Langfuse，经 OTLP 协议上报追踪，任务与模型调用的 span 全量入库，与轨迹 JSONL 关联起来还原全链路。进度卡住能检测兜底，超时自动告警，观测数据反过来作为链路调优的依据。

### 2. 按模型定价统计 Token 成本

大模型调用是有成本的，观测不止看对错还看钱。把每次调用的 Token 用量入库，按模型定价核算单链路成本，成本可量化、可对比，优化有数据支撑而不是拍脑袋。

### 3. 静态前缀复用 KV Cache

诊断链路常达数十轮模型调用，上下文逐轮累积，Token 开销随链路变长快速放大。项目把系统指令与检索上下文固化为静态前缀，请求前缀直接命中 KV Cache 跳过重复计算。用对照实验验证收益，四组前后缓存开关对照，缓存命中 100%，单链路成本降幅约八成。

这项优化的意义一则省钱，二则说明白了一个重要原理：KV Cache 复用让多轮对话的长上下文不需要每次完整重算，是长链路成本收敛的核心杠杆。

## 七、面试追问与答题要点

- **Q：为什么状态存储用 SQLite 而不是 Redis 或 MySQL？**
  答：这是单机轻量运行时，SQLite 嵌入式零部署、事务完备，单写者模型下游冲突天然少。数据量不大、没有分布式需求，上 Redis 与 MySQL 是过度设计。
- **Q：A2A 外部复核挂了怎么办？**
  答：降级不阻断。本地规则引擎仍是主防线，外部复核是增强项，超时不等待、失败不阻塞，主链路结论照常产出，外部结果进日志备查。
- **Q：KV Cache 复用为什么能省这么多？**
  答：静态前缀的 KV 计算被缓存，多轮请求共享同一段前缀，不必每轮重算。前缀越长、轮次越多，复用收益越大，这是这类成本优化的核心杠杆。
- **Q：五态状态机具体哪五态、非法迁移怎么办？**
  答：典型五态如待执行、执行中、成功、失败、已取消。非法迁移直接拒绝并告警，保证状态始终落在设计过的集合内，杜绝悬空态。
- **Q：项目最值得讲的一点是什么？**
  答：轻量但完整。不堆重框架，围绕状态机、可靠投递、确定性审核、可插拔工具与可观测治理，把一条真实故障诊断链路在可控复杂度内跑通，还能量化优化收益。
